## 1. Purpose

This blueprint is the single authority for the governed foundation of Increment 1.
It binds three artefact families into one traceable whole:

1. **Requirements (REQs)** — what the system must do, who owns each row, where it
   came from, and which phase it lands in.
2. **Decisions (DECs)** — what we have decided, who approved it, and which
   Architecture Decision Record (ADR) records the rationale.
3. **Open Questions** — what we have not yet decided, who owns the answer, and
   whether external validation is required before the gate can be passed.

Phase 1 produces documentation and a linter only. **Zero application code is
written in Phase 1.** The repository skeleton (Django project, DRF
scaffold, package layout) is a Phase 3 deliverable. Phase 1 output is
limited to `docs/` and `scripts/`.

This rule is enforced structurally: there is no `src/`, no `manage.py`, no
`pyproject.toml` produced in this increment. Their absence is itself an
acceptance criterion.

## 2. Scope of Increment 1

Increment 1 delivers four capability areas and only four:

1. **Tenancy** — multi-tenant data and compute isolation primitives.
2. **Identity** — authentication, federation, role assignment, delegation.
3. **Audit** — append-only, hash-chained audit log with query and export.
4. **Reliable Core** — idempotency, backpressure, circuit breakers,
   observability, configuration, feature flags.

**Explicitly out of scope for Increment 1:**

- Ledger (any posting, double-entry, or balance computation) — Phase 11.
- First customer deposit — Phase 12 or later.
- KYC vendor integration — Increment 2 (vendor selection is open, see Q6).
- Sanctions/PEP screening runtime — Increment 2 (vendor selection is open,
  see Q7).
- Payment instruction execution — Increment 3.
- FX conversion — Increment 3.

The triage rule (see §9) is the only authority for what is in or out of
Increment 1. `docs/requirements/triage-table.md` is the single pointer for
workflow-level triage; `docs/requirements/scope.md` is the single pointer for
capability-level triage. No other document may override either.

## 3. Glossary

| Term | Definition |
|---|---|
| REQ | A requirement row in `traceability.md`. Carries ID, title, category, status, scope, owner, source. |
| DEC | A decision row in `traceability.md`. Carries the same fields plus an optional ADR reference. |
| ADR | Architecture Decision Record. A standalone markdown file under `docs/adr/` whose YAML front-matter cites exactly one DEC via `DEC: DEC-00XX`. |
| ADR-DEC mapping law | The set of invariants in §8 and linter rule 7. Every ADR cites exactly one DEC; every DEC cites at most one ADR; every ADR is cited by exactly one DEC. |
| Application code | Per DEC-0023: any source artefact whose primary purpose is to execute business logic in production. Excludes: docs, scripts under `scripts/`, linters, fixtures, schema definitions consumed by tooling, ADR stubs. Includes: Django models, DRF serializers/views, service-layer classes, domain modules, infrastructure adapters, migration files generated by `makemigrations`. |
| Agent | A delivery agent per DEC-0022. Nine agents exist. Each ships on a fixed schedule with a shadow→live promotion gate. |
| Shadow mode | An agent produces output that is reviewed by a human but is not authoritative. The agent's output is logged but does not mutate the governed baseline. |
| Live mode | An agent's output is authoritative. A shadow agent must satisfy the promotion gate (see DEC-0022) before going live. |
| Phase | A unit of execution-layer delivery. There are 25 phases derived from 27 stages (see DEC-0021). |
| Stage | A unit of work in the original 27-stage plan. Two stages were merged into adjacent phases per DEC-0021 / errata E3. |
| Increment | A bundle of phases delivered under a single governance envelope. Increment 1 = Phase 1 only (foundation). |
| BLOCKED | A status for open questions whose resolution requires external validation (counsel, pilot partner, funder). A BLOCKED question cannot be unblocked by internal debate alone. |
| HUMAN-APPROVED | A status for decisions in the Legal, Regulatory, Licensing, Business, Budget, or Vendor categories that have received written sign-off from the named approver. Required by linter rule 5. |

## 4. System context

The system is a B2B operating-system provider for regulated financial
workflows. The provider licenses a multi-tenant platform to financial
institution customers (banks, money transmitters, EMIs, fintechs). Each
customer operates as a tenant with isolated data and isolated
configuration. The provider is responsible for the platform; the customer is
responsible for the workflows configured on it.

The business model (DEC-0024) is **Option A**: subscription plus usage,
sold to institutions, with the provider operating the platform as a
regulated service provider (not as a direct lender, deposit-taker, or
money issuer). Whether the provider requires licensing in any given
jurisdiction is OPEN (Q1, Q2) and BLOCKED on external counsel.

| 2 | Repo skeleton; CI; dev environment | Phase 3 begins repo scaffold. |

| 4–7 | Identity: OIDC, SAML, sessions, MFA | |

The 27 → 25 reduction arises from two merges documented in errata E3 and

management" were merged into Phase 7; (b) the original "stage 22: recon
rules" and "stage 23: recon runs" were merged into a single Phase 22.

## 6. Agent delivery model

Per DEC-0022, nine delivery agents operate on a fixed schedule. Each agent
has a defined shadow period and a promotion gate. The gate requires:

1. A documented runbook.
2. Three consecutive shadow runs with zero P0 findings.
3. A human approver sign-off recorded in the agent's promotion log.
4. A rollback procedure tested at least once.

The agent roster, schedules, and promotion status are governed outside this
blueprint (in the operations runbook). The blueprint's only concern is that
agent outputs which touch the governed baseline (REQs, DECs, ADRs, the
linter) must come from a **live** agent, not a shadow one. Phase 1 outputs
are human-authored; agents are first eligible to contribute from Phase 2
onward.

## 8. Decision taxonomy and ADR-DEC mapping law

Per DEC-0023, the ADR-DEC mapping law is:

1. Every ADR file under `docs/adr/` MUST cite exactly one DEC in its YAML
   front-matter, in the form `DEC: DEC-00XX`.
2. Every DEC row MAY cite at most one ADR, in the `ADR` column of the DEC
   table.
3. Every ADR MUST be cited by exactly one DEC. (No orphan ADRs; no
   ADRs cited by two or more DECs.)
4. ADR and DEC IDs are independent number spaces. `ADR-0007` and `DEC-0007`
   are not required to refer to the same decision.
5. When a DEC is superseded, its ADR is marked `Superseded` and a new ADR
   is created for the superseding DEC. The old ADR's front-matter gains a
   `Superseded-By: ADR-00YY` field but its `DEC:` citation is not edited
   (the old DEC keeps its old ADR; the new DEC gets the new ADR).

The DEC seed (24 rows) is:

| ID | Decision | ADR |
|---|---|---|
| DEC-0001…0020 | 1:1 with ADR-0001…0020 | yes (per row) |
| DEC-0021 | Execution-layer phase grouping (27 stages → 25 phases) | ADR-0021 |
| DEC-0022 | Agent delivery schedule + shadow→live promotion gate (9 agents) | none |
| DEC-0023 | Semantic definitions: "application code"; DEC↔ADR mapping law | none |
| DEC-0024 | B2B OS provider business model (Option A) — HUMAN-APPROVED | none |

The 21 ADR stubs (`ADR-0001.md` … `ADR-0021.md`) are committed alongside
this blueprint. Each stub contains YAML front-matter (including the
`DEC:` citation), a title, a Status field, a Context section (one
paragraph), and a Decision section (one paragraph). Full Context /
Decision / Consequences sections are a Phase 2 deliverable per ADR.

## 9. Triage rule

Increment 1 delivers **Tenancy, Identity, Audit, Reliable Core**. The
triage rule is enforced in three places:

1. **Capability level** — `docs/requirements/scope.md` is the single
   authority. Any capability not listed there is out of Increment 1.
2. **Workflow level** — `docs/requirements/triage-table.md` is the single
   authority. Exactly 10 workflows are triaged there. Any workflow not
   listed there is implicitly out of Increment 1 and must be added to the
   table before any work begins on it.
3. **REQ level** — every REQ row in `traceability.md` carries a `Scope`
   field. REQs scoped to Phase 11 or later are not deliverable in
   Increment 1. The linter (rule 3) enforces the scope enum.

The triage rule is non-negotiable. If a Phase 11+ REQ is found to be a
prerequisite for a Phase 1 deliverable, the prerequisite must be split:
extract the Phase 1-relevant slice as a new REQ with a Phase 1 scope, and
leave the original REQ at its later scope. The split is recorded as a
supersession row.

## 10. Phase 0 evidence gates

Phase 2 does not start until Phase 0 evidence has been reviewed and
signed. Three gates must all pass:

1. **Legal gate** — jurisdictions and licensing paths confirmed or marked
   BLOCKED. BLOCKED means Phase 2 does not start; pivot or kill.
2. **Commercial gate** — pilot partner(s) identified or marked BLOCKED.
3. **Financial gate** — budget for Phases 1–3 confirmed or marked BLOCKED.

The gate template lives in `docs/phase-0-evidence.md`. Q1, Q2, Q4, and Q5
in `unresolved-decisions.md` feed the three gates directly. If any of
those four questions is BLOCKED at the gate review, the gate fails and
Phase 2 is held. There are no exceptions to this rule and no override
mechanism.
