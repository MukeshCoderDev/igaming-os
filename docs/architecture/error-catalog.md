This document is the human-readable rendering of the error catalog in
`src/noventra/errors/catalog.py`. It is generated by
`python manage.py generate_error_catalog` (Phase 5+ deliverable;
Phase 4 is manual). The catalog is the single authority; this doc is
a derived artifact. If the two disagree, the catalog is correct and
this doc must be regenerated.

## 1. Format

Each error code produces an RFC 7807 problem+json response with the
following shape:

```json
{
  "type": "https://noventra.example/errors/<code>",
  "title": "<short, human-readable title>",
  "status": <HTTP status>,
  "detail": "<formatted detail message>",
  "code": "<code>",
  "i18n_key": "<i18n key>",
  "correlation_id": "<ULID>",
  "instance": "<optional URI>"
}
```

In DEBUG mode, a `traces` field is added with the stack trace. In
production, `traces` is never present.

## 3. Constraints (enforced by linter rule 19)

1. **One HTTP status per code.** No code maps to multiple statuses.
2. **Every code has an i18n key.** The i18n key resolves via Django's
   i18n system. Default locale: en.
3. **Every code has a title and detail template.** Templates use
   `{name}` placeholders that are filled from `detail_params`.
4. **correlation_id always present.** Even for errors with no
   request context, the correlation_id is the empty string or the
   background-task ID.
5. **Stack traces in logs only.** The `traces` field is dev-only
   (DEBUG=True). Production never includes it.

## 4. Adding a new error code

1. Add a tuple to `ERROR_CATALOG` in
   `src/noventra/errors/catalog.py`.
2. Add the i18n key to the locale files (Phase 5+ i18n work).
3. Regenerate this document (Phase 5+: `python manage.py
   generate_error_catalog`; Phase 4: manual edit).
4. Add a unit test asserting the new code's response shape.
