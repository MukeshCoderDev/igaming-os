# ADR-0003 — Tenant isolation via row-level security

## Context

Multi-tenancy must enforce isolation at the data layer so that a bug in application code cannot leak one tenant's data to another. Schema-per-tenant and database-per-tenant models raise operational cost (N× migrations, N× backup complexity) and complicate cross-tenant analytics. MB-REQ-0001 and MB-REQ-0002 mandate isolation at both data and compute layers.

## Decision

Use a single PostgreSQL database with row-level security (RLS) policies keyed on a `tenant_id` column. The tenant context is set per request via `SET LOCAL app.tenant_id = ...` and cannot be overridden by application code. Cross-tenant synchronous operations are forbidden (MB-REQ-0023). Enforced structurally: every table that holds tenant data has a `tenant_id` column with NOT NULL + FK to the tenant aggregate.

## Alternatives

Alternatives considered: (a) schema-per-tenant — operational explosion (N× migrations); (b) database-per-tenant — cost explosion at scale; (c) application-level filtering (no RLS) — relies on developer discipline; one missed WHERE clause leaks data. (a) and (b) rejected for operational cost; (c) rejected for unacceptable leak risk.

## Consequences

RLS adds query overhead (~5–10% in benchmarks) and complicates cross-tenant analytics (must use a separate analytics replica with RLS disabled). Migration of legacy data requires backfill of `tenant_id`. Debugging is harder: RLS hides rows from interactive sessions.

## Validation Plan

Phase 3: red-team test that attempts to read another tenant's rows via SQL injection, ORM misuse, and direct connection. Phase 4: performance benchmark comparing RLS-on vs RLS-off at 1k req/s. Phase 11: validate that ledger postings (DEC-0011) compose with RLS without cross-tenant leakage.
