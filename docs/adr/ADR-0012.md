# ADR-0012 — Decimal arithmetic for all money

## Context

Floating-point arithmetic introduces rounding errors that compound across ledger postings. Financial systems must use exact decimal arithmetic to avoid these errors. IEEE 754 decimal types or scaled integers are the standard approaches.

## Decision

All money values are represented as decimals with explicit precision (typically 4 decimal places for internal computation, 2 for display). Floating-point is forbidden for money. Rounding rules are explicit per operation and recorded in audit entries. In Python: `decimal.Decimal`; in Postgres: `NUMERIC(18, 4)`.

## Alternatives

Alternatives considered: (a) integer cents — loses precision for FX and fractional-cent operations; (b) floating-point with tolerance — invites bugs; (c) custom Money class with arbitrary precision — over-engineered. (a) rejected for FX precision; (b) rejected for bugs; (c) rejected for complexity.

## Consequences

Decimal arithmetic is slower than integer or float; performance impact is small (~10%) but measurable. Interoperability with external systems that use float (e.g., some payment APIs) requires explicit conversion at the boundary.

## Validation Plan

Phase 11: implement; verify that a 1-cent rounding test (repeated 1M times) produces no drift. Phase 11: integration test with a payment API that uses float; verify boundary conversion. Phase 11: audit log records the rounding rule applied per operation.
