# ADR-0049 — Consent immutability pattern — hash-chained

## Context

Consents are legal evidence. They must be tamper-evident. Phase 7 built a hash-chain infrastructure for audit events. Consent records should reuse that infrastructure: hash-chained, insert-only, with chain break detection. Revocation creates a NEW record (status=revoked), not a mutation of the original granted record.

## Decision

Adopt hash-chained consent immutability, reusing Phase 7 infrastructure (ADR-0035 algorithm, scope, payload, concurrency). Chain scope = per-player (each player has their own consent chain). Chain verifier extended for consent chains (verify_audit_chain --scope=consent:player_uuid). Chain break detection applies (audit.chain_break_detected). Revocation: INSERT a new consent record with status=revoked, revoked_at=NOW(), referencing the original consent_id. The original record is never UPDATEd or DELETEd (insert-only trigger per ADR-0038).

## Alternatives

Alternatives: (a) insert-only without hash chain — no tamper-evidence; (b) hash-chained with separate infra — duplication; (c) mutable consents with audit trail — tamper risk. (a) rejected for no tamper-evidence; (b) rejected for duplication; (c) rejected for tamper risk.

## Consequences

Per-player chains add chain head management overhead (one head per player). Chain verifier must handle many small chains (partitioned by player). Revocation creates 2 records (original + revoked), increasing storage. Querying 'current consent' requires finding the latest record per (player, purpose, channel).

## Validation Plan

Phase 9: consent hash-chain (reuse Phase 7 trigger pattern). Phase 9: chain verifier extended. Phase 9: revocation test (new record, original unchanged). Phase 9: chain break detection test.
