# ADR-0112 — Risk Case Management — Evidence Aggregation & Case Linking

## Context

Risk cases aggregate evidence from multiple modules into a single investigation unit. A single suspicious deposit might trigger a signal, but the investigation requires seeing the player's full activity history: KYC documents (Phase 10), payment records (Phase 12), bonus history (Phase 13), game rounds (Phase 15/16), RG signals (Phase 14), and all prior risk signals (Phase 18). Without aggregation, the compliance officer sees fragments; with aggregation, they see the full picture.

The RiskCase is distinct from:
- Phase 10 KYC case (KYC document review workflow; 16-state FSM)
- Phase 12 dispute case (chargeback dispute workflow; 5-state FSM)
- Phase 13 bonus abuse flag (abuse detection flag; not a full case)

These are separate workflows with separate FSMs. A RiskCase links to them via foreign keys (kyc_case_id, dispute_case_id, abuse_flag_id) but does not replace them. Case linking is the mechanism for full investigation: a single RiskCase can reference a KYC case, a dispute case, a bonus abuse flag, and a SAR case simultaneously, giving the compliance officer a unified view.

## Decision

### RiskCase model

| Field | Type | Notes |
|---|---|---|
| `case_uuid` | UUID PK | |
| `tenant_uuid` | UUID | Tenant scope (RLS) |
| `player_uuid` | UUID | Player under investigation |
| `case_type` | enum | aml_investigation, fraud_investigation, rg_review, bonus_abuse, payment_dispute |
| `status` | enum | open, under_investigation, pending_approval, closed_resolved, closed_escalated, closed_dismissed |
| `priority` | enum | low, medium, high, critical |
| `assigned_to` | str | Compliance officer assigned (named human) |
| `evidence` | JSONB | Aggregated evidence (see below) |
| `kyc_case_uuid` | UUID FK → Phase 10 KYC case (nullable) | Link to KYC case |
| `dispute_case_uuid` | UUID FK → Phase 12 dispute case (nullable) | Link to dispute |
| `abuse_flag_uuid` | UUID FK → Phase 13 abuse flag (nullable) | Link to bonus abuse |
| `sar_case_uuid` | UUID FK → SARCase (nullable) | Link to SAR (if escalated) |
| `cumulative_risk_score` | decimal | Player's risk score at case creation |
| `created_at` | datetime | auto_now_add |
| `updated_at` | datetime | auto_now |

### FSM

```
open → under_investigation → pending_approval → closed_resolved (terminal)
                                              → closed_escalated (terminal; → SAR)
                                              → closed_dismissed (terminal)
```

- `open → under_investigation`: Compliance officer assigned; evidence aggregation begins.
- `under_investigation → pending_approval`: Investigation complete; punitive action requested (ADR-0113) or SAR escalation requested (ADR-0111).
- `pending_approval → closed_resolved`: Approved; punitive action executed; case resolved.
- `pending_approval → closed_escalated`: Escalated to SAR; SAR case created; risk case closed.
- `pending_approval → closed_dismissed`: Dismissed with documented justification.

### Case types (5)

1. **aml_investigation** — AML transaction monitoring case (triggered by critical risk signal).
2. **fraud_investigation** — Fraud case (triggered by fraud signal: chip dumping, bonus abuse with fraud indicators).
3. **rg_review** — Responsible gambling review (triggered by Phase 14 RG distress signals).
4. **bonus_abuse** — Bonus abuse case (triggered by Phase 13 abuse detection).
5. **payment_dispute** — Payment dispute escalated to risk (triggered by Phase 12 dispute that reveals risk indicators).

### Evidence aggregation (pull from multiple modules)

The `evidence` JSONB field contains a structured aggregation of evidence from all relevant modules:

```json
{
  "ledger_entries": [...],           // Phase 11: transaction history (UUIDs + summary)
  "payment_records": [...],          // Phase 12: deposit/withdrawal history (UUIDs + summary)
  "bonus_records": [...],            // Phase 13: bonus awards + abuse flags
  "game_rounds": [...],              // Phase 15/16: relevant game rounds (UUIDs + summary)
  "kyc_documents": [...],            // Phase 10: KYC docs + PEP/sanctions results
  "rg_records": [...],               // Phase 14: SE, limits, distress signals
  "risk_signals": [...],             // Phase 18: all prior risk signals for this player
  "aggregated_at": "2026-10-28T...",
  "aggregated_by": "compliance_officer_name"
}
```

Evidence is aggregated on case creation and refreshed on each investigation step. The full evidence payload is stored (not just UUIDs) to ensure the case is self-contained for audit — even if source records are later archived, the case evidence is preserved.

### Case linking

- Link to Phase 10 KYC case (`kyc_case_uuid`): for AML cases where KYC status is relevant.
- Link to Phase 12 dispute case (`dispute_case_uuid`): for payment dispute cases that escalate to risk.
- Link to Phase 13 bonus abuse flag (`abuse_flag_uuid`): for bonus abuse cases.
- Link to SAR case (`sar_case_uuid`): for AML cases that escalate to SAR filing.

Case linking is bidirectional: the linked case (e.g., KYC case) also records a reference back to the RiskCase. This allows compliance officers to navigate from any case to the related risk case.

### Investigation workflow

1. Compliance officer assigned (`assigned_to`).
2. Evidence aggregated (JSONB populated from all relevant modules).
3. Investigation: compliance officer reviews evidence; may request additional information from other modules.
4. Decision:
   - **Close (resolved):** investigation complete; no punitive action; case resolved.
   - **Close (dismissed):** investigation complete; signal was false positive; case dismissed with justification.
   - **Escalate to SAR:** AML suspicion confirmed; escalate to MLRO via SAR workflow (ADR-0111).
   - **Request punitive action:** punitive action needed (ADR-0113); case moves to `pending_approval`.

## Alternatives

- **Single case model across all modules** (rejected). Different workflows; case type distinction required. A KYC case has a 16-state FSM; a risk case has a 6-state FSM; merging them would force one to compromise.
- **No case linking** (rejected). Compliance officer sees fragments; cannot navigate between related cases. Investigation quality suffers.
- **Evidence as UUIDs only (no payload)** (rejected). Source records may be archived later; case evidence must be self-contained for audit.
- **No case type enum** (rejected). Different case types have different workflows (AML → SAR; fraud → punitive; RG → protection). Without typing, workflow routing is impossible.
- **Auto-close cases** (rejected). Compliance officer judgment required; auto-close would miss escalation opportunities.

## Consequences

- RiskCase model with 6-state FSM + evidence aggregation JSONB.
- Case linking to Phase 10/12/13 + SAR (bidirectional references).
- 5 case types with distinct workflows.
- Evidence payload stored (not just UUIDs) for audit self-containment.
- Compliance officer assignment (named human; CODEOWNERS).
- Linter rule 151: RiskCase model exists with evidence aggregation + case linking fields.

## Validation Plan

- **Case creation test:** create a RiskCase; assert evidence aggregated from all relevant modules.
- **Evidence aggregation test:** player with ledger entries + payments + bonuses + game rounds + KYC docs; create case; assert evidence JSONB contains all.
- **Case linking test:** create RiskCase linked to KYC case + dispute case + abuse flag; assert bidirectional references.
- **FSM transition tests:** open → under_investigation → pending_approval → closed_resolved; open → under_investigation → pending_approval → closed_escalated (SAR); open → under_investigation → closed_dismissed.
- **Escalation to SAR test:** AML case → pending_approval → closed_escalated; assert SAR case created.
- **Linter rule 151 test:** grep for RiskCase model; assert evidence + linking fields present.
