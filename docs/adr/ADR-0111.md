# ADR-0111 — SAR/STR Workflow — MLRO Decision, FIU Submission & Tipping-off Prohibition

## Context

SAR/STR (Suspicious Activity Report / Suspicious Transaction Report) workflow is regulator-mandated across all FATF-member jurisdictions. The MLRO (Money Laundering Reporting Officer) is the single named human responsible for deciding whether to file a SAR to the FIU (Financial Intelligence Unit). This is not a committee decision; it is a named-individual decision with personal legal liability.

The tipping-off prohibition is the most severe constraint in the entire AML framework. Under UK MLR 2017 §333A, US BSA §5318(g)(2), and equivalent laws in every FATF-member jurisdiction, informing a player that a SAR has been filed is a **criminal offence** punishable by imprisonment (up to 2 years in the UK; up to 5 years in the US). This is not a fine — it is personal criminal liability for the individual who tips off. The prohibition applies to everyone in the organization, not just the MLRO.

Phase 10 (KYC) established a SAR stub and the MLRO role. Phase 18 implements the full SAR workflow: signal escalation → MLRO review → FIU submission → closure, with tipping-off prohibition enforced at the code level (linter rules 155 + 158) and at the data level (MLRO-only visibility).

## Decision

| `created_at` | datetime | auto_now_add |
| `updated_at` | datetime | auto_now |

**MLRO-only visibility:** SAR records are accessible ONLY to the MLRO role. This is enforced at:
- DB layer: RLS policy restricts `sar_case` table to `mlro` role.
- Application layer: API endpoints require `mlro` role; non-MLRO requests return 403.
- Audit layer: every SAR read is audited (Phase 7 pattern); non-MLRO read attempts are flagged.

### FSM

```
signal_escalated → mlro_review → filed → closed (terminal)
                                ↘ dismissed (with documented justification)
```

- `signal_escalated → mlro_review`: A critical RiskSignal is escalated to the MLRO for review. The MLRO sees the signal, the evidence, and the player's risk profile.
- `mlro_review → filed`: The MLRO decides to file a SAR. Composes the SAR narrative. Submits to FIU (manual portal or Q5-blocked API). FIU confirmation ID recorded. Account may be frozen per jurisdiction rules.
- `mlro_review → dismissed`: The MLRO decides NOT to file. Must document justification (audited). The signal is dismissed; the case may be closed.
- `filed → closed`: The SAR is closed after filing. Retention timer starts (5-10 years per jurisdiction; OQ-RISK-004).

### MLRO decision

The MLRO is the single named human responsible for the file/dismiss decision. This is NOT a committee decision; it is personal legal liability. The `filed_by` field records the MLRO's name. The MLRO role was ratified in Phase 10 (DEC-0061, ADR-0056).

### FIU submission

- **Manual (portal):** MLRO composes the SAR narrative in the admin UI; downloads the SAR; submits via the FIU portal (NCA SAR Online in UK; FinCEN BSA E-Filing in US; BaFin portal in Germany; Tracfin portal in France). FIU confirmation ID entered manually.
- **API (Q5-blocked):** Automated submission via FIU portal API. Q5-blocked for vendor selection (each FIU has its own API; OQ-RISK-002). Deferred to Phase 22+.

### Account freeze on filing

On SAR filing, the player's account MAY be frozen per jurisdiction rules. This is configurable (Q1-blocked for specific rules). The freeze uses the Phase 14 kill-switch pattern (synchronous; <200ms SLO). The freeze is a punitive action (ADR-0113) and requires dual control if the jurisdiction mandates it.

### Tipping-off prohibition (Law 14 + Phase 10 rule 67)

**This is the most critical constraint in Phase 18.** Violation is criminal liability.

- **Player must NOT be informed of SAR filing.** No email, no in-app notification, no SMS, no push notification. The player must not know a SAR exists.
- **Linter rule 155:** no code path notifies player of SAR. Grep scans codebase for any user-facing notification referencing SAR. Zero findings required.
- **Tipping-off grep:** CI scans all notification templates, email subjects, SMS templates, push notification text for the strings "SAR", "suspicious activity report", "suspicious transaction report", "FIU", "financial intelligence unit", "MLRO". Zero findings required.
- **MLRO-only visibility (linter rule 158):** SAR records accessible only to MLRO role. Extends Phase 10 rule 67.
- **Audit:** every SAR action (creation, review, filing, dismissal, read) is audited (Phase 7). Non-MLRO read attempts are flagged as security incidents.

### Retention

5-10 years per AML regulations (Q1-blocked for specific periods; OQ-RISK-004):
- UK: 5 years from end of relationship
- US: 5 years from filing
- EU: 5 years (AMLD5; some member states 10 years)
- Germany: 10 years (GwG §8)

Retention is enforced via insert-only trigger (per Phase 7 pattern). Deletion before retention expiry is forbidden at DB layer.

## Alternatives

- **Auto-file SAR** (rejected). MLRO judgment is regulator-mandated. The MLRO must review the evidence and decide whether the suspicion meets the filing threshold. Auto-filing would flood the FIU with low-quality SARs and the MLRO's personal liability would be unbounded.
- **No tipping-off prohibition** (rejected). Criminal liability. This is not negotiable.
- **Committee decision (not MLRO)** (rejected). Regulator-mandated single named human. Committee decisions dilute accountability.
- **API submission only (no manual)** (rejected). Q5-blocked; each FIU has its own API. Manual portal submission is the Stage A path.
- **SAR visible to all compliance staff** (rejected). MLRO-only visibility is the Phase 10 pattern; extends to Phase 18. Broader visibility risks tipping-off (a compliance officer might mention the SAR to the player).
- **Retention <5 years** (rejected). Regulator-mandated minimum 5 years.
- **Retention >10 years** (rejected). Exceeds regulatory maximum; unnecessary storage cost.

## Consequences

- SARCase model with FSM + MLRO-only RLS.
- MLRO role required (Phase 10 already ratified).
- FIU submission workflow (manual portal; API Q5-blocked).
- Tipping-off prohibition enforced at code level (linter rule 155) + data level (linter rule 158 MLRO-only).
- Retention 5-10 years per jurisdiction (Q1-blocked; OQ-RISK-004).
- Account freeze on filing (Phase 14 kill-switch pattern; configurable per jurisdiction).
- Every SAR action audited (Phase 7).
- Linter rule 149: SAR MLRO-only visibility enforced.
- Linter rule 155: no code path notifies player of SAR.
- Linter rule 158: SAR visibility MLRO-only (extends Phase 10 rule 67).

## Validation Plan

- **SAR filing test (end-to-end):** escalate a critical signal → MLRO review → file SAR → FIU confirmation ID stored → account frozen → status `filed`. Every step audited.
- **SAR dismissal test:** escalate signal → MLRO review → dismiss with justification → status `dismissed`. Justification audited.
- **Tipping-off grep test (zero findings):** scan all notification templates, email subjects, SMS templates for SAR-related strings. Assert zero findings.
- **MLRO-only visibility test:** non-MLRO user attempts to read SARCase; assert 403 + audit flag.
- **Retention test:** attempt to delete SARCase before retention expiry; assert DB raises.
- **Linter rule 155 test:** grep for notification code referencing SAR; assert zero matches.
- **Linter rule 158 test:** grep for SARCase access code; assert all paths require MLRO role.
- **Linter rule 149 test:** grep for SARCase RLS policy; assert MLRO-only.
