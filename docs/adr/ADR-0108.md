# ADR-0108 — GGR/NGR Model & Regulatory Reporting

## Context

GGR (Gross Gaming Revenue) and NGR (Net Gaming Revenue) are the two metrics every iGaming regulator requires operators to report. UK GC requires monthly GGR; MGA requires quarterly GGR/NGR; Ontario AGCO requires quarterly; each US state gaming commission has its own cadence and format. The formats differ — UK GC wants a CSV with specific columns; MGA wants an Excel workbook with multiple tabs; AGCO wants a JSON submission via their portal API.

Three properties are required:

1. **Source of truth is the ledger.** GGR/NGR are computed from the Phase 11 ledger (the source of financial truth), NOT from telemetry (never-truth per ADR-0104) and NOT from the read model cache (which is a projection; it can drift). The read models (ADR-0107) are an optimization for fast retrieval; the regulatory report is generated by re-querying the ledger (or by verifying the read model against the ledger and then using the read model). Either way, the ledger is the authority.

2. **Per-jurisdiction breakdown.** The regulator wants GGR/NGR per jurisdiction — not a single global number. The player's jurisdiction (sourced from Phase 14 `JurisdictionPort`) determines which bucket each bet/win falls into. A bet placed by a UK player counts toward UK GGR; a bet placed by an Ontario player counts toward Ontario GGR. Cross-jurisdiction aggregation is a defect (regulator-reportable).

3. **Per-game-class breakdown.** Regulators also want GGR/NGR per game class (slots, live_casino, crash, multiplayer). Different game classes have different tax rates in some jurisdictions; different RG implications (slots are higher-risk than live casino). The game class is sourced from the math version (Phase 16 ADR-0099).

## Decision

### GGR/NGR model

- **GGR** = `sum(bets) - sum(wins)` per (tenant, period, game_class, jurisdiction)
- **NGR** = `GGR - bonuses_awarded - bonuses_converted - payment_fees - chargeback_fees - other_deductions`

### Periods

Daily, weekly, monthly, quarterly, yearly. The period is a string (e.g., `2026-Q1`, `2026-10`, `2026-W42`). The period is computed from the event timestamp (UTC).

### Jurisdiction

Per-jurisdiction breakdown (regulator-reportable). Sourced from the player's jurisdiction via Phase 14 `JurisdictionPort`. If the player's jurisdiction cannot be determined (e.g., VPN detected, Q5-blocked `GeoPort` returns unknown), the bet is bucketed as `unknown` and an alert fires. The `unknown` bucket is a defect — every bet must have a jurisdiction before it enters the GGR/NGR read model.

### Game class

Per-game-class breakdown (slots, live_casino, crash, multiplayer). Sourced from the math version (Phase 16 ADR-0099). The game class is part of the math version's `math_config` JSONB; the GGR/NGR consumer reads it from the `game.bet.placed` event payload.

### Source of truth

Phase 11 ledger (NOT telemetry; NOT read model cache). The regulatory report is generated by:

1. Querying the GGR/NGR read model (ADR-0107) for the requested (tenant, period, game_class, jurisdiction).
2. Verifying the read model against the ledger (reconciliation job; ADR-0107).
3. If reconciliation passes: use the read model values for the report.
4. If reconciliation fails: HALT; do not generate the report until the mismatch is resolved.

This ensures the regulatory report is always sourced from ledger-reconciled data.

### Per-jurisdiction formats (Q1-blocked; stub for dev)

- **UK GC:** monthly GGR report (CSV with columns: period, game_class, ggr_gbp).
- **MGA:** quarterly GGR/NGR report (Excel workbook with tabs: summary, by_game_class, by_jurisdiction).
- **AGCO:** quarterly GGR/NGR report (JSON submission via portal API).
- **Other jurisdictions:** per local requirements (Q1-blocked for specific formats).

For Stage A, the format configuration is a JSONB field on a `JurisdictionReportConfig` model (per-tenant, per-jurisdiction). The stub returns a generic JSON format; production config (per jurisdiction) is Q1-blocked.

### Submission

- **Manual** (portal): operator downloads the report from the admin UI and uploads it to the regulator portal. The `submitted_at` + `submitted_by` fields record the manual submission.
- **API** (Q5-blocked): automated submission via regulator portal API. The API integration is a future phase (Q5-blocked for vendor selection).

### Audit

Every report generation + submission is audited (Phase 7). Event types:
- `regulatory.report.generated` (with reconciliation_passed flag)
- `regulatory.report.submitted` (with submitted_by + jurisdiction_code)

## Alternatives

- **Telemetry as source** (rejected). Telemetry is never-truth (Law 6, ADR-0104). A GGR report sourced from telemetry is regulator-reportable.
- **Read model cache as source without reconciliation** (rejected). Read models can drift. A stale read model produces an inaccurate report.
- **No regulatory reporting** (rejected). Regulator-mandated. Failure to report is a fineable offence.
- **Single global GGR/NGR number** (rejected). Regulators require per-jurisdiction breakdown.
- **No per-game-class breakdown** (rejected). Regulators require per-game-class; different tax rates; different RG implications.
- **Direct ledger query for every report** (rejected). A quarterly report over 10M events takes minutes. The read model + reconciliation pattern returns in milliseconds while preserving ledger authority.
- **Auto-submission via API** (rejected for now). Q5-blocked. Manual submission is the Stage A path; API integration is a future phase.

## Consequences

- GGR/NGR read models required (ADR-0107). Per-jurisdiction + per-game-class breakdown in the materialized views.
- `RegulatoryReport` model + RLS + audit trigger (Phase 7 pattern).
- Per-jurisdiction format configuration (`JurisdictionReportConfig`) — Q1-blocked for specific formats.
- Manual submission workflow (admin UI + audit log). API submission is Q5-blocked.
- Linter rule 145: every regulatory report generated from ledger-reconciled read models. The `reconciliation_passed` field must be True; a report with `reconciliation_passed = False` is a defect.
- Open question OQ-DATA-002: regulatory report format per jurisdiction (Q1-blocked for specific formats).
- Open question OQ-DATA-003: regulator portal API integration (Q5-blocked for vendor selection).

## Validation Plan

- **GGR formula verification test:** place 10 bets (£100 each) + 5 wins (£80 each); assert GGR = £1000 - £400 = £600.
- **NGR formula verification test:** GGR £600 - £50 bonus awarded - £20 bonus converted - £5 payment fee = £525.
- **Per-jurisdiction breakdown test:** place bets from UK + Ontario players; assert UK GGR and Ontario GGR are separate; assert no cross-jurisdiction aggregation.
- **Per-game-class breakdown test:** place slots bets + live casino bets; assert slots GGR and live_casino GGR are separate.
- **Regulatory report generation test:** generate a monthly GGR report for UK GC; assert the report payload matches the expected format (CSV columns); assert `reconciliation_passed = True`.
- **Reconciliation HALT test:** tamper with the GGR read model; attempt to generate a report; assert HALT (`reconciliation_passed = False`; report not generated).
- **Source-of-truth test:** generate a report; verify the report's GGR value matches the ledger's GGR value (not just the read model's value).
- **Linter rule 145 test:** grep for `RegulatoryReport.objects.create`; assert each call follows a reconciliation check.
