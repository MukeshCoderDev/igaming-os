# ADR-0009 — Declarative workflow engine

## Context

Customer pain (Pain-REQ-0005) demands configurable approval workflows without code. Imperative workflow code in services creates a tight coupling between workflow definition and deployment cadence. MB-REQ-0007 mandates declarative workflows.

## Decision

Adopt a declarative workflow engine: workflows are defined as versioned, immutable documents (DEC-0010) and executed by a generic engine. Workflow definitions live in a dedicated context and are independently deployable from the services that host them.

## Alternatives

Alternatives considered: (a) imperative workflow code in services — couples deployment cadence; (b) embedded BPMN engine (Camunda, Flowable) — heavyweight, Java-centric; (c) AWS Step Functions — cloud lock-in. (a) rejected for coupling; (b) rejected for stack mismatch; (c) rejected for lock-in (risk-register entry).

## Consequences

Workflow definitions become a new artifact type with its own versioning, review, and deployment pipeline. The engine is a SPOF; if it stops, no workflow progresses. Debugging declarative workflows is harder than imperative code.

## Validation Plan

Phase 8: prototype the engine with 3 reference workflows (approval, escalation, parallel branches). Phase 9: load-test the engine at 1k concurrent workflow instances. Phase 10: verify rollback semantics when a workflow version is superseded.
