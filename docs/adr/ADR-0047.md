# ADR-0047 — Player entity model + User relationship

## Context

Phase 9 introduces the Player entity — the end-user of a tenant's platform (e.g., a bank's customer). Players are distinct from Users (Phase 6): a User is an authenticated identity; a Player is the person the data belongs to. A Player may or may not be linked to a User (e.g., a prospect who hasn't registered yet). Players are tenant-scoped; multi-tenant player support is a design decision.

## Decision

Adopt a separate Player entity, optionally linked to User (Phase 6) via a nullable user_uuid FK. Tenant-scoped (RLS per DEC-0003). Multi-tenant player decision: Phase 9 supports single-tenant players only (a player belongs to one tenant); multi-tenant players are Phase 10+ (Q61). PII fields per extended PII register (email, full_name, date_of_birth, phone, address, jurisdiction). Lifecycle FSM via Phase 8 state machine base (ADR-0044). Every state change emits outbox events (ADR-0040) + audit events (Phase 7).

## Alternatives

Alternatives: (a) Player = User (no separate entity) — conflates identity with person; (b) Player as a role on User — loses prospect state; (c) multi-tenant players from day 1 — complexity before need. (a) rejected for conflation; (b) rejected for prospect loss; (c) rejected for complexity.

## Consequences

Player + User relationship requires careful sync (player.user_uuid may be NULL for prospects). Multi-tenant players (Q61) deferred. PII fields must be redacted per Phase 4 + Phase 7 redaction policies. Player deletion (right-to-erasure) cascades to consents, login history, etc.

## Validation Plan

Phase 9: Player model + migration + RLS. Phase 9: lifecycle FSM (8 states). Phase 9: tenant-scoping test (player in tenant A invisible to tenant B). Phase 10: multi-tenant player evaluation (Q61).
