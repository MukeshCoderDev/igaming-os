# ADR-0002 — Adopt hexagonal architecture (ports and adapters)

## Context

Domain logic must be testable in isolation, free of framework and infrastructure coupling. Direct dependencies on ORMs, HTTP frameworks, or message buses in domain code make tests slow and refactors risky. NFR §7.1 (testability) requires 100% of domain modules unit-testable without external dependencies.

## Decision

Adopt hexagonal architecture: domain logic interacts with the outside world only through ports (interfaces) defined in the domain layer. Adapters (database, HTTP, message bus) implement those ports and live outside the domain. No domain code imports infrastructure. Enforced structurally by MB-REQ-0005, MB-REQ-0008, MB-REQ-0009, MB-REQ-0011, MB-REQ-0026.

## Alternatives

Alternatives considered: (a) layered architecture (controller / service / repository) — permits domain logic in services that import ORM models; (b) clean architecture (Uncle Bob) — conceptually equivalent to hexagonal but with more layers; (c) naked objects — UI directly reflects domain models, too inflexible for a multi-tenant B2B platform. (a) rejected for insufficient isolation; (b) rejected for layer proliferation; (c) rejected for UX rigidity.

## Consequences

More interfaces and indirection than a layered design; learning curve for new engineers. Adapter boilerplate can be reduced but not eliminated. Risk of 'port explosion' if not disciplined.

## Validation Plan

Phase 3: static analysis rule that rejects any import of `django.db`, `rest_framework`, or `pika` from `domain/` packages. Phase 4: coverage gate — domain modules must achieve 100% boundary coverage with stub adapters. Phase 2 risk-register entry tracks the 'port explosion' risk.
