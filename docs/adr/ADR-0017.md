# ADR-0017 — Blue/green deployments per tenant

## Context

Deploying a new version to all tenants simultaneously creates blast radius risk: a regression affects everyone at once. Per-tenant rollouts reduce this risk and align with the tenant-as-aggregate-root model (DEC-0014).

## Decision

Deployments are blue/green per tenant. A new version is deployed alongside the old; tenants are migrated one at a time (canary first, then full population). Rollback is per-tenant. The deployment framework records migration state per tenant.

## Alternatives

Alternatives considered: (a) big-bang deployments — maximum blast radius; (b) canary deployments by percentage of traffic — not tenant-aligned; (c) feature-flag-gated rollouts — useful within a version but not a deployment strategy. (a) rejected for blast radius; (b) rejected for tenant alignment; (c) rejected for scope.

## Consequences

Two versions of the platform run simultaneously during rollout; database schema must be backward-compatible across one version (forward-only migrations, DEC-0019). Operational complexity: monitoring two versions, debugging cross-version issues.

## Validation Plan

Phase 3: implement; verify a single-tenant rollout end-to-end including rollback. Phase 4: load-test simultaneous two-version operation. Phase 8: verify that a schema migration is compatible with both versions.
