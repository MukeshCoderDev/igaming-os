# ADR-0034 — Service/agent identity model (shadow→live gate + typ=service JWT + endpoint separation)

## Context

Phase 6 introduces service/agent identities for non-human callers (internal services, background workers, the nine delivery agents per DEC-0022). Service identities must be distinct from human users: they authenticate with typ=service JWTs, cannot use human endpoints, and are subject to the shadow→live promotion gate from DEC-0022. Defense-in-depth: claim + endpoint + role.

## Decision

Adopt a service_identity table (UUID PK, name, tenant FK, status [shadow/live], created_at, promoted_at). Shadow services cannot mutate state (read-only). Promotion to live requires the DEC-0022 gate (runbook + 3 shadow runs + human approver + rollback). Service JWTs carry typ=service claim; human JWTs carry typ=bearer. Endpoints are marked human-only or service-only via a decorator (@human_only / @service_only). Defense-in-depth: claim check + endpoint check + role check (service role).

## Alternatives

Alternatives: (a) service accounts as regular users — no shadow→live gate; (b) no endpoint separation — relies on role check only; (c) mutual TLS only (no JWT) — no tenant context; (d) opaque service tokens (no JWT) — requires DB lookup. (a) rejected for no gate; (b) rejected for weak defense-in-depth; (c) rejected for no tenant context; (d) rejected for DB overhead.

## Consequences

Service identity lifecycle (shadow→live→deprecated) must be managed. Endpoint decorators must be maintained as new endpoints are added. The nine delivery agents (DEC-0022) each get a service identity. Shadow services that attempt mutation must be rejected with a clear error. Promotion gate is manual in Phase 6 (ops console Phase 7+).

## Validation Plan

Phase 6: service_identity table + migration. Phase 6: typ=service JWT issuance. Phase 6: @human_only / @service_only decorators. Phase 6: shadow→live gate test (shadow cannot mutate). Phase 6: agent-vs-human enforcement test. Phase 7: promotion gate automation + ops console.
