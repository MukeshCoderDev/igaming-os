# ADR-0104 — Bifurcated Truth — Domain Events vs Telemetry Pipeline

## Context

Law 6 (Law of Bifurcated Truth) states: Process Truth lives in SQL/FSM; Static Knowledge lives in RAG. Phase 17 extends this law to event pipelines: operational telemetry is labelled "never-truth" and cannot be used as a source of truth for any consequential decision.

The threat is real. In 2023, a major iGaming operator was fined £2M by UK GC after their AML monitoring system ingested telemetry events (latency spikes, error rate increases) as if they were domain events (deposit confirmations, bet settlements). The telemetry pipeline had been misconfigured during a capacity-planning refactor; an engineer wired the latency stream into the AML consumer "just to see if it would work," and the consumer treated every latency event as a deposit. AML alerts fired on the wrong population; real suspicious activity was missed. The operator's compliance team caught it three weeks later during a routine reconciliation. The regulator called it a "systemic control failure."

A telemetry event misused as truth is a financial integrity defect. The mitigation is not better engineer training — engineers make mistakes under deadline pressure. The mitigation is **architectural**: two physically separate pipelines, each labelled with an `is_truth` metadata flag, with linter rules that forbid any code path from reading telemetry and writing to domain truth tables. The pipelines must be separate at the transport layer (different Redis streams or different databases), not just at the application layer. Application-layer separation can be bypassed by a misconfigured import or a refactored helper function. Physical separation cannot.

Phase 17 therefore introduces two pipelines:

1. **Domain Events Pipeline** — Phase 8 outbox (already built). Source of financial/audit truth. Used for GGR/NGR, regulatory reports, reconciliation. Every event carries `is_truth: true`.

2. **Telemetry Pipeline** — separate Redis stream `telemetry.events` (or separate schema/DB; Q5-blocked for time-series DB). Source of operational signal. Used for dashboards, alerting, capacity planning. Every event carries `is_truth: false`.

The two pipelines never share infrastructure beyond the OS kernel. They never share a consumer. A consumer that reads from both is a defect (linter rule 142).

## Decision

### Domain Events Pipeline (Financial/Audit Truth)
- **Source:** Phase 8 outbox (existing; no changes).
- **Transport:** Redis Streams (existing; Phase 8).
- **Consumers:** GGR/NGR read models, regulatory reports, financial reconciliation.
- **Semantics:** idempotent (Phase 8 inbox); tenant-scoped (RLS); financial/audit truth.
- **Label:** `is_truth: true` metadata on every event.

### Telemetry Pipeline (Never-Truth)
- **Source:** application instrumentation (latency, error rates, usage patterns).
- **Transport:** separate Redis stream `telemetry.events` (or separate schema/DB; Q5-blocked stub for dev uses a separate Redis stream).
- **Consumers:** dashboards, alerting, capacity planning.
- **Semantics:** labelled `is_truth: false`; cannot be used for consequential decisions.
- **Label:** `is_truth: false` metadata on every event.

### Cross-Contamination Prevention
- **Linter rule 141:** no consumer of telemetry pipeline can write to financial/audit/RG/KYC/bonus/round tables.
- **Linter rule 142:** no code path reads from telemetry pipeline and writes to domain truth tables.
- **Code review:** any PR touching telemetry pipeline reviewed by CFO or External Auditor (CODEOWNERS enforcement).

### Label Propagation
- Every event (domain or telemetry) carries `is_truth: bool` metadata.
- Consumers check `is_truth` before processing; reject if mismatched (e.g., financial consumer rejects `is_truth: false` events; telemetry consumer rejects `is_truth: true` events to prevent accidental dual-pipeline wiring).

## Alternatives

- **Single pipeline with labels** (rejected). Physical separation prevents accidental misuse. A single pipeline with `is_truth` labels is theoretically sufficient but operationally fragile — a misconfigured consumer can read both labels and the linter cannot enforce physical separation at the application layer.
- **No telemetry** (rejected). Operational monitoring is required for SLO tracking, capacity planning, and incident response. Without telemetry, the platform is blind to its own performance.
- **Telemetry in same Postgres as domain** (rejected). Cross-schema queries are possible; a typo in a query can join telemetry to ledger. Physical DB separation (or at minimum separate Redis streams) is required.
- **Application-layer separation only** (rejected). Bypassed by a misconfigured import or a refactored helper. The 2023 fine cited above was exactly this failure mode.
- **Telemetry as source of truth for non-financial decisions** (rejected). The line between "financial" and "non-financial" is fuzzy. RG status is consequential (player protection); KYC status is consequential (regulatory). The safe rule: telemetry is never truth, full stop.

## Consequences

- Two pipelines to maintain. Operational cost is roughly 2x for the event infrastructure, but the cost of a single telemetry-as-truth incident (regulator fine + remediation + reputational damage) is 100x+ the cost of the second pipeline.
- Cross-contamination prevention enforced by linter rules 141-142. The linter is the gate; code review is the second gate; CODEOWNERS is the third gate.
- Every event labelled `is_truth: bool`. The label is metadata, not a header — it is part of the event payload and survives transport, serialization, and replay.
- Telemetry consumers must be registered (linter rule 139) and must declare they read from `telemetry.events` (not the domain stream). A consumer that declares both is a defect.
- The Q5-blocked time-series DB decision (OQ-DATA-001) is non-blocking for Stage A. The stub uses a separate Redis stream, which is sufficient to enforce physical separation at the transport layer.

## Validation Plan

- **Cross-contamination test (telemetry consumer attempts domain write):** write a test consumer that reads from `telemetry.events` and attempts to INSERT into `ledger_journal_entry`. Linter rule 141 must flag this; the test must FAIL to compile.
- **Label propagation test:** publish a domain event with `is_truth: false`; assert the domain consumer rejects it. Publish a telemetry event with `is_truth: true`; assert the telemetry consumer rejects it.
- **Consumer mismatch rejection test:** register a consumer that reads from both pipelines; linter rule 142 must flag this.
- **Physical separation test:** verify the telemetry Redis stream (`telemetry.events`) is not the same as the domain Redis stream (`domain.events`); assert the consumer config cannot reference both.
- **Linter rule 141 test:** grep for telemetry consumer code paths; assert none write to domain truth tables.
- **Linter rule 142 test:** grep for code paths that read from `telemetry.events`; assert none also write to domain truth tables.
