# ADR-0006 — Append-only audit log (no update/delete API)

## Context

Regulatory regimes (FATF, GDPR, SOC 2) require audit logs to be tamper-evident and retained for years. An audit log that allows updates or deletes cannot satisfy tamper-evidence requirements. Law-REQ-0010 mandates immutability; MB-REQ-0004 enforces it structurally.

## Decision

The audit service exposes only an append API. There is no update and no delete API, and no operational procedure that performs deletion. Retention enforcement (NFR §4.1) is a forward-only archival operation to write-once storage (e.g., S3 Object Lock), not a deletion. See MB-REQ-0004 and Law-REQ-0010.

## Alternatives

Alternatives considered: (a) CRUD with soft-delete — deleted rows are recoverable in principle but the API surface invites misuse; (b) append + administrative delete with two-person approval — operationally heavy and still permits tampering if approvers are compromised; (c) blockchain-style distributed log — over-engineered for a single-platform audit log. (a) and (b) rejected for tamper risk; (c) rejected for complexity.

## Consequences

Storage cost grows monotonically. Retention enforcement requires a separate archival pipeline. Query performance degrades as the log grows; partitioning and projection read models (DEC-0018) mitigate.

## Validation Plan

Phase 1: implemented as a stub contract. Phase 8: red-team test that attempts deletion via SQL, ORM, and admin shell. Phase 9: verify that retention archival to S3 Object Lock is irreversible. Phase 10: load-test append at 5k events/s sustained.
