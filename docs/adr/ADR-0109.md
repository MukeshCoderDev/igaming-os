# ADR-0109 — Risk Signal Model, Signal Type Catalog & Generation

## Context

Risk signals are the input to transaction monitoring. Misconfigured signals = missed suspicious activity = regulator fine. The 2019 Danske Bank Estonia scandal (€200B in suspicious flows through a non-resident portfolio) was fundamentally a signal-generation failure: the bank's AML system generated signals but the signals were misconfigured (threshold too high, velocity rules absent for non-resident accounts), so suspicious activity went undetected for years. The resulting fine was €1.5B+ across multiple jurisdictions.

Three properties are required for the signal model:

1. **Rule-based (explainable).** Regulators (FATF, FCA, FinCEN, BaFin, AMF) require that AML decisions be explainable. When a regulator asks "why was this transaction flagged?" the answer must be a deterministic rule ("deposit velocity > 5 in 24h, threshold per TM-rule-003"), not "the ML model scored it 0.87." ML-based signals are deferred to Phase 19+ or vendor (Q5-blocked, OQ-RISK-001). Phase 18 ships rule-based signals only.

2. **Closed enumeration of signal types.** A free-form signal_type field would allow operators to invent types ("weird_activity", "looks_fishy") that are untestable and ungovernable. A closed catalog of 12 signal types (velocity_deposit, velocity_bet, velocity_withdrawal, structural_structuring, structural_smurfing, behavioral_unusual_bet, behavioral_chip_dumping, jurisdictional_high_risk, pep_linked, sanctions_linked, device_fingerprint_anomaly, kyc_mismatch) covers the FATF-mandated categories and is testable per type.

3. **Dual generation path (scheduled + real-time).** Scheduled generation (every 5 minutes) catches patterns that require a time window (velocity, structuring). Real-time generation (on event publish via Phase 8 outbox consumer) catches high-severity single-event signals (sanctions match, PEP match) that cannot wait 5 minutes. Both paths feed the same RiskSignal table; idempotency (Phase 8 inbox pattern, extended in Phase 17 ADR-0106) prevents duplicate signals.

### SignalType catalog (closed enumeration — 12 types)

**Velocity signals (3):**
- `velocity_deposit` — deposit velocity above threshold (e.g., >5 deposits in 24h)
- `velocity_bet` — bet velocity above threshold (e.g., >100 bets in 10 minutes)
- `velocity_withdrawal` — withdrawal velocity above threshold (e.g., >3 withdrawals in 1h)

**Structural signals (2):**
- `structural_structuring` — multiple deposits just below CTR threshold (structuring; e.g., 3 × $9,500 deposits in 24h where CTR threshold is $10,000)
- `structural_smurfing` — multiple small deposits from multiple sources (smurfing; e.g., 10 deposits from 8 different payment methods in 24h)

**Behavioral signals (2):**
- `behavioral_unusual_bet` — unusual bet patterns (e.g., large bets immediately after small deposits; bet size >> deposit size)
- `behavioral_chip_dumping` — chip dumping (balance transfer to another player; detected via game-round patterns where one player loses consistently to another)

**Jurisdictional signals (1):**
- `jurisdictional_high_risk` — transactions with high-risk jurisdictions (FATF grey/black list; sourced from Phase 14 JurisdictionPort)

**Linked signals (4):**
- `pep_linked` — PEP-linked transactions (Phase 10 PEP screening match)
- `sanctions_linked` — sanctions-linked transactions (Phase 10 sanctions screening match)
- `device_fingerprint_anomaly` — device fingerprint anomalies (Phase 13 abuse detection)
- `kyc_mismatch` — bonus/activity without KYC (Phase 13 pattern; player activity level inconsistent with KYC status)

### Signal sources (domain events — Phase 8 outbox)

- Phase 11 ledger events (transaction patterns)
- Phase 12 payment events (deposit/withdrawal patterns)
- Phase 13 bonus events (abuse patterns)
- Phase 15/16 game round events (bet patterns)
- Phase 14 RG events (distress signals — feed risk scoring)
- Phase 10 KYC events (PEP/sanctions matches — real-time)

### Signal generation

- **Rule-based (deterministic, explainable)** — recommended for regulators. Every signal cites the TM rule that generated it (via `tm_rule_uuid`).
- **ML-based** — deferred to Phase 19+ or vendor (Q5-blocked; OQ-RISK-001). Not in Phase 18 scope.
- **Scheduled job** — every 5 minutes (scans recent transactions; evaluates each TM rule). Celery beat task `generate_risk_signals`.
- **Real-time** — on event publish (Phase 8 outbox consumer). Evaluates real-time rules (high-severity single-event signals: sanctions match, PEP match). Generates RiskSignal immediately.

### Severity escalation

- low: risk_score_contribution 1-10
- medium: risk_score_contribution 11-25
- high: risk_score_contribution 26-50
- critical: risk_score_contribution 51+ (auto-escalate to RiskCase per ADR-0112)

## Alternatives

- **ML-based only** (rejected). Regulator scrutiny; explainability required. The Danske Bank scandal showed that opaque ML models allow suspicious activity to go undetected because no one can explain why the model did or did not flag a transaction.
- **Manual signal generation** (rejected). Cannot scale; human reviewers miss patterns; regulator mandates automated monitoring.
- **Free-form signal_type** (rejected). Untestable; ungovernable. Operators would invent types; no consistent testing possible.
- **Scheduled only (no real-time)** (rejected). Sanctions match must trigger within seconds, not 5 minutes. FATF Rec 20 requires prompt detection.
- **Real-time only (no scheduled)** (rejected). Velocity and structuring patterns require a time window; real-time evaluation of every event against every rule is computationally infeasible.
- **Shared signal_type with Phase 10 KYC flags** (rejected). Different workflows; Phase 10 KYC flags feed into signals but are not signals themselves.

## Consequences

- 12 signal types in closed catalog. Linter rule 147 enforces the catalog.
- Rule-based generation. Every signal cites its TM rule.
- 5-minute scheduled job + real-time consumer. Both feed the same RiskSignal table.
- Idempotency: same event + same rule → single signal (Phase 17 inbox pattern).
- False positive monitoring: dashboard tracks signal dismissal rate per rule; high dismissal rate triggers rule review.
- Severity escalation: critical signals auto-escalate to RiskCase (ADR-0112).
- Linter rule 147: RiskSignal model exists with 12 signal types.
- Linter rule 148: TMRule model exists with 5 rule types.

## Validation Plan

- **Signal generation tests (each of 12 types):** for each signal type, construct a triggering scenario; assert RiskSignal generated with correct severity + evidence.
- **False positive monitoring test:** generate 100 signals; dismiss 95; assert dismissal rate dashboard shows 95%.
- **Severity escalation test:** generate a critical signal; assert auto-escalation to RiskCase.
- **Scheduled job test:** inject transactions; run scheduled job; assert signals generated.
- **Real-time consumer test:** publish a sanctions match event; assert signal generated within 1 second.
- **Idempotency test:** deliver the same event twice; assert single signal (Phase 17 inbox pattern).
- **Linter rule 147 test:** grep for RiskSignal model; assert 12 signal types in enum.
- **Linter rule 148 test:** grep for TMRule model; assert 5 rule types in enum.
