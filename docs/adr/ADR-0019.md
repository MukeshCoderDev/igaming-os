# ADR-0019 — Schema migrations forward-only

## Context

Down-migrations (rolling back a schema change) are risky in production: they can destroy data that the new schema captured. Most teams avoid them, which makes the 'rollback' path untested and therefore non-existent in practice. Blue/green deployments (DEC-0017) require forward-only migrations to maintain two-version compatibility.

## Decision

Database migrations are forward-only. A migration that needs to be reversed is reversed by a forward migration that restores the prior state. Down-migrations are forbidden in production. This forces schema changes to be additive where possible. MB-REQ-0021, MB-REQ-0022.

## Alternatives

Alternatives considered: (a) bidirectional migrations — encourages risky down-migrations; (b) no migrations (manual schema changes) — error-prone; (c) expand-contract pattern without forward-only constraint — works but easy to violate. (a) rejected for risk; (b) rejected for error-proneness; (c) rejected for enforcement gap.

## Consequences

Schema changes are slower: each change requires a forward migration, deploy, verify, then potentially a cleanup migration. Storage cost from obsolete columns/tables until cleanup migration. Developers must learn the expand-contract pattern.

## Validation Plan

Phase 3: linter rule that rejects down-migrations. Phase 3: verify a sample expand-contract migration (add column, deploy, backfill, drop old column). Phase 8: verify two-version compatibility (DEC-0017) holds across a migration.
