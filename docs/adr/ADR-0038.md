# ADR-0038 — Insert-only enforcement (trigger + GRANT + monitoring)

## Context

The audit log must be insert-only (DEC-0006). API-level enforcement (no update/delete endpoint) is insufficient: an attacker with DB access could UPDATE or DELETE directly. Enforcement must be at the database level, for all roles including the table owner. Superuser bypass is unavoidable in PostgreSQL but must be monitored.

## Decision

Adopt three-layer insert-only enforcement: (1) GRANT INSERT, SELECT only to noventra_app — no UPDATE/DELETE privilege; (2) BEFORE UPDATE OR DELETE trigger raises exception for all roles including owner (the trigger uses RAISE EXCEPTION; even the owner can't bypass a trigger); (3) RULE-based denial as defense-in-depth (CREATE RULE ... DO INSTEAD NOTHING — optional, mitigates ORM-generated UPDATEs). Superuser bypass: PostgreSQL superuser can bypass triggers; this is unavoidable but monitored via a separate audit trigger that logs any superuser DML on audit_event to a separate table (audit_superuser_action).

## Alternatives

Alternatives: (a) API-level only (no trigger) — bypassable with DB access; (b) REVOKE all from owner + GRANT to app only — owner can't manage the table; (c) event-sourcing (no update ever) — over-engineered for audit log; (d) separate append-only database — operational cost. (a) rejected for bypass; (b) rejected for management; (c) rejected for complexity; (d) rejected for cost.

## Consequences

Trigger adds ~1ms per statement (negligible). RULE-based denial can mask ORM bugs (an UPDATE that silently does nothing is confusing). Superuser monitoring adds a separate table + trigger; the monitoring itself must not be bypassable (separate schema, separate grants).

## Validation Plan

Phase 7: UPDATE/DELETE raises for all roles test (including owner). Phase 7: superuser bypass monitoring test. Phase 7: RULE-based denial test (optional). Phase 8: load-test trigger overhead at 5k inserts/s.
