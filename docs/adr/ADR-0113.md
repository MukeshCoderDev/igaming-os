# ADR-0113 — Punitive Action Approval, Dual Control & Audit

## Context

Law 14 (Law of Bounded Agents): consequential actions require human approval. Phase 18 extends this to punitive actions against players. A punitive action is any action that restricts a player's account or reverses their financial position: account freeze, account closure, bonus clawback, payment block, self-exclusion enforcement.

The threat is abuse of power. A rogue compliance officer could freeze any player's account without oversight. A compromised MLRO account could close accounts en masse. The mitigation is **dual control**: high-severity punitive actions require two different humans (requester + approver), and the system enforces that they are different people. Low-severity actions (account freeze for a clear SAR filing) may require single approval; high-severity actions (account closure, SE enforcement) require dual control.

The 2018 Wells Fargo account-closure scandal (where 2M fake accounts were created and then closed without oversight) showed what happens when punitive actions bypass approval. The fine was $3B+. The lesson: every punitive action must be traceable to named humans, and high-severity actions must have separation of duties.

## Decision

### PunitiveAction model

| `requested_by` | str | Named human (compliance officer) |
| `requested_at` | datetime | |
| `approved_by` | str | Named human (compliance officer or MLRO; must differ from requested_by for high-severity) |
| `approved_at` | datetime | |
| `executed_at` | datetime | |
| `justification` | TEXT | Required; audited |
| `reversal_uuid` | UUID FK → PunitiveAction (nullable) | If reversed, points to the reversal action |
| `created_at` | datetime | auto_now_add |

### Action types (5)

1. **account_freeze** — freeze player account (Phase 14 kill-switch pattern; synchronous; <200ms SLO). Severity: low (single approval).
2. **account_closure** — close player account permanently. Severity: high (dual control). IRREVERSIBLE.
3. **bonus_clawback** — reverse awarded bonuses (Phase 11 terminal reversal). Severity: low. Reversible.
4. **payment_block** — block deposits/withdrawals (Phase 12 integration). Severity: low. Reversible.
5. **se_block** — enforce self-exclusion (Phase 14 SE). Severity: high (dual control). IRREVERSIBLE (regulator-mandated; SE is terminal).

### Approval workflow

```
requested → approved → executed
         ↘ rejected
```

- `requested → approved`: Compliance Officer or MLRO approves. For high-severity (account_closure, se_block), `approved_by` must differ from `requested_by` (dual control).
- `requested → rejected`: Approver rejects with documented justification.
- `approved → executed`: Action executed. `executed_at` recorded. Audit event emitted (Phase 7).

### Dual control (high-severity)

- `account_closure` and `se_block` require dual control: requester != approver.
- The system enforces this at the application layer (status transition check) AND at the DB layer (CHECK constraint on high-severity actions).
- Linter rule 157: high-severity actions require dual control (requester != approver).
- Linter rule 156: no punitive action executes without recorded approval.

### Audit

Every approval + execution is audited (Phase 7). Event types:
- `punitive.action_requested` (with action_type, severity, requested_by, case_uuid)
- `punitive.action_approved` (with approved_by, justification)
- `punitive.action_rejected` (with rejected_by, justification)
- `punitive.action_executed` (with executed_at, side effects)
- `punitive.action_reversed` (with reversal_uuid, reversed_by, justification)

### Reversibility

| Action | Reversible? | Reversal mechanism |
|---|---|---|
| account_freeze | YES | Unfreeze (new PunitiveAction with action_type=account_freeze, status=executed, reversal_uuid points to original) |
| bonus_clawback | YES | Re-award via Phase 11 reversal-of-reversal (new ledger entry; not mutation of original) |
| payment_block | YES | Unblock (new PunitiveAction) |
| se_block | NO | IRREVERSIBLE (regulator-mandated; SE is terminal per Phase 14 ADR-0085) |
| account_closure | NO | IRREVERSIBLE (terminal) |

Reversal is always a NEW PunitiveAction (insert-only per Phase 7 pattern). The original action is never mutated; the reversal references it via `reversal_uuid`.

## Alternatives

- **Auto-execute punitive actions** (rejected). Law 14 mandates human approval. Auto-execution would allow a rogue or compromised account to act without oversight.
- **Single approval for all** (rejected). High-severity actions (account closure, SE enforcement) require separation of duties. Single approval is insufficient for irreversible actions.
- **No reversal** (rejected). Some actions (freeze, clawback, block) should be reversible if the appeal (ADR-0114) overturns them. Irreversible reversibility would be unjust.
- **Reversal by mutation** (rejected). Mutating the original action destroys the audit trail. Reversal must be a new action (insert-only).
- **SE enforcement reversible** (rejected). SE is regulator-mandated terminal (Phase 14 ADR-0085). Allowing reversal would violate the SE-survives-erasure principle.
- **Account closure reversible** (rejected). Terminal by definition; reversal would require recreating the account (new UUID; not the same account).
- **Dual control for all** (rejected). Overkill for low-severity actions (freeze for clear SAR). Slows operations unnecessarily.

## Consequences

- PunitiveAction model with 5-state FSM + approval workflow.
- Dual control for high-severity (account_closure, se_block): requester != approver.
- 2 irreversible actions (se_block, account_closure); 3 reversible (account_freeze, bonus_clawback, payment_block).
- Reversal = new PunitiveAction (insert-only); never mutation.
- Every action audited (Phase 7).
- Linter rule 152: PunitiveAction model exists with approval workflow.
- Linter rule 156: no punitive action executes without recorded approval.
- Linter rule 157: high-severity actions require dual control.

## Validation Plan

- **Approval test (no execution without approval):** create PunitiveAction; attempt to execute without approval; assert refusal.
- **Dual control test (high-severity requires requester != approver):** create high-severity action; same person requests + approves; assert refusal.
- **Dual control test (low-severity allows single approval):** create low-severity action; single approver; assert execution succeeds.
- **Audit test:** execute punitive action; assert audit events emitted (requested, approved, executed).
- **Reversal test (reversible actions):** execute account_freeze; reverse; assert new PunitiveAction created; assert original unchanged; assert account unfrozen.
- **Irreversibility test (se_block):** attempt to reverse se_block; assert refusal.
- **Irreversibility test (account_closure):** attempt to reverse account_closure; assert refusal.
- **Linter rule 156 test:** grep for punitive action execution code; assert each follows approval check.
- **Linter rule 157 test:** grep for high-severity action approval; assert requester != approver check.
