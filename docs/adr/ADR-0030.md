# ADR-0030 — pgbouncer compatibility (transaction-mode; SET LOCAL only)

## Context

Phase 5 introduces pgbouncer for connection pooling (R-SCL-02 risk; Q30 selection). pgbouncer in transaction-mode breaks session-level features: SET (without LOCAL), session cursors, prepared statements, and advisory locks. The Django app must use only transaction-safe patterns.

## Decision

Adopt pgbouncer in transaction-mode. Constraints: (1) SET LOCAL only (never bare SET) — the tenant middleware uses SET LOCAL app.tenant_uuid; (2) no session cursors — use server-side cursors only within a single transaction; (3) ATOMIC_REQUESTS=True or explicit atomic blocks — no implicit multi-statement transactions; (4) prepare_threshold=None on psycopg connection — disables prepared statements; (5) no LISTEN/NOTIFY (session-level). Document all constraints in docs/architecture/pgbouncer-compatibility.md. pgbouncer added to local docker-compose.yml.

## Alternatives

Alternatives: (a) pgbouncer session-mode — loses pooling benefits; (b) Pgcat — less mature; (c) Odyssey — fewer features; (d) no pooler — R-SCL-02 ceiling unmitigated. (a) rejected for pooling loss; (b) and (c) rejected for maturity/features; (d) rejected for unmitigated risk.

## Consequences

Developers must learn transaction-safe patterns. Some Django features (e.g., postgresql FTS with session-level GIN config) are unavailable. Debugging is harder (no session state). prepare_threshold=None has a small perf cost (~5%).

## Validation Plan

Phase 5: pgbouncer test passes against local compose instance (read/write/rollback/recycle). Phase 5: SET LOCAL app.tenant_uuid works under pgbouncer (test). Phase 6: load-test connection pool hit rate. Phase 8: verify audit log append works under pgbouncer.
