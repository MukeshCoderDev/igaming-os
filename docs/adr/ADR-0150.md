# ADR-0150 — Docs Portal — API Reference, Integration Guides, SDK Docs & Versioning

## Context

Partners need documentation to integrate. Without a docs portal, integration is ad-hoc and error-prone. Docs must be versioned per API version. Stripe Docs is the industry benchmark.

The 2023 Twilio developer survey found that 73% of integration failures stem from poor documentation (outdated, incomplete, or inaccurate). The lesson: docs must be generated from the API schema (OpenAPI), not hand-written; hand-written docs drift from the API. Versioning ensures partners see docs matching their API version.

## Decision

### DocsPortal

Developer-facing documentation site.

### Contents

1. **API Reference** (OpenAPI-generated from Phase 3 schema; drf-spectacular).
2. **Integration Guides:**
   - Partner onboarding (how to get partner keys; sandbox provisioning).
   - Webhook setup (how to register endpoint; verify signatures; handle retries).
   - SDK usage (how to use Player SDK; reference lobby).
   - Conformance suite (how to pass; what's tested).
3. **SDK Documentation** (Player SDK spec; methods; events; errors).
4. **Changelog** (API versioning; breaking changes; deprecation notices).
5. **Status Page** (API uptime; incident history; webhook delivery status).

### Implementation

- Static site generator (MkDocs or Docusaurus) for performance + simplicity.
- OR dynamic (Django admin + API) for personalization.
- Recommend: MkDocs (static) + dynamic elements (status page; partner-specific docs).
- Source: `docs/` directory (existing structure; Phase 2 established docs/).

### Authentication

- **Public docs** (prospects; no auth): API reference overview; integration guides summary; SDK overview.
- **Partner docs** (partner key auth): full API reference; partner-specific webhook config; SDK download; conformance results.
- **Linter rule 221:** partner-specific docs require partner key auth.

### Versioning

- Docs versioned per API version (v1, v2, etc.).
- Deprecated APIs marked; migration guides provided.
- Changelog per version.

### AI-powered search (Phase 19 RAG integration — optional)

- Partners can search docs in natural language.
- Phase 19 RAG pipeline (prefiltered by `tenant_id` = partner's tenant).
- Returns grounded answers with citations to doc chunks.
- May use Phase 19 LLM Gateway (cost tracked per partner).
- Q5-blocked for production LLM; stub for dev.

## Alternatives

- **No docs portal** (rejected). Partners cannot integrate; support burden. The Twilio survey is the canonical evidence.
- **Dynamic only** (rejected). Performance; complexity.
- **No versioning** (rejected). Breaking changes confuse partners; partners on old API version see new API docs.
- **Hand-written API reference** (rejected). Drifts from API; the Twilio survey showed 73% of failures from poor docs.
- **No partner auth** (rejected). Partner-specific docs (webhook config; conformance results) must be authenticated.
- **No AI search** (acceptable for Stage A). Q5-blocked; optional; can add later.

## Consequences

- DocsPortal (MkDocs + dynamic elements).
- Partner key auth for partner docs (linter rule 221).
- Versioned per API version.
- Optional AI search (Phase 19; Q5-blocked).
- Open question OQ-DEV-005: docs portal AI search (Q5-blocked).

## Validation Plan

- **Docs generation test (OpenAPI → API reference):** generate docs from OpenAPI schema; assert API reference matches schema.
- **Partner auth test (linter rule 221):** attempt to access partner docs without partner key; assert 401.
- **Versioning test:** docs for v1 vs v2; assert deprecated APIs marked; assert migration guide present.
- **AI search test (Phase 19 integration; Q5-blocked stub):** search docs in natural language; assert grounded answer with citations (stub for dev).

## Decision statement (one line)

DEC-0151 → Docs Portal (MkDocs + OpenAPI + partner auth + versioning; optional AI search; linter rule 221). Owner: Product Owner + API Owner. Status: PROPOSED.
