# ADR-0120 — TruthConsistencyValidator (Law 13; SQL Fact Checking; Hard Fail)

## Context

Law 13 (Law of Truth Consistency): A TruthConsistencyValidator checks every RAG answer against SQL facts. Contradiction = hard fail, safe fallback, incident signal. This is the financial integrity guard for AI responses.

The threat is AI-generated misinformation about financial facts. A player asks "what is my current balance?" and the RAG retrieves an outdated support article that says "your balance is shown on the dashboard." The LLM composes: "Your current balance is $500." But the actual ledger balance is $750. The player acts on the wrong number (places a $600 bet expecting it to be declined; it's accepted; the player is now overdrawn). This is a financial integrity defect caused by AI misinformation.

The 2024 Air Canada chatbot incident (cited in ADR-0116) is the canonical example: the chatbot gave incorrect bereavement fare information, the customer acted on it, and the airline was held liable. The TruthConsistencyValidator is the architectural mitigation: every AI claim that references a financial/regulatory fact is checked against the SQL source of truth (Phase 11 ledger, Phase 12 payments, Phase 10 KYC, Phase 14 RG, Phase 13 bonuses, Phase 15-16 rounds). If the claim contradicts the SQL fact, the response is hard-failed and the player sees a safe fallback.

## Decision

### TruthConsistencyValidator (Step 7 of RAG pipeline)

**1. Claim extraction:** Parse LLM output for claims that reference facts.
- Fact types: balance, payment status, KYC status, RG status, bonus state, round result.
- Regex + LLM-based extraction (LLM extracts claims; regex classifies fact-referencing claims).

**2. Fact identification:** Classify each fact-referencing claim by fact type.
- "Your balance is $500" → fact_type = balance, asserted_value = $500.
- "Your KYC is verified" → fact_type = kyc_status, asserted_value = verified.
- "Your last deposit was $100" → fact_type = payment, asserted_value = $100.

**3. SQL query:** Query the source of truth for the actual fact.
- Balance → Phase 11 ledger (BalanceService).
- Payment status → Phase 12 payments (PaymentOrder.status).
- KYC status → Phase 10 KYC (KYCCase.status).
- RG status → Phase 14 protection (SelfExclusion, PlayerLimit).
- Bonus state → Phase 13 bonuses (BonusAward.status).
- Round result → Phase 15-16 games (GameRound.outcome).

**4. Comparison:** Compare claim's asserted value against SQL fact.
- Numeric: exact match (within tolerance for currency: ±0.01).
- Enum: exact match (case-insensitive).
- String: exact match or fuzzy match (Levenshtein distance ≤2).

**5. Verdict:**
- **CONSISTENT:** claim matches SQL fact → proceed (citation attached).
- **CONTRADICTION:** claim contradicts SQL fact → hard fail; safe fallback; incident signal.
- **UNVERIFIABLE:** claim references fact that cannot be verified (e.g., historical fact no longer in active window) → soft warning; proceed with caveat ("This information may be outdated; please verify on your dashboard.").

### Safe fallback

"I cannot confirm this information; please contact support or check your dashboard."

The fallback is deterministic (no LLM call); it is the same for all contradictions. The player never sees the contradictory claim.

### Incident signal

- Contradiction logged (Phase 7 audit event `ai.contradiction_detected` with claim, asserted_value, sql_fact, fact_type).
- Alert security owner (Slack `#security-alerts`).
- Pattern analysis: repeated contradictions may indicate prompt injection or RAG poisoning (someone injected chunks that contradict the ledger).

### Implementation

- Pure function; no side effects; deterministic.
- Input: LLM claims + SQL facts (queried in parallel).
- Output: verdict per claim + overall verdict (hard fail if any CONTRADICTION).
- Latency target: <200ms p99 (parallel SQL queries).

## Alternatives

- **No validation** (rejected). Law 13 violation; financial integrity at risk. The Air Canada incident is the canonical example.
- **Soft warnings only** (rejected). Contradiction must hard-fail; a soft warning allows the player to see the wrong number.
- **LLM-based validation (LLM checks its own claims)** (rejected). LLM checking LLM is circular; the same hallucination that produced the claim may produce a false "consistent" verdict.
- **Validation after response sent** (rejected). Player sees the wrong number; validation after-the-fact does not prevent the harm.
- **Validation only for balance** (rejected). All 6 fact types are consequential (payment status, KYC status, RG status, bonus state, round result). Validating only balance leaves the other 5 unprotected.
- **Tolerance for numeric mismatch (±$1)** (rejected). Even a $1 mismatch can cause overdraft; tolerance must be ±$0.01 (currency rounding only).

## Consequences

- TruthConsistencyValidator required (Step 7 of RAG pipeline).
- Hard fail on contradiction (no soft pass).
- Incident signal on contradiction (alert + pattern analysis).
- Safe fallback (deterministic; no LLM).
- 6 fact types validated (balance, payment, KYC, RG, bonus, round).
- Pure function; deterministic; <200ms p99.
- Linter rule 172: TruthConsistencyValidator runs on every fact-referencing claim.
- Linter rule 173: contradiction = hard fail (no soft-pass for contradictions).
- Telemetry is never-truth (Law 6); SQL facts only (Phase 17 bifurcated truth).

## Validation Plan

- **Consistency test:** claim matches SQL fact → CONSISTENT → proceed with citation.
- **Contradiction test:** claim contradicts SQL fact → CONTRADICTION → hard fail → safe fallback.
- **Incident signal test:** contradiction → audit event `ai.contradiction_detected` + Slack alert.
- **Safe fallback test:** contradiction → player sees "I cannot confirm this information; please contact support or check your dashboard."
- **Fact type coverage test:** all 6 fact types (balance, payment, KYC, RG, bonus, round) validated.
- **Unverifiable test:** historical fact → UNVERIFIABLE → soft warning with caveat.
- **Numeric tolerance test:** balance claim ±$0.01 → CONSISTENT; balance claim ±$0.02 → CONTRADICTION.
- **Latency test:** 10 claims validated in parallel → <200ms p99.
- **Linter rule 172 test:** grep for RAG response code; assert each calls TruthConsistencyValidator on fact-referencing claims.
- **Linter rule 173 test:** grep for contradiction handling; assert hard fail (no soft pass).
