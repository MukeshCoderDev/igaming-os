# ADR-0099 — Math Version Model — Immutability + Hash Verification

## Context

Game math config (RTP, volatility, hit frequency, paytable) is regulator-sensitive. Every change requires recertification by an approved lab (GLI, BMM, iTechLabs). If math config could be mutated in place, an operator could ship a "patched" math version to production that has never been certified — a regulator-reportable event in every jurisdiction we operate in (UK GC, MGA, state gaming commissions, Ontario AGCO, etc.).

Two distinct regulator mandates drive this ADR:

1. **Immutability after certification.** Once a math version is certified by a lab, its configuration cannot be modified — even by an admin with full DB access. The certified version is what the lab tested; anything else is uncertified. The model must enforce this at the data layer (insert-only trigger per Phase 7 pattern), not at the application layer (which can be bypassed by a privileged user with raw SQL access).

2. **Tamper detection at game launch.** When a player initiates a round, the platform must verify that the math version loaded into memory matches the certified math version byte-for-byte. If a privileged user could modify the math config row in the DB and then trigger a round, the round would use uncertified math. To detect this, every math version carries a `math_config_hash` — SHA-256 over canonical JSON of the config — and the round-initiation code verifies the hash before accepting any bet.

## Decision

`MathVersion` model:

| Field | Type | Notes |
|---|---|---|
| `version_uuid` | UUID PK | Per-version identifier |
| `tenant_uuid` | UUID | Tenant scope (RLS per Phase 5) |
| `game_id` | str | Game identifier (e.g., `slots_starburst`) |
| `version` | str | Semver-style (e.g., `1.0.0`, `1.0.1-rc1`) |
| `rtp_percentage` | decimal | 4 decimal places (e.g., 96.1234) |
| `volatility` | enum | low, medium, high |
| `hit_frequency` | decimal | 0.0–1.0 |
| `paytable` | JSONB | Full paytable structure |
| `math_config` | JSONB | Full math config (RNG seed handling, reel strips, etc.) |
| `math_config_hash` | char(64) | SHA-256 hex over canonical JSON of `math_config` |
| `status` | enum | draft, certified, published, superseded, revoked |
| `certified_at` | datetime | Lab certification timestamp |
| `certified_by` | str | Lab name (e.g., "GLI") |
| `cert_evidence_id` | UUID FK → CertificationEvidence | Phase 16 ADR-0102 |
| `created_at` | datetime | auto_now_add |
| `superseded_by` | UUID FK → MathVersion | For supersession chain |

**Immutability:** The math_version table has an insert-only trigger (per Phase 7 audit pattern). UPDATE and DELETE are forbidden at the DB level. Supersession is recorded as a new row (status=superseded on the old row, status=published on the new row, linked by `superseded_by`).

**Hash verification at launch:** When a round is initiated, the round service loads the active math version, recomputes `SHA-256(canonical_json(math_config))`, and compares to the stored `math_config_hash`. Mismatch → round initiation refuses (no bet accepted). Match → round records the `math_version_uuid` and `math_config_hash` on the round row; both are part of the round hash (Phase 16 ADR-0101).

**Canonical JSON:** The hash is computed over canonical JSON (sorted keys, no whitespace, no NaN, no Unicode escapes for ASCII). A reference implementation is provided in `noventra.modules.games.domain.math_version.canonical_json()`.

## Alternatives

- **Mutable math versions with audit log** (rejected). Audit log shows the change but the round may have used the modified config before the audit was reviewed. Regulator-reportable.
- **Application-layer immutability** (rejected). Bypassed by raw SQL access. Not regulator-defensible.
- **No hash verification** (rejected). Trusts the DB row at round initiation. Vulnerable to privileged-user tampering.
- **Hash over the entire row** (rejected). Includes timestamp and status fields that legitimately change. Hash must be over the math config only.
- **MD5 or SHA-1** (rejected). Cryptographically broken. SHA-256 minimum.

## Consequences

- Math version rows are permanent. Retention is 7+ years per regulator (Q1-blocked for specific periods; default 7 years).
- Every math change creates a NEW row. The old row is `superseded`, never deleted. This means the math_version table grows monotonically — acceptable; math versions are infrequent (per release, not per round).
- Round-initiation latency increases by ~1ms (SHA-256 of a few KB). Within the kill switch SLO budget.
- The `canonical_json()` function must be stable across Python versions. We pin to `json.dumps(obj, sort_keys=True, separators=(',', ':'))`.
- Linter rule 121 forbids any code path that mutates a `MathVersion` row outside the supersession flow.
- Linter rule 122 requires every round-initiation code path to verify `math_config_hash` before accepting a bet.

## Validation Plan

- Immutability test: attempt `UPDATE math_version SET rtp_percentage = 99.0` → DB raises.
- Immutability test: attempt `DELETE FROM math_version WHERE ...` → DB raises.
- Hash verification test: tamper with `math_config` JSON; recompute hash; mismatch detected at round initiation.
- Supersession test: create v1, certify, publish; create v2, certify, publish; assert v1.status = superseded, v1.superseded_by = v2.version_uuid, v2.status = published.
- Round-launch test: init round; assert round row records both `math_version_uuid` and `math_config_hash`.
- Linter rule 121: grep for UPDATE/DELETE on math_version table; assert zero matches outside the supersession service.
- Linter rule 122: grep for round-initiation code paths; assert each calls `verify_math_config_hash()`.
