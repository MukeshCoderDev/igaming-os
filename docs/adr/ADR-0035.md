# ADR-0035 — Hash-chain architecture (SHA-256, hybrid scope, Merkle-style payload)

## Context

The audit log must be tamper-evident: any modification of a past entry must be detectable on read. Append-only (DEC-0006) prevents API-level modification but not direct DB access. A hash chain makes any past modification detectable. The chain must work under pgbouncer transaction-mode (Phase 5 ADR-0030) and support redaction without breaking the chain (Phase 7 ADR-0037).

## Decision

Adopt SHA-256 hash chaining. Chain scope = hybrid: per-tenant chains for tenant-scoped events + a global chain for system events (auth.*, security.*). Payload hashing = Merkle-style: each payload field is hashed individually, and the field hashes are combined into a Merkle root; this allows redacting individual fields without breaking the chain (only the redacted field's hash is preserved). Trigger = BEFORE INSERT on audit_event: computes hash = SHA256(prev_hash || merkle_root || event_meta). Chain head stored in audit_chain_head (singleton per scope). Concurrency: use INSERT ... RETURNING with a table-level lock on audit_chain_head (pgbouncer-compatible; short critical section).

## Alternatives

Alternatives: (a) single global chain — bottleneck; (b) per-event chains (no chain) — no tamper-evidence; (c) signed entries only (no chain) — doesn't detect insertion/deletion; (d) external transparency log — over-engineered; (e) bare SHA-256 (not Merkle) — can't redact without breaking chain. (a) rejected for bottleneck; (b) rejected for no tamper-evidence; (c) rejected for insertion blindness; (d) rejected for complexity; (e) rejected for redaction incompatibility.

## Consequences

SHA-256 is current standard; migration plan if compromised: add a new chain with SHA-3 (or whatever is current) and cross-sign the old chain head into the new chain. Append is serialized per scope (table-level lock on chain head); throughput bounded by hash computation (~50k/s, well above NFR §3.3 target of 5k/s). Verification is O(N) per scope; scheduled verifier must partition.

## Validation Plan

Phase 7: chain verifier passes in CI (rule 39). Phase 7: concurrent insert test (10 parallel appends; all hashes valid). Phase 7: break detection test (modify a past entry → verifier detects). Phase 8: load-test at 5k events/s sustained. Phase 24: external chain-head publication (transparency log).
