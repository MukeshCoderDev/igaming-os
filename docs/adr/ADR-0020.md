# ADR-0020 — Telemetry via OpenTelemetry

## Context

Vendor-locked telemetry (Datadog, New Relic, etc.) creates switching costs and complicates multi-vendor observability stacks. A standard instrumentation layer preserves optionality. MB-REQ-0020 mandates boundary telemetry.

## Decision

Adopt OpenTelemetry as the sole telemetry library. Spans, metrics, and logs are emitted via OTel. The exporter is configurable per environment (Jaeger locally, vendor in production). All boundary operations emit spans (MB-REQ-0020).

## Alternatives

Alternatives considered: (a) Datadog-only — vendor lock-in; (b) Prometheus + Jaeger separately — works but no unified instrumentation; (c) custom telemetry library — maintenance burden. (a) rejected for lock-in; (b) rejected for fragmentation; (c) rejected for burden.

## Consequences

OTel SDK is still maturing; some language ecosystems have gaps. Performance overhead (~1–3% CPU) is measurable. Sampling strategy must be tuned to balance cost and observability.

## Validation Plan

Phase 2: stub contract. Phase 3: implement; verify spans appear in Jaeger. Phase 4: load-test OTel overhead at 10k req/s. Phase 8: verify 100% boundary coverage (NFR §5.1).
