# ADR-0101 — Game Round Lifecycle — Math Version Lock + RNG Seed Lock + Round Hash

## Context

Phase 15 (ADR-0092) defined the GameRound FSM (OPEN → CLOSED → SETTLED/VOIDED/CANCELLED). Phase 16 extends the round model with three regulator-mandated properties:

1. **Math version locked at round initiation.** Once a round starts, the math version cannot change mid-round. Without this lock, a privileged operator could swap math config between bet placement and outcome calculation, producing uncertified outcomes. The round row must record `math_version_uuid` and `math_config_hash` at initiation; the outcome calculation must verify both before producing a result.

2. **RNG seed locked at round initiation.** The seed for the round is generated (or injected in sandbox) at initiation and recorded on the round row. Without this lock, an operator could regenerate seeds until a favorable outcome is produced ("seed farming"). The seed is part of the round hash, so any post-initiation change is detected.

3. **Round hash for tamper-evidence.** The round carries a SHA-256 hash over (math_version_hash, rng_seed, bet_config, outcome). This hash is computed at settlement and verified at every downstream read (audit, dispute evidence, regulator inquiry). Any tampering with any of the four inputs is detected.

These three properties together close the audit chain: the math is certified (Phase 16 ADR-0099), the RNG is auditable (Phase 16 ADR-0100), and the round is tamper-evident (this ADR). A regulator inquiry can reconstruct any round from (math_version, rng_seed, bet_config) and verify the outcome matches the recorded hash.

## Decision

`GameRound` (extends Phase 15 model) gains the following fields:

| Field | Type | Notes |
|---|---|---|
| `math_version_uuid` | UUID FK → MathVersion | Locked at initiation; immutable |
| `math_config_hash` | char(64) | Snapshot of MathVersion.math_config_hash at initiation |
| `rng_seed_hex` | char(64) | 256-bit hex seed; locked at initiation |
| `bet_config` | JSONB | Final bet configuration at CLOSED transition |
| `outcome` | JSONB | Outcome at SETTLED transition |
| `round_hash` | char(64) | SHA-256 hex over canonical JSON of (math_version_hash, rng_seed, bet_config, outcome) |

**Lifecycle:**

1. **Initiation (OPEN state):** Round service generates (or accepts) an RNG seed via `RngPort.generate_seed()`. Round service loads the active math version, verifies `math_config_hash` (per ADR-0099), and records `math_version_uuid` + `math_config_hash` + `rng_seed_hex` on the round row. Round transitions to OPEN. Bets accepted.

2. **Bet acceptance (OPEN state):** Each bet is recorded. Bets do not affect the seed or math version. The `bet_config` field is updated as bets arrive (it is finalized at CLOSED transition).

3. **Close (CLOSED state):** Round transitions OPEN → CLOSED. `bet_config` is frozen (canonical JSON of all bets). `closed_at` is recorded. No more bets accepted.

4. **Settle (SETTLED state):** Round service computes the outcome deterministically from `(math_version, rng_seed, bet_config)` using `RngPort.next_int()`/`next_float()` with the recorded seed. Outcome is recorded. `round_hash` is computed as `SHA-256(canonical_json({math_version_hash, rng_seed, bet_config, outcome}))` and recorded.

5. **Void (VOIDED state):** Per Phase 15 ADR-0093 — round is voided, bets returned via RealRoundVoidingAdapter. `round_hash` is still computed (with outcome = null) for audit completeness.

**Hash verification at downstream reads:**
- Audit service (Phase 7) recomputes `round_hash` on every read; mismatch → audit failure.
- Dispute evidence pack (Phase 12 ADR-0076) includes `round_hash` so the lab can verify.
- Regulator inquiry API returns `round_hash` so the regulator can independently verify.

## Alternatives

- **No math version lock** (rejected). Mid-round math swap possible; uncertified outcomes.
- **No RNG seed lock** (rejected). Seed farming possible; favorable outcomes can be regenerated.
- **No round hash** (rejected). Tampering undetected; regulator inquiry cannot verify.
- **Hash over round row only** (rejected). Round row includes timestamps that change; hash must be over the four immutable inputs.
- **MD5 hash** (rejected). Cryptographically broken.
- **Compute round hash at initiation** (rejected). Outcome not yet known; hash would be incomplete.

## Consequences

- Round row gains 6 new fields. Migration adds columns + indices on `math_version_uuid`, `rng_seed_hex`.
- Round-initiation latency increases by ~1ms (math version load + hash verification). Within kill switch SLO budget.
- Round-settlement latency increases by ~1ms (outcome calculation + hash computation). Within SLO.
- Every downstream read of a round recomputes the hash. This is a CPU cost on audit reads but is regulator-defensible.
- Linter rule 125 forbids any code path that mutates `math_version_uuid`, `math_config_hash`, or `rng_seed_hex` after round initiation.
- Linter rule 126 requires every round-settlement code path to compute `round_hash` and record it.
- Linter rule 127 requires every audit read of a round to verify `round_hash`.

## Validation Plan

- Math version lock test: attempt to mutate `math_version_uuid` after round initiation → DB raises.
- RNG seed lock test: attempt to mutate `rng_seed_hex` after round initiation → DB raises.
- Round hash test: settle a round; recompute hash from (math_version_hash, rng_seed, bet_config, outcome); assert match.
- Tamper detection test: modify `outcome` JSON after settlement; recompute hash; assert mismatch.
- Determinism test: replay (math_version, rng_seed, bet_config) → assert identical outcome across 100 runs.
- Linter rule 125: grep for UPDATE on `math_version_uuid`/`math_config_hash`/`rng_seed_hex` outside initiation; assert zero.
- Linter rule 126: grep for SETTLED transition code; assert each computes `round_hash`.
- Linter rule 127: grep for audit read of round; assert each verifies `round_hash`.
