# ADR-0147 — Partner Key Model — Prefixed, Scoped, Rotatable & Hash Storage

## Context

Phase 12 established key separation (`sk_test_` vs `sk_live_`) for PSP keys (ADR-0074). Phase 24 extends to partner keys. Blueprint §12 threat: "sandbox↔prod key confusion" — keys must be prefixed to prevent cross-environment use. Partner keys are service identities (Phase 6) with scoped permissions. Rotation supports breach response.

The 2023 Slack API key incident ($4M in fraudulent charges) illustrated the cost of un-prefixed keys: a developer accidentally used a production key in a test script; the script ran in a loop; $4M in charges accrued overnight before anyone noticed. If the key had been prefixed (`sk_live_`), the developer would have seen the prefix and known to use a test key. The lesson: keys must be prefixed, and the prefix must be validated against the endpoint environment.

The 2022 CircleCI breach illustrated the cost of plaintext key storage: attackers exfiltrated plaintext API keys from CircleCI's database; customers' production systems were compromised within hours. The lesson: keys must be stored as hashes (SHA-256); plaintext shown only once at creation.

## Decision

### PartnerKey model

| Field | Type | Notes |
|---|---|---|
| `key_uuid` | UUID PK | |
| `tenant_uuid` | UUID | Tenant scope (RLS per Phase 5) |
| `partner_id` | UUID FK → Phase 23 Contract | Partner = operator contract |
| `key_prefix` | enum | `sk_test_`, `sk_live_` |
| `key_hash` | char(64) | SHA-256; never store plaintext |
| `scope` | JSONB | Permissions: `read_players`, `write_webhooks`, `read_ledger`, `launch_games`, etc. |
| `status` | enum | active, revoked, rotated |
| `created_at` | datetime | auto_now_add |
| `revoked_at` | datetime (nullable) | |
| `rotated_from` | UUID FK → PartnerKey (nullable) | Links new key to old on rotation |
| `last_used_at` | datetime (nullable) | Updated on every API call |
| `created_by` | str | Named human |

### Prefixed

- `sk_test_` prefix for sandbox keys.
- `sk_live_` prefix for production keys.
- **Linter rule 219:** key prefix validated against endpoint environment (sandbox key on prod → 401; prod key on sandbox → 401).

### Scoped

- Permissions defined per partner contract (Phase 23 Contract.scope).
- Examples: `read_players` (player lookup), `write_webhooks` (register webhook endpoint), `read_ledger` (balance query), `launch_games` (game session).
- Scope checked on every API call.
- **Linter rule 220:** every partner API call checks scope.

### Rotatable

- Partners can rotate keys via developer portal.
- Old key `status=revoked`; new key `status=active`; `rotated_from` links new to old.
- Rotation audited (Phase 7).
- Supports breach response (compromised key → rotate → old key revoked).

### Hash storage

- Key shown ONCE at creation (full key returned to partner; never retrievable again).
- Only SHA-256 hash stored (`PartnerKey.key_hash`).
- Key validation: hash comparison on every API call.
- **Linter rule 216:** no plaintext partner keys in code/logs (extends Phase 4 secret scanning).

### Key delivery

- Created via developer portal (partner authenticated).
- Full key returned once (displayed; partner must store securely).
- If lost: partner must rotate (old key revoked; new key issued).

### Key validation flow

1. Partner API call with `Authorization: Bearer sk_live_...`
2. Extract key; hash it (SHA-256).
3. Lookup PartnerKey by `key_hash`.
4. Verify `status=active`.
5. Verify `key_prefix` matches endpoint environment (sandbox vs prod) — linter rule 219.
6. Verify `scope` includes requested action — linter rule 220.
7. Verify rate limit (per partner; per key).
8. Update `last_used_at`.
9. Generate receipt ID (Law 17; linter rule 225).
10. Proceed or deny (401/403).

## Alternatives

- **Plaintext key storage** (rejected). Security risk; breach exposes all keys. The CircleCI breach is the canonical example.
- **Single environment keys (no prefix)** (rejected). Blueprint §12 threat; sandbox/prod confusion. The Slack incident is the canonical example.
- **Unscoped keys** (rejected). Partner could access unintended data; over-privileged.
- **No rotation** (rejected). Compromised keys cannot be revoked; breach response impossible.
- **Key shown multiple times** (rejected). If the key is retrievable, it's stored plaintext; security risk.
- **No last_used_at tracking** (rejected). Cannot detect stale keys; cannot identify unused keys for revocation.

## Consequences

- PartnerKey model with prefix + scope + rotation + hash storage.
- Linter rules 216 (no plaintext), 219 (prefix validation), 220 (scope check), 225 (receipt ID).
- Key shown once at creation; hash stored.
- Rotation audited (Phase 7).
- Blueprint §12 sandbox↔prod confusion threat mitigated.
- Open question OQ-DEV-001: partner key scope catalog (closed? OPEN).

## Validation Plan

- **Key creation test (prefix + hash):** create `sk_test_` key; assert `key_hash` is SHA-256; assert full key returned once.
- **Scope check test:** call API with key missing required scope; assert 403.
- **Rotation test:** rotate key; assert old key `status=revoked`; new key `status=active`; `rotated_from` links.
- **Sandbox/prod rejection test (linter rule 219):** `sk_test_` key on prod endpoint → 401; `sk_live_` key on sandbox endpoint → 401.
- **Hash storage test (linter rule 216):** grep for plaintext partner keys in code/logs; assert zero matches.
- **Key validation flow test:** full 10-step flow; assert each step enforced.
- **Receipt ID generation test (linter rule 225):** every partner API call generates receipt ID (Law 17).
