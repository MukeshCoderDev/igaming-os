# ADR-0151 — Player SDK, Reference Lobby & Conformance Suite (Production-Key Gate)

## Context

Blueprint §21: "Build second: Engagement & Developer Platform (The B2B Wedge)." Blueprint ADR-0020: Player SDK Conformance Gate. The acceptance criterion is unique: non-conforming frontend cannot obtain prod keys. This is a regulator-defensible quality bar.

The 2022 FanDuel API integration failure ($2M in lost deposits over 48 hours) illustrated the cost of no conformance gate: an operator's frontend had a bug in the deposit flow (wrong parameter name); deposits failed silently (no error displayed to player); players abandoned; $2M in lost revenue. The operator had not tested their frontend against the platform's API before deploying to production. The lesson: a conformance suite that verifies the frontend works correctly BEFORE production keys are issued prevents broken integrations from reaching production.

Blueprint ADR-0020 (seeded in Phase 2) specified the conformance gate. Phase 24 implements it. This is long-arc governance: Phase 2 ADR stub → Phase 24 implementation — 22 phases from design to implementation.

## Decision

Three artifacts:

### 1. Player SDK Spec

Documented specification for how third-party frontends (operator lobbies) integrate with Noventra.

Covers:
- Authentication (JWT from Phase 6; partner key from Phase 24).
- Game launch (Phase 15 game session creation; provider callback handling).
- Wallet display (Phase 11 balance query; authorization-read rule).
- Bonus display (Phase 13 bonus award; wagering progress).
- RG controls (Phase 14 reality checks; self-exclusion; limits).
- Payment flows (Phase 12 hosted fields; deposit/withdrawal).
- Real-time updates (Phase 14 WebSocket; game state; kill-switch).
- Error handling (Phase 4 error format; retry; idempotency).

Versioned (SDK version per API version). Published to docs portal.

### 2. Reference Lobby

Open-source reference implementation of the Player SDK.
- Demonstrates correct integration patterns.
- Partners can fork and customize; or build their own conforming to spec.
- Test bed for conformance suite.
- Published to GitHub (or equivalent).
- Licensed permissively (MIT or Apache 2.0) to encourage adoption.

### 3. Conformance Suite (Production-Key Gate)

Automated test suite that verifies a partner's frontend conforms to Player SDK spec.

**Tests (9 categories):**
1. Auth flow (login; token refresh; logout).
2. Game launch (session creation; provider callback; round result).
3. Wallet display (balance query; authorization-read; real-time update).
4. Bonus display (award; wagering progress; conversion).
5. RG controls (reality check trigger; self-exclusion; limit enforcement).
6. Payment flows (deposit hosted fields; withdrawal; payment status).
7. Error handling (error format; retry; idempotency).
8. Rate limit handling (429; backoff).
9. WebSocket integration (connection; message; kill-switch sever).

**Production-key gate:**
- Partner must pass conformance suite to obtain production keys (`sk_live_`).
- If non-conforming: production keys denied; partner must fix and re-test.
- Conformance result: pass/fail per test; overall pass required.
- Conformance run: automated; triggered by partner via developer portal.
- Conformance result stored; audited (Phase 7).
- **Linter rule 218:** no production PartnerKey with `status=active` without conformance pass.

**ConformanceResult model:**

**Blueprint ADR-0020 closure:** ADR-0020 (Player SDK Conformance Gate) was seeded in Phase 2. Phase 24 implements it. Long-arc governance: Phase 2 ADR stub → Phase 24 implementation.

## Alternatives

- **No conformance gate** (rejected). Broken integrations reach production; regulator risk. The FanDuel incident is the canonical example.
- **Manual conformance review** (rejected). Slow; subjective; doesn't scale.
- **Closed-source SDK** (rejected). Adoption barrier; partners want reference implementation.
- **No reference lobby** (rejected). Partners have no example to follow; integration from scratch is error-prone.
- **Conformance suite without production-key gate** (rejected). Partners can skip conformance; broken integrations reach production.
- **Conformance suite not automated** (rejected). Manual runs are slow; not reproducible.

## Consequences

- Player SDK Spec + Reference Lobby + Conformance Suite.
- Production-key gate (linter rule 218).
- ADR-0020 closure (Phase 2 → Phase 24; 22-phase long-arc).
- Open-source reference lobby (MIT or Apache 2.0; OQ-DEV-003).
- ConformanceResult model (audited; Phase 7).
- Open question OQ-DEV-003: reference lobby license (OPEN).
- Open question OQ-DEV-004: conformance suite hosting (OPEN).

## Validation Plan

- **Conformance suite test (each of 9 categories):** for each category, run conformance; assert pass/fail correct.
- **Production-key gate test (non-conforming → denied):** partner fails conformance; attempt to obtain `sk_live_`; assert denied with `E_CONFORMANCE_NOT_PASSED`.
- **Production-key gate test (conforming → issued):** partner passes conformance; obtain `sk_live_`; assert issued.
- **Reference lobby fork test:** fork reference lobby; customize; run conformance; assert passes.
- **SDK versioning test:** SDK v1 vs v2; assert versioned docs; assert breaking changes marked.
- **ADR-0020 closure verification:** verify ADR-0020 status transition from PROPOSED to ACCEPTED; verify Phase 24 implements the conformance gate specified in ADR-0020.
- **Linter rule 218 test:** grep for production PartnerKey creation; assert all require conformance pass.
