# ADR-0152 — Validation Suite — Security, Concurrency, Chaos & Load

## Context

Phase 25 is the final validation before launch. Every prior phase (1-24) converges here. Without comprehensive validation suites, the system may fail in production — financial integrity defects, security vulnerabilities, performance bottlenecks, or chaos failures. Blueprint §14 Stages 26-27 specify security/concurrency/chaos/load suites. Errata E5 restored the capacity table.

The 2019 Knight Capital failure ($440M in 45 minutes) is the canonical example of insufficient validation: the trading firm deployed untested code to production; a flag mismatch caused the system to buy high and sell low at extreme volume; $440M lost before anyone could stop it. The lesson: every financial system must be validated under concurrency, chaos, and load before launch — not after.

Phase 25's four validation suites are the architectural mitigation: security (penetration + PCI + AI Boundary + tipping-off + injection), concurrency (6 financial invariants under load), chaos (8 failure injection scenarios), load (capacity table + SLOs). All four must pass for GO.

## Decision

### 1. Security Suite

- OWASP ASVS L2 verification.
- 19+ penetration scenarios (from Phase 1-10 deep audit).
- Cross-tenant leak negative test suite (Salesforce-style).
- SAR tipping-off grep (against REAL code — finally non-vacuous after 15 phases of UNVERIFIED).
- PCI SAQ-A boundary verification (no PAN anywhere in code/DB/logs).
- AI Boundary enforcement (AI never writes domain truth — linter rule 175 against real code).
- Injection suite (Phase 19 — 5 types: prompt injection, jailbreak, RAG poisoning, citation hallucination, truth contradiction; all rejected; 0% success rate).

### 2. Concurrency Suite

**Phase 11:** 6 concurrency scenarios (concurrent debits; concurrent reversals; concurrent idempotency; balance read during write; cross-account transfer; concurrent debit+credit).
**Phase 12:** payment concurrency (concurrent deposits; PSP retry idempotency).
**Phase 13:** bonus concurrency (concurrent claims; wagering progress).
**Phase 14:** kill-switch concurrency (concurrent SE + fan-out; <200ms SLO).
**Phase 18:** TM rule concurrency (concurrent signal generation).
**Phase 22:** MarketingGate concurrency (concurrent sends; race condition: self-exclude between queue and send).

**Financial invariants verified under concurrent load:**
1. Double-entry balance: `sum(debit) = sum(credit)` per entry, under concurrent inserts.
2. Immutability: no UPDATE/DELETE on posted entries, under concurrent access.
3. Idempotency: same key + same body = single effect, under concurrent retries.
4. Tenant scoping: cross-tenant = zero rows, under concurrent multi-tenant load.
5. Audit chain: hash chain integrity, under concurrent inserts.
6. Ledger reconciliation: read model matches ledger, under concurrent writes.

### 3. Chaos Suite (Netflix-style)

- KillSwitchConsumer crash → recovery via outbox (at-least-once; idempotent).
- Outbox relay crash → recovery; no missed events.
- Redis crash → consumers pause; recover on restart.
- Postgres failover → RTO/RPO measured.
- ASGI WebSocket server crash → connections re-established.
- Celery worker crash → jobs re-queued; idempotent.
- Vendor outage (PSP, KYC, game provider) → circuit breaker; fallback.
- Network partition → split-brain prevention; consistency maintained.

### 4. Load Suite (errata E5 capacity table)

**Capacity table (errata E5 restored per blueprint §0):**

| Metric | Initial | Growth | Global |
|---|---|---|---|
| Wallet TPS | 5-10 | 100 | 1000+ |
| Concurrents | 2k | 50k | 500k+ |
| Events/sec | 500 | 10k | 100k+ |

**Planning assumptions, not forecasts** (per blueprint).

**Load test scenarios:**
- Steady-state: 1x baseline for 1 hour; verify SLOs met.
- Burst: 10x baseline for 1 minute; verify no errors; verify recovery.
- Sustained peak: 5x baseline for 1 hour; verify SLOs met.
- Stress: ramp until break; document breaking point; verify graceful degradation.

**Performance targets verified:**
- Kill Switch <200ms SLO (Phase 14 — most critical; regulator-mandated).
- RLS query latency: <50ms p99 across all tenant-scoped tables.
- Audit chain insert throughput: >500 events/sec sustained.
- MarketingGate decision latency: <50ms p99.
- LLM RAG pipeline: <5s p99 end-to-end (Phase 19).
- Partner webhook delivery: <5s p99 (Phase 24).

## Alternatives

- **Partial validation** (rejected). Launch risk; regulator risk. The Knight Capital failure is the canonical example.
- **Manual testing only** (rejected). Cannot scale; subjective; not reproducible.
- **No chaos testing** (rejected). Production failures undetected. Netflix's chaos engineering showed this is essential.
- **No load testing** (rejected). Performance bottlenecks undetected until production.
- **No security testing** (rejected). Vulnerabilities exploited in production.
- **No concurrency testing** (rejected). Race conditions corrupt financial integrity.

## Consequences

- 4 validation suites (security + concurrency + chaos + load).
- Comprehensive coverage across all 25 phases.
- All four must pass for GO.
- Kill Switch <200ms is regulator-mandated (non-negotiable).
- Tipping-off grep finally non-vacuous (real code to scan).
- AI Boundary finally verifiable (linter rule 175 against real code).

## Validation Plan

- Each suite executed; results documented; failures remediated; re-run until GREEN.
- Security suite: penetration report; cross-tenant leak test; tipping-off grep; PCI scan; AI Boundary grep; injection suite.
- Concurrency suite: 6 financial invariants under concurrent load; all must hold.
- Chaos suite: 8 failure scenarios; all recover.
- Load suite: capacity table scenarios; all SLOs met.
