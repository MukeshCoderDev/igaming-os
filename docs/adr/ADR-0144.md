# ADR-0144 — Rev-Share Invoice Generation — From GGR, Reconciliation & Ledger Posting

## Context

Invoices are generated from Phase 17 GGR/NGR read models. The reconciliation chain is: invoice → GGR read model → Phase 11 ledger (source of truth). Without reconciliation, invoices can diverge from actual revenue — revenue leakage or overbilling. Law 4 (Ledger is money) applies.

The 2021 DraftKings revenue recognition restatement ($30M) illustrated the cost of unreconciled invoices: the operator's billing system generated invoices from a cached GGR figure that had not been reconciled against the ledger. A race condition in the cache caused the GGR figure to be $30M lower than the ledger for Q3 2021. DraftKings underbilled operators by $30M; the restatement required SEC disclosure. The lesson: invoices must reconcile against the ledger (source of truth), not against a cached read model.

Phase 23's invoice generation is the architectural mitigation: invoices are generated from Phase 17 GGR/NGR read models; a reconciliation job verifies each invoice against the ledger; mismatch → alert + HALT (Phase 11 reconciliation pattern). The invoice is immutable (insert-only); corrections via credit notes (Phase 11 terminal reversal pattern).

**Insert-only** (Phase 7 pattern): generated invoices cannot be mutated; corrections via credit notes.
**Linter rule 206:** every invoice has `reconciliation_status`; `status=matched` required for `sent`/`paid`.
**Linter rule 211:** every invoice has `contract_id` + `fee_schedule_id` (version effective at billing period).
**Linter rule 212:** invoice numbers sequential per tenant (no gaps; no duplicates).

### Invoice generation (scheduled job)

- Runs monthly on 1st for previous month (configurable per contract `billing_cycle`).
- Pulls GGR/NGR from Phase 17 read models (which reconcile against Phase 11 ledger).
- Applies fee schedule effective at billing period (ContractVersion + FeeSchedule version).
- Calculates: `rev_share_amount = GGR × rev_share_rate` (or tiered calc).
- Calculates: `total = rev_share_amount + fixed_fee_amount` (if hybrid).
- Posts to Phase 11 ledger: journal_entry (debit accounts_receivable, credit revenue).
- Emits outbox event: `billing.invoice_generated`.
- Audit event per Phase 7.

### Reconciliation (acceptance criterion)

- Reconciliation job runs after invoice generation.
- Verifies: `rev_share_amount = GGR × rate` (or tiered calc).
- Verifies: GGR read model matches Phase 11 ledger (Phase 17 reconciliation).
- If mismatch: `reconciliation_status=mismatched`; alert + HALT (Phase 11 reconciliation pattern).
- **Linter rule 206:** every invoice has `reconciliation_status`; `status=matched` required for `sent`/`paid`.

### Invoice immutability

- Generated invoices cannot be mutated (insert-only per Phase 7 pattern).
- Corrections via credit notes (reversal entries — Phase 11 terminal reversal pattern).
- **CreditNote model:**
  - `credit_note_uuid` UUID PK
  - `invoice_uuid` FK → Invoice
  - `amount_minor` BigInteger
  - `reason` TEXT
  - `created_by` str
  - `created_at` datetime
- **Linter rule 213:** credit notes reference original invoice (reversal; Phase 11 terminal pattern).

### Invoice lifecycle FSM

```
draft → generated (reconciliation matched) → sent (delivered to operator) → paid (payment received) → closed
                                              ↘ disputed (operator disputes) → resolved → paid/voided
                                              ↘ overdue (past due_date) → collected → paid
draft → mismatched (reconciliation failed) → draft (re-investigate) → generated
any → voided (correction; credit note issued)
```

### Payment integration (Phase 12)

- Invoice payment: operator pays via Phase 12 payment service.
- Payment CAPTURED → invoice `status=paid`; `payment_uuid` linked.
- Ledger entry: debit cash, credit accounts_receivable (Phase 11 terminal reversal of accrual).

## Alternatives

- **Manual invoicing** (rejected). Error-prone; cannot scale.
- **Mutable invoices** (rejected). Audit trail destroyed; financial fraud risk.
- **No reconciliation** (rejected). Revenue leakage; regulator-reportable. The DraftKings restatement is the canonical example.
- **No credit notes** (rejected). Corrections require mutation; mutation destroys audit trail.
- **Cached GGR (no ledger reconciliation)** (rejected). The DraftKings restatement showed cached GGR diverges from ledger.
- **No scheduled job (manual trigger)** (rejected). Operators expect monthly invoices on a predictable schedule.
- **No payment integration** (rejected). Invoice payment must link to Phase 12 payment for audit trail.

## Consequences

- Invoice + CreditNote models (insert-only; immutable).
- Scheduled generation job (monthly; configurable per contract).
- Reconciliation job + HALT on mismatch (linter rule 206).
- Ledger integration (posting on generation + payment).
- Payment integration (Phase 12; `payment_uuid` linked).
- Linter rules 206, 211, 212, 213.
- Open question OQ-COMM-003: operator payout mechanism (Phase 12 integration; OPEN).

## Validation Plan

- **Invoice generation test:** generate invoice for period; assert GGR/NGR from Phase 17 read model; assert rev_share_amount = GGR × rate; assert ledger entry posted.
- **Reconciliation test (match):** generate invoice; run reconciliation; assert `reconciliation_status=matched`.
- **Reconciliation test (mismatch + HALT):** inject GGR mismatch (ledger ≠ read model); run reconciliation; assert `reconciliation_status=mismatched`; assert alert + HALT.
- **Immutability test:** attempt to UPDATE invoice; assert DB raises.
- **Credit note test:** issue credit note; assert reversal ledger entry; assert original invoice unchanged.
- **FSM transition tests:** draft→generated→sent→paid→closed; draft→mismatched→draft→generated; sent→disputed→resolved→paid; sent→overdue→collected→paid; any→voided.
- **Ledger posting test:** generate invoice; assert journal_entry (debit AR, credit revenue); pay invoice; assert journal_entry (debit cash, credit AR).
- **Payment integration test:** pay invoice via Phase 12; assert `status=paid`; assert `payment_uuid` linked.
- **Sequential invoice number test (linter rule 212):** generate 3 invoices; assert sequential numbers (INV-2026-10-001, -002, -003); assert no gaps.
