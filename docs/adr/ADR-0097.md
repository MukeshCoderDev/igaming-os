# ADR-0097 — Provider Callback Validation — HMAC + Replay Protection + Idempotency

## Context

Game providers (Phase 15 game-launch path) call back into our platform to report bet placements, settlements, voids, and bonus triggers. These callbacks are money-direction events: a forged "settlement won" callback credits a player balance that was never wagered. A replayed "settlement lost" callback could double-debit if not deduplicated. A delayed callback delivered out-of-order could void a round that has already been settled. Each of these is regulator-reportable.

The web is hostile. Callbacks arrive over TLS but TLS does not authenticate the sender — any party that can route packets to our endpoint can attempt delivery. We must therefore authenticate every callback cryptographically, reject replays, and deduplicate by provider event ID.

## Decision

Every provider callback MUST pass three independent gates before any DB write:

1. **HMAC-SHA256 signature verification (constant-time).**
   - The provider and Noventra share a per-tenant secret, rotated quarterly.
   - The signature is `HMAC-SHA256(secret, timestamp + "." + raw_body)`.
   - Verification uses `hmac.compare_digest` to prevent timing attacks.
   - Failure → HTTP 400. No DB write. Logged at WARN with provider name + IP, not body.

2. **Replay protection (timestamp tolerance + nonce cache).**
   - The callback body carries a `timestamp` field. We reject any callback where `|now - timestamp| > 5 minutes` (configurable per provider).
   - Within the tolerance window, we cache the `(provider, event_id)` tuple in Redis with TTL = tolerance + 60s. A second delivery of the same tuple within the window is rejected as replay (HTTP 200, idempotent ack — we do not want the provider to retry).

3. **Idempotency (Phase 8 inbox pattern).**
   - After signature + replay checks pass, we insert a row into `inbox_event` keyed by `(tenant_uuid, provider, provider_event_id)`. The unique constraint deduplicates.
   - A duplicate insert (constraint violation) returns HTTP 200 with `{"status": "already processed"}`. The provider treats this as success and does not retry.
   - The inbox row records the raw body, signature, and processing status. On crash mid-processing, the relay (Phase 8 outbox/inbox) re-drives the event to completion.

Order of gates is mandatory: signature first (cheap, rejects forgery), then replay (cheap, rejects re-delivery within window), then idempotency (DB write, deduplicates). Any other order either leaks information or wastes DB writes.

## Alternatives

- **TLS client certificates** (rejected). Operationally heavy; not all providers support it. We may add this as defense-in-depth later (Q5 budget).
- **OAuth 2.0 client-credentials flow** (rejected). Adds token-refresh dependency; failures cascade to money events.
- **Signature only, no replay** (rejected). Vulnerable to captured-packet replay within the timestamp tolerance.
- **Idempotency only, no signature** (rejected). Anyone can deliver a "valid" event with a fresh event_id.

## Consequences

- Every provider integration must publish a callback signature spec. The integration contract is part of the operator onboarding pack.
- Redis must be highly available for replay protection. Phase 14 already requires this for kill switch.
- The `inbox_event` table grows at provider-event rate. Retention is 30 days (Phase 7 audit retention is 7 years; inbox is operational, not audit).
- Linter rule 114 (Phase 15) forbids any provider callback handler that does not call all three gates in order.

## Validation Plan

- Forgery test: send a callback with a wrong signature → HTTP 400, no DB write.
- Replay test: send the same callback twice within tolerance → first 200 processed, second 200 already-processed, exactly one DB row.
- Out-of-tolerance test: send a callback with timestamp = now - 10 minutes → HTTP 400, no DB write.
- Idempotency test: simulate provider retry (crash mid-processing) → second delivery resumes from inbox, exactly-once ledger posting.
- Linter rule 114: grep for callback handlers; assert each calls `verify_signature`, `check_replay`, `record_inbox` in that order.
