# ADR-0103 — Release FSM — Evidence-Gated Transitions (No Skipping)

## Context

A game release is the lifecycle from initial draft through to publication and (eventually) suspension/revocation. Each transition requires specific evidence: a draft can become math_configured only when a math version exists; math_configured can become rng_certified only when an RNG cert is attached; rng_certified can become math_certified only when a math cert is attached; and so on.

The regulator mandate (Law 19) is absolute: no game can skip states. An operator cannot publish a game that has not been lab-tested, even if the operator is confident in the math. An operator cannot publish a game whose math has been modified since certification, even if the modification is a one-line fix to a typo in the paytable. Every state transition requires its specific evidence; absent evidence → no transition.

This is the most regulator-sensitive FSM in the platform. It is also the most operator-friction-heavy: operators want to ship fast, and the FSM is the gate that prevents them from shipping uncertified math. The FSM must therefore be:

1. **Enforced at the data layer** (DB trigger or application-level invariant that cannot be bypassed by an admin).
2. **Auditable** (every transition logged with the evidence that authorized it).
3. **Evidence-linked** (the transition record cites the specific evidence UUID that authorized it; without that UUID, the transition cannot proceed).

### States + transitions

| From | To | Required evidence |
|---|---|---|
| draft | math_configured | `active_math_version_uuid` set (math version exists in draft status) |
| math_configured | rng_certified | `rng_cert_evidence_uuid` set (RNG cert evidence attached, non-expired) |
| rng_certified | math_certified | `math_cert_evidence_uuid` set (math cert evidence attached, non-expired) |
| math_certified | lab_tested | `lab_test_evidence_uuid` set (lab test evidence attached, non-expired) |
| lab_tested | ready_for_release | All three evidence UUIDs verified non-expired |
| ready_for_release | published | `operator_approval_at` + `operator_approval_by` set (operator sign-off) |
| published | suspended | Any: cert expired, operator action, regulator mandate |
| suspended | published | Re-certification: new evidence attached; operator re-approval |
| suspended | revoked | Terminal: regulator-mandated revocation |
| published | revoked | Terminal: regulator-mandated revocation |

### No skipping

The FSM implementation MUST refuse any transition that skips a state. Example: a release in `math_configured` cannot transition directly to `published` — it must pass through `rng_certified`, `math_certified`, `lab_tested`, `ready_for_release`, in order.

This is enforced by:
1. The `@transition` decorator on each method (Phase 8 state machine base) — only one source state per transition.
2. A DB-level CHECK constraint that verifies the `status` column only accepts the listed values.
3. An application-level invariant that the transition method was called (not bypassed by raw SQL).

### Evidence verification

Each transition method verifies the required evidence UUID is set AND that the linked `CertificationEvidence` is non-expired. If the evidence is missing or expired, the transition raises `TransitionError` and the release remains in its current state.

## Alternatives

- **Single "approved" state** (rejected). No visibility into what evidence is missing; regulator inquiry cannot tell if RNG was certified but math wasn't.
- **Optional evidence** (rejected). Operators would skip; regulator-reportable.
- **Application-level enforcement only** (rejected). Bypassed by raw SQL access.
- **No suspension path** (rejected). Operators cannot respond to cert expiry or regulator mandate without suspending; would force revocation (terminal, no recovery).
- **Auto-publish on ready_for_release** (rejected). Operator sign-off is regulator-mandated; auto-publish removes the human gate.

## Consequences

- New `GameRelease` model. Migration creates table + RLS + CHECK constraint on `status`.
- 9 transition methods on the FSM. Each verifies evidence; each emits audit + outbox events.
- Operator approval is a named-human action. The `operator_approval_by` field is a string (not a UUID) because it is a name on a record, not a system user.
- Linter rule 131 forbids any code path that publishes a release without all evidence verified.
- Linter rule 132 forbids any code path that skips a state (e.g., direct draft→published).
- Linter rule 133 requires every release in `published` status to have a non-expired cert evidence chain.

## Validation Plan

- Happy-path test: draft → math_configured → rng_certified → math_certified → lab_tested → ready_for_release → published. Each transition succeeds.
- Negative test: draft → published (skip) → TransitionError.
- Negative test: math_configured → rng_certified with missing evidence → TransitionError.
- Negative test: math_configured → rng_certified with expired evidence → TransitionError.
- Negative test: ready_for_release → published without operator_approval → TransitionError.
- Suspension test: published → suspended (cert_expired); assert active rounds voided; assert new rounds refused.
- Re-certification test: suspended → published (new evidence attached; operator re-approval).
- Revocation test: published → revoked (terminal); assert no further transitions possible.
- Linter rule 131: grep for `status = 'published'` on GameRelease; assert each follows evidence verification.
- Linter rule 132: grep for `@transition` on GameRelease; assert each has a single source state.
- Linter rule 133: query for published releases with expired evidence; assert zero.
