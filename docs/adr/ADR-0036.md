# ADR-0036 — AuditEvent schema + partitioning + event type taxonomy

## Context

The audit log needs a stable schema that supports: tenant-scoped + global events, human vs service actors (Phase 6 distinction), a closed event type catalog, JSON payload, hash chain fields, and partitioning for retention (7-year default, jurisdiction-dependent). The schema must compose with the hash chain (ADR-0035) and redaction (ADR-0037).

## Decision

AuditEvent schema: UUID PK, tenant_id (NULL for global events), actor_id, actor_type (human|service), event_type (closed catalog), target_type, target_id, payload (JSONB), prev_hash, hash, correlation_id (from Phase 4), created_at (DB now()). Partitioning: by month + tenant (PARTITION BY RANGE (created_at) with sub-partitioning by tenant_id LIST). Event type taxonomy: closed catalog seed covering auth.*, tenancy.*, rbac.*, audit.*, security.* events. New types require ADR amendment. Catalog at src/noventra/apps/audit/domain/event_types.py (frozen-tree-cited path).

## Alternatives

Alternatives: (a) single table (no partitioning) — unmanageable at 7-year retention; (b) per-tenant tables — operational explosion; (c) open event type catalog (ad-hoc strings) — audit risk; (d) protobuf payload (not JSONB) — harder to query. (a) rejected for retention; (b) rejected for operational cost; (c) rejected for audit risk; (d) rejected for queryability.

## Consequences

Partitioning adds DDL complexity (monthly partition creation must be automated). Closed catalog requires ADR amendment for new types (intentional friction). JSONB payload is flexible but not type-safe; the event type catalog mitigates. created_at uses DB now() (not app time) for tamper-resistance.

## Validation Plan

Phase 7: migration creates audit_event (partitioned) + audit_chain_head. Phase 7: event type catalog closed (linter rule 40). Phase 7: baseline partition for current month. Phase 8: monthly partition automation (cron). Phase 8: load-test insert at 5k/s.
