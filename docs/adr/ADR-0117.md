# ADR-0117 — Knowledge Chunk Model, Lifecycle & Synchronous Revocation

## Context

Knowledge chunks feed RAG retrieval. A chunk is a unit of static knowledge — a paragraph from a policy document, a FAQ answer, a support article. Chunks are embedded (vectorized) and stored in pgvector for semantic retrieval.

Law 10 (Synchronous Revocation) mandates that a revoked chunk is unretrievable in the same transaction. This is not a cache invalidation problem — it is a regulatory compliance problem. If a player asks "what is the bonus wagering requirement?" and the RAG retrieves a revoked chunk that says "10x" when the current requirement is "20x", the player receives incorrect information. If the player acts on that information (places bets expecting 10x wagering), the operator is liable for the discrepancy.

Law 22 (Edge) mandates realtime invalidation: when a chunk is revoked, all RAG caches that may have cached the chunk must be invalidated immediately. A stale cache that serves a revoked chunk is the same defect as a slow DB that serves it.

Embedding model versioning is required because embedding models change. OpenAI's `text-embedding-ada-002` (1536 dims) was superseded by `text-embedding-3-small` (1536 dims, better quality) and `text-embedding-3-large` (3072 dims). Chunks embedded with the old model cannot be queried with the new model — the vector spaces are incompatible. Without versioning, an embedding model upgrade silently breaks retrieval.

### Synchronous revocation (Law 10)

- Revoked chunk unretrievable in the same transaction.
- DB trigger `BEFORE UPDATE` sets `lifecycle = 'revoked'`; subsequent `SELECT` queries filter `lifecycle != 'revoked'` (Phase 7 pattern, rule 97 extension).
- Linter rule 163: revoked knowledge chunk unretrievable same transaction.
- The retrieval query (ADR-0118) includes `AND lifecycle = 'active'` in the WHERE clause — revoked chunks are never returned.

### Realtime invalidation (Law 22)

- Revoked chunk emits `knowledge.chunk_revoked` event via `RealtimePort` (Phase 14 real adapter).
- RAG cache (semantic cache in Redis) invalidated on receipt.
- All connected RAG consumers receive the invalidation event; stale cache entries purged.
- Linter rule 174: distress signals bypass AI (Law 16); chunk revocation uses the same realtime infrastructure.

### Re-indexing

- When embedding model changes, all chunks must be re-embedded.
- `ReindexJob`: scheduled Celery task; idempotent; per-tenant.
- Old embeddings retained until new embeddings complete + verified; then old chunks → `superseded`.
- Re-indexing is non-blocking (new queries use old embeddings until switchover).

### Embedding model versioning

- Chunks tagged with `embedding_model_version`.
- Queries use matching model; mismatched model = re-embed on read (or reject).
- Linter rule 164: every knowledge chunk has `embedding_model_version` NOT NULL.
- Open question OQ-AI-002: embedding model selection + dimension (1536 for OpenAI; OPEN).

### Lifecycle FSM

```
draft → active → superseded (new version published) → revoked (terminal)
                ↘ revoked (direct revocation)
```

- `draft → active`: chunk published; available for retrieval.
- `active → superseded`: new version published; old version retained for audit but unretrievable.
- `active → revoked`: direct revocation (Law 10); unretrievable same transaction.
- `superseded → revoked`: superseded chunk also revoked (rare; regulatory takedown).

## Alternatives

- **Mutable chunks** (rejected). Law 10 mandates synchronous revocation. Mutable chunks allow in-place edits that bypass revocation.
- **No embedding versioning** (rejected). Model changes break retrieval silently; queries return wrong results.
- **Cache invalidation only (no DB trigger)** (rejected). Race condition: cache invalidated but DB still serves old chunk for in-flight queries. DB trigger is the authoritative gate.
- **Async revocation (eventual consistency)** (rejected). Law 10 mandates synchronous; a revoked chunk served even once is a compliance defect.
- **Single embedding model (no versioning)** (rejected). Model upgrades break all existing embeddings; re-indexing required; versioning is the only safe path.
- **Re-embed on every query (no stored embeddings)** (rejected). Computationally infeasible; latency >5s per query.

## Consequences

- KnowledgeChunk model with pgvector embedding.
- Synchronous revocation (DB trigger + retrieval query filter).
- Realtime invalidation (RealtimePort event; cache purge).
- Reindex job (scheduled; idempotent; per-tenant).
- Embedding model versioning (every chunk tagged; mismatch = reject or re-embed).
- Linter rule 162: knowledge chunk lifecycle transitions audited (Phase 7).
- Linter rule 163: revoked chunk unretrievable same transaction (Law 10).
- Linter rule 164: every chunk has `embedding_model_version` NOT NULL.
- Open question OQ-AI-002: embedding model selection + dimension (OPEN).

## Validation Plan

- **Synchronous revocation test:** revoke a chunk; in the same transaction, query for it; assert zero rows returned.
- **Realtime invalidation test:** revoke a chunk; assert `knowledge.chunk_revoked` event emitted; assert RAG cache purged.
- **Reindex test:** change embedding model; run ReindexJob; assert all chunks re-embedded; assert old chunks → `superseded`; assert new chunks → `active`.
- **Embedding version mismatch test:** query with mismatched embedding model; assert rejection (or re-embed on read).
- **Lifecycle FSM test:** draft → active → superseded; draft → active → revoked; assert transitions audited.
- **Linter rule 163 test:** grep for retrieval queries; assert each includes `lifecycle = 'active'` filter.
- **Linter rule 164 test:** grep for KnowledgeChunk model; assert `embedding_model_version` field NOT NULL.
