# ADR-0032 — RBAC model (permission-based, closed catalog, baseline roles)

## Context

Phase 6 introduces role-based access control with a permission catalog. The catalog must be a closed enumeration (no ad-hoc permissions). Baseline roles (admin, manager, viewer, service) are seeded by migration. The model composes with tenant memberships: a user's effective permissions are the intersection of their membership role (per-tenant) and the permission catalog.

## Decision

Adopt permission-based RBAC. Permission catalog is a closed enumeration in src/noventra/apps/identity/domain/permissions.py (frozen-tree-cited path). Each permission has a code, description, and category. Roles are collections of permissions. Baseline roles seeded by migration: admin (all permissions), manager (read + write + invite), viewer (read-only), service (service-only permissions). Tenant memberships carry a role FK. Effective permissions = role's permissions intersected with the catalog. Custom roles are Phase 7+.

## Alternatives

Alternatives: (a) ABAC (attribute-based) — more flexible but harder to audit; (b) flat roles (no permission catalog) — inflexible; (c) delegated OAuth scopes — coarse; (d) open permission catalog (ad-hoc) — audit risk. (a) rejected for auditability; (b) rejected for inflexibility; (c) rejected for coarseness; (d) rejected for audit risk (must be closed).

## Consequences

Permission catalog must be maintained as new endpoints are added. Custom roles (Phase 7+) add complexity. The (role × endpoint) test matrix grows quadratically; parametrized tests mitigate. Service role must be distinct from human roles (no human can have service permissions).

## Validation Plan

Phase 6: permission catalog closed (linter rule 35). Phase 6: baseline roles seeded. Phase 6: (role × endpoint) test matrix parametrized. Phase 6: cross-tenant denial at user-membership level. Phase 7: custom roles + permission management UI.
