# ADR-0127 — Approval Gates (Law 14; High-Risk Requires Human Approval)

## Context

Law 14 (Law of Bounded Agents): Consequential actions require human approval. Unapproved high-risk agent actions are the canonical AI safety failure. The 2024 e-commerce refund agent (cited in ADR-0125) is one example; another is the 2023 Knight Capital trading algorithm incident ($440M loss in 45 minutes) where an unbounded algorithm executed trades without approval gates.

In iGaming, the stakes are regulator-sensitive. An unbounded Fraud/AML agent could freeze player funds without approval (Law 14 violation; regulator-reportable). An unbounded Retention agent could queue bonus-recommending journeys for vulnerable players (Law 18 violation). An unbounded Game QA agent could approve a math change without lab certification (Law 19 violation). The approval gate is the architectural mitigation: high-risk tools do not execute until a named human approves.

Phase 18 (ADR-0113) established the punitive action approval pattern (dual control for high-severity). Phase 20 extends this to agent actions: every high-risk tool call creates an approval request; the tool does not execute until a human approves; if rejected, the tool never executes. The workflow is auditable (Phase 7), time-bounded (SLA), and enforceable at the linter level (rule 178).

### Approval workflow

1. Agent calls high-risk tool (`requires_approval=true`) → approval request created (`status=pending`).
2. Tool does NOT execute; `output` is NULL.
3. Human reviewer notified (via Phase 8 notifications — internal channel; Slack/email to approver queue).
4. Human reviews `input`; approves or rejects with `justification`.
5. If approved (`status=approved`): tool executes; `output` recorded; `status=executed`; audit event emitted (Phase 7).
6. If rejected (`status=rejected`): tool does not execute; rejection reason recorded; audit event emitted.
7. If not reviewed within SLA (default 24h; OQ-AGENT-002): `status=expired`; tool does not execute; alert to compliance officer.

### High-risk tools (requires_approval=true)

| Tool | Agent | Approval Gate | Approver |
|---|---|---|---|
| `journey_queue` | Retention | campaign_approval | Marketing Manager + Compliance Officer |
| `bonus_recommend` | Retention / Support | campaign_approval | Compliance Officer |
| `evidence_summarize_for_sar` | Fraud/AML | punitive_actions | MLRO (Phase 18 ADR-0111) |
| `test_approve` | Game QA | math_changes | Compliance Officer + Lab (Phase 16 ADR-0103) |
| `code_merge` | Dev Assistant | code_review | Engineering Lead |
| `report_external` | Analytics | external_reports | CFO + Compliance Officer |

Low-risk tools (`requires_approval=false`): execute immediately (logged in execution log per ADR-0128).

### Dual control (extends Phase 18 ADR-0113)

- Critical agent actions (e.g., SAR filing by Fraud/AML agent) require dual approval.
- Requester (agent) and approver (human) are always different (agent cannot approve its own request).
- For the most critical actions (SAR filing), two human approvers may be required (MLRO + Legal Counsel).
- **Linter rule 178:** high-risk tool execution requires `approved_by` NOT NULL.

### SLA enforcement

- Default SLA: 24 hours (configurable; OQ-AGENT-002).
- Celery beat task `check_approval_sla` runs hourly.
- Approvals past SLA → `status=expired`; tool does not execute; alert to compliance officer.
- SLA per approval_gate (configurable): punitive_actions 4h; math_changes 8h; campaign_approval 24h; code_review 48h.

## Alternatives

- **Auto-approve** (rejected). Law 14 violation; safety risk. The Knight Capital incident is the canonical example.
- **All tools require approval** (rejected). Low-risk tools (player_lookup, segment_query) don't need friction; approval fatigue leads to rubber-stamping.
- **No SLA (approvals never expire)** (rejected). Pending approvals accumulate; forgotten approvals become stale; the agent's request no longer reflects the current state.
- **Agent approves its own request** (rejected). No separation of duties; the agent could approve anything it requested.
- **Single approver for all** (rejected). Different approval gates need different expertise (MLRO for SAR; Engineering Lead for code; CFO for external reports).
- **No justification field** (rejected). Approver must document why they approved/rejected; regulator inquiries ask "why was this approved?"

## Consequences

- AgentApproval model with 5-state FSM (pending → approved/rejected → executed/expired).
- Approval workflow (create → notify → review → execute/reject).
- SLA enforcement (default 24h; per-gate configurable).
- Dual control for critical actions (agent != approver; sometimes 2 human approvers).
- Linter rule 178: high-risk tool execution requires `approved_by` NOT NULL.
- Every approval + execution audited (Phase 7).
- Open question OQ-AGENT-002: approval SLA default (24h recommended; OPEN).

## Validation Plan

- **Approval workflow test (pending → approved → executed):** agent calls high-risk tool; approval created (pending); human approves; tool executes; output recorded; audit event emitted.
- **Rejection test:** agent calls high-risk tool; approval created (pending); human rejects; tool does not execute; rejection reason recorded.
- **SLA expiry test:** approval pending > 24h; Celery task runs; status → expired; tool does not execute; alert fired.
- **Dual control test:** agent attempts to approve its own request; assert denied (agent != approver).
- **High-risk-without-approval denied test (linter rule 178):** attempt to execute high-risk tool without `approved_by`; assert denied with `E_AGENT_APPROVAL_REQUIRED`.
- **Justification required test:** attempt to approve without justification; assert denied.
- **Per-gate SLA test:** punitive_actions approval expires in 4h; campaign_approval in 24h; assert different SLAs enforced.
