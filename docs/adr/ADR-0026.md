# ADR-0026 — Error format (RFC 7807 + catalog + i18n-key messages)

## Context

API errors must be machine-readable, consistent across endpoints, and i18n-capable. Ad-hoc error JSON shapes break client integrations. RFC 7807 (Problem Details for HTTP APIs) is the standard. A central catalog prevents code drift. Stack traces must never leak in production (NFR §1 security).

## Decision

Adopt RFC 7807 problem+json. Catalog of error codes in src/noventra/errors/catalog.py. Each code has: code, http_status (one per code), i18n_key (default en), title, detail_template. Generated docs at docs/architecture/error-catalog.md. correlation_id always included. Stack traces emitted in logs only, never in response bodies; traces field is dev-only (DEBUG=True).

## Alternatives

Alternatives: (a) ad-hoc JSON errors — inconsistent; (b) DRF default error responses — not RFC 7807; (c) JSON:API errors — heavier schema. (a) rejected for inconsistency; (b) rejected for non-conformance; (c) rejected for weight.

## Consequences

Catalog must be regenerated when codes are added. i18n keys must resolve for every supported locale (Q19). One-HTTP-status-per-code constraint requires careful code design (no multi-status codes).

## Validation Plan

Phase 4: catalog parses (test asserts every code has required fields); one HTTP status per code (test); i18n keys resolve (test against en locale). Phase 4: stack-trace suppression test against production settings.
