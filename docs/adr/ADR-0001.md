# ADR-0001 — Adopt event-sourced domain model

## Context

The platform must support a complete audit trail of every state change, rebuildable read models, and deterministic replay for compliance and recovery. Traditional CRUD persistence loses history and complicates regulatory evidence collection. FATF Rec.11 and GDPR Art.5(2) accountability both favor an immutable event record as the source of truth.

## Decision

Adopt event sourcing as the primary persistence model for domain aggregates. State changes are recorded as immutable domain events; aggregates are rebuilt by replaying events. Read models are projections from the event log and may be rebuilt at any time (DEC-0018).

## Alternatives

Alternatives considered: (a) CRUD with audit triggers — simpler to implement but loses history and complicates rebuilds; (b) Change Data Capture (CDC) on top of CRUD — adds operational complexity without simplifying the model; (c) Temporal tables (PostgreSQL pg_temporal / SQL:2011) — limited to row-level history, no domain-event semantics. (a) and (b) rejected for insufficient auditability; (c) rejected for loss of domain semantics.

## Consequences

Event store becomes a critical SPOF; operational discipline required for schema evolution of events (versioning, upcasters). Read-model lag must be monitored. Developer ergonomics: aggregates cannot be inspected via simple SQL queries; tooling required. Storage cost grows monotonically; snapshotting mitigates but does not eliminate.

## Validation Plan

Phase 3 spike: implement a single aggregate (Tenant) end-to-end with event sourcing; verify rebuild from empty event log produces identical state. Phase 4: load-test the event store at 10k events/s sustained. Phase 11: validate that ledger postings (DEC-0011) compose naturally with event-sourced aggregates.
