# ADR-0014 — Tenant as first-class aggregate root

## Context

Every operation in the platform is scoped to a tenant. Without a first-class tenant aggregate, scoping leaks into every service and every model, creating isolation risks (DEC-0003).

## Decision

Tenant is a first-class aggregate root. Every other aggregate carries a `tenant_id` reference. The tenant is the root of the authorization graph and the unit of metering, billing, and audit.

## Alternatives

Alternatives considered: (a) tenant as a tag on resources — no enforcement; (b) tenant as a configuration value — easily spoofed; (c) tenant implicit in user identity — breaks for service-to-service calls. (a) rejected for no enforcement; (b) rejected for spoofing risk; (c) rejected for service auth gap.

## Consequences

Every aggregate must carry `tenant_id`; this is enforced by RLS (DEC-0003) but is also a code-level invariant. Tenant deletion is a multi-step process: disable, archive, purge (after retention period).

## Validation Plan

Phase 3: implement the Tenant aggregate; verify that every subsequent aggregate (User, AuditEntry, etc.) carries `tenant_id`. Phase 4: red-team test that attempts to create a resource without a tenant. Phase 8: verify audit log queries are scoped to the requesting user's tenant.
