# ADR-0116 — Prompt Template Versioning

## Context

Prompts change over time. Without versioning, you cannot audit which prompt produced which response — a regulator inquiry asks "what prompt was used for this AI-generated response on 2026-03-15?" and the answer is "we don't know" because the prompt was edited in place. You cannot A/B test (no way to compare two versions side by side). You cannot rollback (a bad prompt change breaks production and there is no previous version to revert to).

The 2023 Air Canada chatbot incident illustrates the stakes: the chatbot gave a customer incorrect bereavement fare information, the customer sued, and Air Canada was held liable for the chatbot's response. The airline could not produce the exact prompt used at the time of the incident because prompts were edited in place without version history. The court ruled that the airline was responsible for the chatbot's output — and without prompt versioning, the airline could not even reconstruct what the chatbot was instructed to say.

Phase 19 mandates prompt versioning: every prompt change creates a new version; old versions retained indefinitely; every LLM call records which prompt version was used (Phase 7 audit event `ai.prompt_used`).

## Decision

### PromptTemplate model

| Field | Type | Notes |
|---|---|---|
| `template_uuid` | UUID PK | |
| `tenant_uuid` | UUID | Tenant scope (RLS) |
| `name` | str | e.g., `rag_answer_composer`, `chat_general` |
| `version` | str | Semver (e.g., `1.0.0`, `1.1.0`, `2.0.0`) |
| `template` | TEXT | Prompt text with `{{variable}}` placeholders |
| `variables` | JSONB | Variable definitions + defaults |
| `status` | enum | draft, active, deprecated |
| `created_at` | datetime | auto_now_add |
| `created_by` | str | Named human (CODEOWNERS) |
| `updated_at` | datetime | auto_now |

**Unique constraint:** `(tenant_uuid, name, version)` — no duplicate versions per name per tenant.

### Versioning

- Every prompt change creates a NEW version (insert-only per Phase 7 pattern).
- Old versions retained indefinitely (audit trail).
- Only one `active` version per `name` per tenant; activating a new version deactivates the previous.
- `deprecated` versions retained for audit; new LLM calls refuse to use them.

### A/B testing

- Two `active` versions allowed per `name` (A + B).
- Traffic split configurable (e.g., 80/20).
- Results tracked per version (response quality, cost, latency).
- Winner promoted to sole `active`; loser → `deprecated`.

### Rollback

- Revert to previous version: set previous version `active`; current version `deprecated`.
- Audit logged (Phase 7 event `ai.prompt_rollback`).

### Audit trail

- Every LLM call records which prompt version was used (Phase 7 audit event `ai.prompt_used` with `template_uuid`, `version`, `variables_rendered`).
- Linter rule 160: every LLM call records `prompt_template_id`.

### Variables

- Tenant-specific overrides (e.g., operator name, support hours, jurisdiction-specific disclaimers).
- Variables resolved at render time; missing variable = hard fail (no silent default).

## Alternatives

- **No versioning** (rejected). Cannot audit; cannot rollback; cannot A/B test. The Air Canada incident is the canonical example.
- **External prompt management (LangSmith, PromptLayer)** (rejected initially). Adds dependency; build in-house for control. May revisit in Phase 22 if scale demands.
- **In-place editing with audit log** (rejected). Audit log shows the change but the LLM call may have used the pre-edit prompt; reconstruction is impossible.
- **Single active version (no A/B)** (rejected). Cannot optimize prompts; cannot test changes before full rollout.
- **Variable defaults (silent)** (rejected). Missing variable = silent default = wrong prompt rendered. Hard fail is safer.

## Consequences

- PromptTemplate model required with versioning + unique constraint.
- Every LLM call records prompt version (linter rule 160).
- A/B testing supported (two active versions; traffic split).
- Rollback supported (audit logged).
- Variables resolved at render time; missing = hard fail.
- Linter rule 160: every LLM call records `prompt_template_id`.

## Validation Plan

- **Versioning test:** create prompt v1.0.0; edit → v1.1.0; assert both exist; assert v1.0.0 retained.
- **A/B test:** activate v1.0.0 (80%) + v1.1.0 (20%); assert traffic split; assert results tracked per version.
- **Rollback test:** activate v1.1.0; rollback to v1.0.0; assert v1.0.0 active; v1.1.0 deprecated; audit event emitted.
- **Audit trail test:** make an LLM call; assert `ai.prompt_used` audit event with template_uuid + version + variables_rendered.
- **Missing variable test:** render prompt with missing variable; assert hard fail (no silent default).
- **Linter rule 160 test:** grep for LLM call code; assert each records `prompt_template_id`.
