# ADR-0130 — Agent Runtime (Orchestration; LLM Integration; Outbox Events)

## Context

Agents need orchestration: LLM generates tool calls (Phase 19); tools execute (Phase 20 ADR-0126); approvals gate high-risk (ADR-0127); execution logs record (ADR-0128); outbox emits events (Phase 8). The runtime ties these together into a coherent execution path.

The threat is orchestration gaps. Without a runtime, each agent implements its own LLM-call-then-tool-execute-then-log flow, and the flows drift. One agent forgets to log; another forgets to check approval; a third bypasses the LLM gateway and calls OpenAI directly. The runtime centralizes the flow so all agents behave consistently. The runtime is the single chokepoint; if the runtime is correct, all agents are correct; if the runtime has a bug, all agents have the bug (but the bug is in one place, fixable in one place).

Phase 19's 10-step RAG pipeline (ADR-0124) is the precedent: each step is a pure function; the pipeline composes them. Phase 20's AgentRuntime follows the same pattern: each phase of agent execution (trigger → LLM → tool check → approval → execute → log → outbox) is a pure function; the runtime composes them.

## Decision

### AgentRuntime service

**1. Agent invocation:**
- **Trigger:** user query (chat), scheduled job (e.g., RG Triage hourly), or event-driven (e.g., Fraud/AML on risk signal).
- **Agent identity:** service identity (Phase 6 `typ=service`); scoped permissions.
- **Context:** `tenant_id`, `player_id` (if applicable), `correlation_id` (Phase 4).

**2. LLM call (Phase 19):**
- Agent prompt template (Phase 19 ADR-0116) loaded by name + version.
- LLM Gateway (Phase 19 ADR-0115) called.
- LLM output: structured tool call `{tool_name, input}` OR natural language response.
- LLM call recorded (Phase 19 audit; `llm_call_id` for execution log link).

**3. Tool execution (ADR-0126):**
- If LLM output is a tool call:
  - Check tool in agent's `allowed_tools` (else denied with `E_AGENT_TOOL_FORBIDDEN`; **linter rule 182**).
  - Check tool NOT in agent's `forbidden_tools` (defense-in-depth; else denied).
  - Validate `input` against tool's `input_schema` (else denied with `E_TOOL_INPUT_INVALID`).
  - If high-risk (`requires_approval=true`): create approval request (ADR-0127); do not execute; `status=pending_approval`.
  - If low-risk: execute mapped service method (ADR-0126); validate output against `output_schema`.
- Tool execution logged (ADR-0128).

**4. Approval handling (ADR-0127):**
- If approval pending: human reviews; approves/rejects (with justification).
- If approved: execute mapped service method; log; emit outbox event.
- If rejected: log; do not execute; emit outbox event (`agent.tool_denied`).
- If expired (SLA breach): log; do not execute; alert compliance officer.

**5. Outbox events (Phase 8):**
- Every tool execution emits outbox event: `agent.tool_executed` with `tool_name`, `input`, `output`, `agent_id`, `correlation_id`.
- Consumers: reporting (Phase 17), risk (Phase 18), compliance (Phase 21).
- Outbox pattern (Phase 8): event + tool execution in same DB transaction (atomic).

**6. Degradation (Law 16):**
- If LLM Gateway degrades (Phase 19 L0-L4): agent degrades accordingly.
- L3: deterministic fallback (e.g., Support Knowledge → "Please contact support").
- L4: refuse + log ("Agent unavailable; please contact support").
- Degradation is per-agent (configurable): some agents (RG Triage) have no L4 — they must always respond (distress detection is too important to refuse).

**7. Distress short-circuit (Law 16):**
- If distress signal detected (Phase 14 RGPort): agent bypasses LLM; deterministic response.
- RG Triage agent specifically: distress detection is its primary function; distress short-circuit is mandatory.
- Distress short-circuit latency: <100ms p99 (no LLM call).
- **Linter rule 182 (extension):** distress signals bypass agent LLM.

### Runtime composition (pure functions)

Each phase is a pure function: input → output, no side effects (except Phase 2 LLM call, which is non-deterministic but goes through the gateway). Phases are composed in sequence:

```
trigger → llm_call → tool_check → approval_check → tool_execute → log → outbox
```

Any phase can short-circuit the pipeline:
- `trigger`: distress signal → deterministic response (bypass LLM).
- `tool_check`: forbidden tool → denied (bypass execution).
- `approval_check`: high-risk → pending approval (bypass execution until approved).

Short-circuits are logged (ADR-0128) with appropriate status (`denied`, `pending_approval`, `distress_short_circuit`).

## Alternatives

- **Direct LLM-to-DB** (rejected). Law 14 violation; no bounded tools; no enforcement.
- **No runtime (agents are just prompts)** (rejected). No enforcement; no audit; each agent drifts.
- **Runtime as monolithic function** (rejected). Hard to test; hard to extend; pure-function composition is testable.
- **No degradation** (rejected). Law 16 mandates graceful degradation; silent failure abandons the user.
- **No distress short-circuit** (rejected). Law 16 mandates distress bypasses AI; an LLM generating a "sympathetic response" to a self-exclusion signal is a regulator-reportable defect.
- **No outbox events** (rejected). Phase 8 outbox is the reliability pattern; without it, events are lost on crash.
- **Per-agent runtime (no shared runtime)** (rejected). Drift; one agent forgets to log; another forgets approval check. Shared runtime = single point of correctness.

## Consequences

- AgentRuntime service (orchestration; pure-function composition).
- LLM integration via Phase 19 LLM Gateway.
- Approval handling via Phase 20 ADR-0127.
- Execution logs via Phase 20 ADR-0128.
- Outbox events via Phase 8.
- Degradation L0-L4 (per-agent configurable).
- Distress short-circuit (<100ms p99; mandatory for RG Triage).
- Linter rule 182: agent cannot call tool not in `allowed_tools` (Law 14).
- Open question OQ-AGENT-004: agent scheduling (RG Triage hourly; Fraud/AML event-driven; OPEN).
- Open question OQ-AGENT-006: distress short-circuit threshold (Phase 14 RGPort integration; OPEN).

## Validation Plan

- **End-to-end agent test (trigger → LLM → tool → execution → log → outbox):** invoke Support Knowledge agent; assert LLM call → tool call → execution → log entry → outbox event.
- **Approval handling test:** invoke Retention agent with high-risk tool; assert approval request created; assert tool does not execute until approved; assert execution + log + outbox after approval.
- **Degradation test (L0→L4):** trigger each degradation level; assert correct behavior per agent.
- **Distress short-circuit test:** send distress signal; assert agent bypasses LLM; assert deterministic response <100ms.
- **Forbidden tool denied test (linter rule 182):** agent attempts to call tool not in `allowed_tools`; assert denied with `E_AGENT_TOOL_FORBIDDEN`.
- **Outbox event test:** tool executes; assert outbox event emitted in same transaction; assert event contains `tool_name`, `input`, `output`, `agent_id`, `correlation_id`.
- **Per-agent degradation test:** RG Triage agent at L4 must still respond (distress detection); Support Knowledge agent at L4 may refuse.
