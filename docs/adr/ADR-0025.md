# ADR-0025 — Structured logging (structlog, JSON Lines, redaction, sampling)

## Context

Phase 4 requires structured logging that survives machine parsing at scale, redacts PII and secrets at the logger boundary, and samples noisy endpoints (health, metrics). Python's stdlib logging is unstructured; ad-hoc formatters drift between services. NFR §5 (observability) and audit §1.4 require JSON Lines with required fields.

## Decision

Adopt structlog with JSON Lines output. Required fields per audit §1.4: timestamp (ISO 8601 UTC), level, event, logger, correlation_id, tenant_id (when in request context), request_id, module, line. Redaction at the logger boundary: PII register (docs/architecture/data-classification.md) is the source of truth for PII fields; secret redaction by name + regex (SECRET_KEY, passwords, tokens). 1-in-100 sampling on /health/ and /metrics/. Package: src/noventra/observability/.

## Alternatives

Alternatives: (a) stdlib logging + custom JSON formatter — reinvents structlog; (b) loguru — nice DX but non-standard; (c) vendor-locked (Datadog, NewRelic) — conflicts with ADR-0020 OTel decision. (a) and (b) rejected for non-standardization; (c) rejected for lock-in.

## Consequences

structlog adds ~1ms per log call. Redaction regex must be maintained as new PII fields are added. Sampling config must be tuned per environment. Dev ergonomics: pretty-print in local dev, JSON in production.

## Validation Plan

Phase 4: unit tests for redaction (PII + secret by name and regex); regression test with injected secret. Phase 4: sampling assertion on /health/. Phase 5: load-test logger overhead at 5k req/s.
