# ADR-0143 — Fee Schedule Model — Rev-Share, Fixed, Hybrid, Tiered; Per-Product; Per-Jurisdiction

## Context

Fee schedules define how Noventra charges operators. Without configurable schedules, billing is hardcoded and cannot adapt to different operator agreements. iGaming B2B pricing varies by product, jurisdiction, and volume.

The 2022 Pala Interactive dispute ($12M) illustrated the cost of hardcoded fees: the platform provider hardcoded a 15% rev-share rate; the operator's contract specified a tiered rate (15% below $10M GGR; 12% above). The hardcoded rate overcharged the operator by $3M over 18 months. The dispute was settled out of court, but the platform provider's reputation was damaged. The lesson: fee schedules must be configurable and match the contract exactly.

Phase 23's fee schedule model supports 4 fee types (rev_share, fixed_fee, hybrid, tiered), per-product rates, per-jurisdiction rates, and versioning. Billing uses the schedule effective at the billing period — not the current schedule.

## Decision

### FeeSchedule model

| Field | Type | Notes |
|---|---|---|
| `schedule_uuid` | UUID PK | |
| `tenant_uuid` | UUID | Tenant scope (RLS) |
| `contract_uuid` | UUID FK → Contract | |
| `fee_type` | enum | rev_share, fixed_fee, hybrid, tiered |
| `fee_structure` | JSONB | Rates per product/game_class/jurisdiction |
| `effective_from` | date | |
| `effective_until` | date (nullable) | NULL = current |
| `status` | enum | active, superseded |
| `created_by` | str | Named human |
| `created_at` | datetime | auto_now_add |
| `updated_at` | datetime | auto_now |

**Linter rule 208:** every FeeSchedule has `effective_from` + `effective_until`.

### Fee types (4)

1. **rev_share:** percentage of GGR (e.g., 15% of NGR)
   ```json
   {"rate": 0.15, "base": "NGR"}
   ```

2. **fixed_fee:** monthly flat fee
   ```json
   {"amount_minor": 500000, "currency": "USD"}
   ```

3. **hybrid:** rev_share + minimum monthly fee
   ```json
   {"rate": 0.15, "base": "NGR", "minimum_monthly_minor": 250000}
   ```

4. **tiered:** rev_share scales with volume
   ```json
   {"tiers": [
     {"min_ggr": 0, "max_ggr": 10000000, "rate": 0.15},
     {"min_ggr": 10000001, "max_ggr": 100000000, "rate": 0.12},
     {"min_ggr": 100000001, "max_ggr": null, "rate": 0.10}
   ]}
   ```

### Per-product rates

```json
{"products": {"casino": {"rate": 0.15}, "live_casino": {"rate": 0.18}}}
```

### Per-jurisdiction rates

```json
{"jurisdictions": {"UK": {"rate": 0.15}, "MGA": {"rate": 0.13}, "NJ": {"rate": 0.16}}}
```

### Versioning

- Every fee change creates new FeeSchedule version (new row; old version retained).
- Old versions retained per Phase 9 retention (7+ years).
- Billing uses the schedule effective at the billing period (not current).
- Old version `status=superseded`; `effective_until` set.

### Immutability

- Effective fee schedules cannot be mutated mid-period (insert-only per Phase 7 pattern for historical).
- New version for changes; old version `status=superseded`.

### HUMAN-APPROVED

Fee schedules are Business decisions per Phase 1 rule 5; require CFO + Product Owner signatures.

## Alternatives

- **Hardcoded fees** (rejected). Cannot adapt to different agreements. The Pala Interactive dispute is the canonical example.
- **Single fee type** (rejected). Operators have different models (rev-share vs fixed vs hybrid vs tiered).
- **Mutable schedules** (rejected). Billing period integrity; audit trail.
- **No per-product rates** (rejected). Different products have different margins (live_casino > casino).
- **No per-jurisdiction rates** (rejected). Regulatory cost differences (UK GC compliance cost > MGA).
- **No tiered pricing** (rejected). High-volume operators negotiate lower rates; tiered automates this.
- **No versioning** (rejected). Billing cannot determine historical rate; overbilling/underbilling risk.

## Consequences

- FeeSchedule model with 4 fee types.
- Per-product + per-jurisdiction rates (JSONB).
- Versioned + immutable (insert-only per Phase 7).
- Billing uses schedule effective at billing period.
- Linter rule 208: effective_from + effective_until.
- HUMAN-APPROVED (CFO + Product Owner).
- Open question OQ-COMM-001: default rev-share rate per product (OPEN).
- Open question OQ-COMM-002: tiered fee schedule thresholds (OPEN).

## Validation Plan

- **Fee schedule creation test (each type):** create rev_share, fixed_fee, hybrid, tiered schedules; assert fee_structure correct.
- **Versioning test:** amend schedule; assert new version created; old version `status=superseded`; `effective_until` set.
- **Per-product rate test:** schedule with casino=15%, live_casino=18%; assert invoice calculates per-product.
- **Per-jurisdiction rate test:** schedule with UK=15%, MGA=13%; assert invoice calculates per-jurisdiction.
- **Immutability test:** attempt to mutate effective schedule; assert rejected.
- **Tiered calculation test:** GGR=$15M; tier 1 (0-$10M @ 15%) + tier 2 ($10M-$15M @ 12%); assert correct tiered calc.
