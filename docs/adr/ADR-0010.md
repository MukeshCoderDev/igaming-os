# ADR-0010 — Workflow versioning (immutable definitions)

## Context

In-flight workflow instances must complete against the definition they started under; otherwise, audit and compliance evidence is ambiguous. Mutating a workflow definition while instances are running breaks this invariant.

## Decision

Workflow definitions are immutable and versioned. A new version is a new document; the old version is retained. In-flight instances bind to the version they started under. New instances bind to the latest version by default but may pin to a specific version explicitly.

## Alternatives

Alternatives considered: (a) mutable definitions with in-flight migration — complex and risky; (b) mutable definitions with restart-on-change — disrupts in-flight instances; (c) versioned definitions with mandatory migration — same complexity as (a). (a) and (c) rejected for complexity; (b) rejected for disruption.

## Consequences

Storage cost: every workflow definition version is retained indefinitely. Long-running workflows (days, weeks) pin old definitions, complicating cleanup. UI must surface which version an instance is running.

## Validation Plan

Phase 8: implement versioning; verify that an in-flight instance completes against its original definition after a new version is published. Phase 9: penetration test — attempt to mutate a definition via the admin API. Phase 10: load-test definition lookup at 5k req/s.
