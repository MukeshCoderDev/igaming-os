# ADR-0016 — Feature flags at boundary

## Context

Feature flags evaluated inside domain logic create testability and determinism problems (the same input can produce different outputs depending on flag state). Domain logic must be deterministic (MB-REQ-0025, NFR §7.2).

## Decision

Feature flags are evaluated at the boundary (API gateway or service entry point) and injected into the request context. Domain logic reads the flag value from the context, never from a flag client. This preserves determinism (NFR §7.2).

## Alternatives

Alternatives considered: (a) flag client in domain — breaks determinism; (b) compile-time flags — no runtime toggling; (c) per-tenant configuration instead of flags — too coarse for gradual rollouts. (a) rejected for determinism; (b) rejected for inflexibility; (c) rejected for granularity.

## Consequences

Flag evaluation at the boundary adds latency (~1ms typical). Flag state must be propagated to async contexts (Celery, webhooks) explicitly. Flag misconfiguration can disable critical paths.

## Validation Plan

Phase 1: stub contract. Phase 4: implement; verify that a domain test passes regardless of flag state (determinism test). Phase 8: load-test flag evaluation at 10k req/s.
