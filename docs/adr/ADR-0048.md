# ADR-0048 — Consent schema + jurisdiction-aware fields

## Context

GDPR Art.7 requires demonstrable consent. The consent schema must capture: who consented, to what purpose, via which channel, when, from what IP/user-agent, and the policy version they consented to. Jurisdiction-aware extensions are needed for jurisdictions with stricter consent requirements (e.g., some require double opt-in). The schema must be immutable (revocation creates a new record, not a mutation).

## Decision

Adopt a consent schema: id (UUID), player_id (FK), tenant_id, purpose (closed catalog), channel (matches Phase 8 NotificationChannel), status (granted, revoked, expired, pending), granted_at, revoked_at, policy_version, consent_text_hash (SHA-256 of the consent text presented), ip_address, user_agent, correlation_id, created_at. Jurisdiction-aware extensions: jurisdiction field (from player's jurisdiction), double_opt_in_required (bool), double_opt_in_verified_at. Policy versioning: policy_version field; re-consent trigger on policy change; grace period documented (Q66); refusal → consents withdrawn. HUMAN-APPROVED per linter rule 5 (Legal/Regulatory category).

## Alternatives

Alternatives: (a) single consent flag (boolean) — insufficient for GDPR; (b) consent as a field on Player — no history; (c) consent as an event in the audit log — no queryable index. (a) rejected for GDPR; (b) rejected for no history; (c) rejected for queryability.

## Consequences

Consent schema is complex (12+ fields). Policy versioning requires a policy store (Phase 10+). Jurisdiction-aware extensions are Q1-blocked (can't finalize without jurisdiction list). Double opt-in adds UX friction. Consent text hash requires the consent text to be versioned + stored.

## Validation Plan

Phase 9: Consent model + migration + RLS. Phase 9: consent CRUD API. Phase 9: policy versioning stub. Phase 10: jurisdiction-aware extensions (Q1 unblock). Phase 10: policy store + re-consent trigger.
