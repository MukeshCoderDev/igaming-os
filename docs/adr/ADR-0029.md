# ADR-0029 — Tenant resolution (JWT claim primary + X-Tenant-ID header fallback)

## Context

Every request to a tenant-scoped endpoint must resolve the active tenant before any DB call. The tenant identity comes from the authenticated user's JWT (primary) or an X-Tenant-ID header (fallback for service-to-service or migration scenarios). Missing or malformed tenant identity must fail fast with 400 before any database query is issued, so RLS never sees a NULL tenant_uuid.

## Decision

Adopt TenantResolutionMiddleware in src/noventra/middleware/tenant.py. Resolution order: (1) JWT `tenant_id` claim if present; (2) X-Tenant-ID header if JWT absent or claim missing. Validate format (UUID v4) and existence (cached tenant lookup). On missing/malformed: 400 E_TENANT_MISSING / E_TENANT_INVALID via problem_response(). On valid: set contextvar + SET LOCAL app.tenant_uuid = '<uuid>' on the DB connection. The middleware runs AFTER CorrelationIdMiddleware so log lines carry both correlation_id and tenant_id.

## Alternatives

Alternatives: (a) X-Tenant-ID header only — spoofable; (b) JWT only — breaks service-to-service; (c) tenant in URL path — couples tenancy to routing; (d) tenant from DB lookup of API key — extra DB call per request. (a) rejected for spoofing; (b) rejected for service auth; (c) rejected for coupling; (d) rejected for DB overhead.

## Consequences

Adds one DB round-trip per request for tenant existence check (mitigated by cache). JWT claim must be populated by the identity service (Phase 6+). X-Tenant-ID header fallback is restricted to internal service-to-service (mTLS) in production; the middleware trusts the header only when the request comes from an authenticated internal caller.

## Validation Plan

Phase 5: middleware 400s before DB on missing/malformed (test). Phase 5: cross-tenant read = zero rows; write = 403 E_TENANT_FORBIDDEN (test). Phase 6: JWT claim populated by identity service. Phase 7: load-test tenant lookup cache hit rate.
