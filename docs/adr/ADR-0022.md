# ADR-0022 — Repository skeleton (pyproject, Docker, compose, Makefile, CI)

## Context

Phase 3 begins the first application code. A reproducible, pinned-dependency repository skeleton is required so that every developer and CI runner produces the same environment. The skeleton must encode the constraints from stage-02-handoff.md §3 (module → Django app map, Postgres 16 major version lock, RLS role model, idempotent init scripts).

## Decision

Adopt a src-layout Python project rooted at `src/noventra/`. Pin all dependencies in `pyproject.toml` with a lock file. Provide `docker-compose.yml` with Postgres 16 and Redis 7 (pinned majors) with healthchecks and `depends_on: healthy`. Provide a `Makefile` with targets: bootstrap, migrate, test, lint, typecheck, runserver. Provide `deploy/docker/init/` idempotent SQL scripts. Provide `.env.example`, `.pre-commit-config.yaml`, `CODEOWNERS`, `README.md`.

## Alternatives

Alternatives considered: (a) flat layout (no `src/`) — makes accidental imports easier; (b) pip-tools instead of poetry/uv — more manual; (c) Docker-only dev (no local venv) — slower inner loop; (d) k8s-based dev — over-engineered for Phase 3. (a) rejected for import safety; (b) rejected for manual burden; (c) rejected for inner-loop speed; (d) rejected for complexity.

## Consequences

Developers must learn src-layout conventions. Lock-file maintenance is a recurring task. Docker-compose adds resource overhead on dev machines. Init scripts must be kept idempotent.

## Validation Plan

Phase 3: `make bootstrap && make migrate && make runserver` works end-to-end on a clean machine. CI green on trunk. Phase 4: load-test the dev environment with 10 concurrent developers.
