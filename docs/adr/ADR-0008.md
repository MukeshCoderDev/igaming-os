# ADR-0008 — Idempotency keys on all mutations

## Context

Distributed systems retry. Without idempotency, a retried request can double-charge a customer or double-post a ledger entry. Customer pain (Pain-REQ-0011) confirms this is a top concern for integrators. NFR §2.4 mandates 100% of mutating endpoints idempotent.

## Decision

Every mutating API endpoint accepts an idempotency key (header `Idempotency-Key`). The reliability context (see domain-boundaries.md §6) deduplicates requests within the key's lifetime (default 24h) and returns the original response on replay. See MB-REQ-0013.

## Alternatives

Alternatives considered: (a) client-side deduplication — clients are unreliable; (b) server-side request-hash deduplication — fails when clients legitimately send similar but distinct requests; (c) database unique constraints — protects against duplicate writes but does not return the original response. (a) rejected for unreliability; (b) rejected for false positives; (c) rejected for incomplete semantics.

## Consequences

Idempotency key store must be highly available; loss of the store causes deduplication failure. Key lifetime (24h) bounds the replay window; clients with longer retry intervals must handle 425 Too Early. Storage cost: one row per mutating request.

## Validation Plan

Phase 1: implemented as a stub contract. Phase 3: integration test that submits every mutating endpoint twice with the same key and asserts identical responses. Phase 8: load-test the idempotency store at 10k req/s. Phase 11: verify ledger postings are idempotent end-to-end.
