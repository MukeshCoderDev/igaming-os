# ADR-0107 — Read Models — GGR/NGR Projections, Refresh Strategies, Reconciliation

## Context

Read models are denormalized projections from domain events. They exist because computing GGR/NGR on read (e.g., `SELECT SUM(bets) - SUM(wins) FROM ... WHERE tenant = X AND period = Y`) is too slow for regulatory reports — a quarterly report over 10M events takes minutes, and the regulator portal times out. A materialized view that is refreshed in real time (on every event) or scheduled (hourly/daily) returns in milliseconds.

GGR and NGR are regulator-reportable metrics. They must reconcile against the Phase 11 ledger (the source of financial truth). If the read model says GGR = £1M but the ledger says GGR = £1.1M, the read model is wrong and the operator must investigate before filing the regulatory report. A mismatch that goes undetected is a regulator-reportable defect.

Four read models are required in Phase 17:

1. **GGR (Gross Gaming Revenue):** `sum(bets) - sum(wins)` per (tenant, period, game_class, jurisdiction). Real-time refresh. Materialized view `ggr_mv`.

2. **NGR (Net Gaming Revenue):** `GGR - bonuses_awarded - bonuses_converted - payment_fees - chargeback_fees - other_deductions` per (tenant, period, game_class, jurisdiction). Real-time + scheduled (hourly full rebuild). Materialized view `ngr_mv`.

3. **Player activity:** sessions, bets, deposits, withdrawals per (player, period). Real-time refresh. Materialized view `player_activity_mv`.

4. **Financial summary:** deposits, withdrawals, bonuses awarded, bonuses converted per (tenant, period). Scheduled (daily) refresh. Materialized view `financial_summary_mv`.

The reconciliation job is the safety net. It runs daily (default; OQ-DATA-006). For each read model, it recomputes the metric from the ledger and compares to the read model's stored value. Mismatch → alert + HALT (the read model is not to be trusted until the mismatch is resolved). The HALT is operator-initiated (the alert pages the CFO); it does not auto-shutdown the platform.

### Read models

1. **GGR (Gross Gaming Revenue):**
   - Formula: `sum(bets) - sum(wins)` per (tenant, period, game_class, jurisdiction)
   - Source events: `game.bet.placed`, `game.bet.result`
   - Refresh: real_time (outbox consumer updates `ggr_mv` on every bet)
   - Materialized view: `ggr_mv`

2. **NGR (Net Gaming Revenue):**
   - Formula: `GGR - bonuses_awarded - bonuses_converted - payment_fees - chargeback_fees - other_deductions`
   - Source events: GGR + `bonus.award_created`, `bonus.converted`, `payment.captured`, `dispute.lost`
   - Refresh: real_time + scheduled (hourly full rebuild to catch drift)
   - Materialized view: `ngr_mv`

3. **Player activity:**
   - Sessions, bets, deposits, withdrawals per (player, period)
   - Source events: `player.session.started`, `player.session.ended`, `game.bet.placed`, `payment.captured`, `payment.payout_initiated`
   - Refresh: real_time
   - Materialized view: `player_activity_mv`

4. **Financial summary:**
   - Deposits, withdrawals, bonuses awarded, bonuses converted per (tenant, period)
   - Source events: `payment.captured`, `payment.payout_initiated`, `bonus.award_created`, `bonus.converted`
   - Refresh: scheduled (daily at 03:00 UTC)
   - Materialized view: `financial_summary_mv`

### Refresh strategies

- **real_time:** outbox consumer updates the read model in the same DB transaction as the event. Lowest lag; highest write amplification. Used for GGR, NGR, player_activity.
- **scheduled:** Celery job rebuilds the materialized view on a schedule (hourly/daily). Higher lag; lower write amplification. Used for financial_summary.
- **on_demand:** admin trigger (for corrections after a bug fix). Not used in normal operation.

### Tenant scoping

Every read model is tenant-scoped (RLS per Phase 5). The materialized views include `tenant_uuid` in their PK; cross-tenant queries return zero rows. Linter rule 143 enforces this — every read model migration must include `tenant_uuid` in the materialized view's PK and RLS policy.

### Reconciliation

- Daily reconciliation job (Celery beat, 04:00 UTC): for each read model, recompute the metric from the Phase 11 ledger and compare to the read model's stored value.
- Mismatch (delta > £0.01 or 0.01%, whichever is greater) → alert + HALT.
  - Alert: PagerDuty to CFO + External Auditor.
  - HALT: the read model is marked `stale` in the dashboard; regulatory report generation refuses to use a stale read model.
- Audit event: `reporting.reconciliation.completed` (match) or `reporting.reconciliation.mismatch` (HALT).
- The reconciliation pattern reuses Phase 11's `ReconciliationLog` model (extended with a `read_model_name` field).

## Alternatives

- **Compute on read (no read models)** (rejected). Slow for large datasets; regulator reports would take minutes; portal timeouts.
- **No reconciliation** (rejected). Financial integrity requires verification. A stale read model used for a regulatory report is regulator-reportable.
- **Reconciliation only on demand** (rejected). Operators forget; staleness goes undetected for weeks.
- **Reconciliation every hour** (rejected). Overkill for daily-scheduled read models; acceptable overhead for real-time read models but the daily job catches drift in both. Hourly reconciliation is a future option if drift becomes a problem.
- **No HALT on mismatch** (rejected). Without HALT, the operator files an inaccurate regulatory report. HALT forces investigation before submission.
- **Single read model for GGR + NGR** (rejected). GGR is needed for some reports; NGR for others. Coupling them complicates refresh (GGR is real-time; NGR has scheduled rebuild). Separate read models are simpler.

## Consequences

- 4 read models with materialized views. Migration creates 4 materialized views + RLS + refresh triggers.
- Real-time + scheduled refresh. Real-time consumers update on every event; scheduled Celery jobs rebuild hourly/daily.
- Daily reconciliation job. Failure is alertable; mismatch triggers HALT.
- Linter rule 143: every read model tenant-scoped (RLS).
- Linter rule 144: GGR/NGR read models reconcile against Phase 11 ledger (reconciliation job exists).
- The Q5-blocked time-series DB decision (OQ-DATA-001) does not affect read models — they are Postgres materialized views, not time-series.
- Open question OQ-DATA-006: reconciliation cadence default is daily (recommended); may be tightened to hourly for high-volume tenants.

## Validation Plan

- **GGR calculation test:** place 10 bets, 5 wins; assert `ggr_mv` matches `sum(bets) - sum(wins)`.
- **NGR calculation test:** GGR + 2 bonuses awarded + 1 bonus converted + 1 payment fee; assert `ngr_mv` matches `GGR - bonuses - fees`.
- **Reconciliation mismatch HALT test:** tamper with `ggr_mv` (set value to £999); run reconciliation; assert HALT (read model marked stale; alert fires).
- **Reconciliation match test:** normal flow; run reconciliation; assert `reporting.reconciliation.completed` audit event.
- **Tenant scoping test:** tenant A's GGR query returns only tenant A's rows; cross-tenant query returns zero rows.
- **Real-time refresh test:** place a bet; assert `ggr_mv` updates within 1 second.
- **Scheduled refresh test:** trigger the hourly NGR rebuild; assert `ngr_mv` matches a fresh computation.
- **Linter rule 143 test:** grep for read model migrations; assert each has `tenant_uuid` in PK + RLS policy.
- **Linter rule 144 test:** grep for reconciliation Celery task; assert it exists and runs daily.
