# ADR-0106 — Consumer Registry, Idempotency, Lag Monitoring & DLQ

## Context

Phase 8 established the inbox pattern for idempotency: every consumer has an inbox table keyed by `(message_id, consumer_id)`; same event delivered twice produces a single side effect. Phase 17 extends this with three additional subsystems: a consumer registry, lag monitoring, and DLQ (dead-letter queue) integration.

The threat model is operational, not regulatory, but the consequences are regulator-adjacent. If a consumer falls behind (lag grows), the GGR read model becomes stale. A regulator report generated from a stale read model is inaccurate — and the operator may not notice until the next reconciliation cycle (daily). If a consumer crashes mid-processing and the event is not redelivered, the read model is permanently wrong until someone manually replays. If a poison message (un-deserializable payload) blocks a consumer, the entire pipeline stalls.

Three subsystems address these:

1. **Consumer registry.** Every consumer is registered with its schema, owner, and status. Unregistered consumers are a defect (linter rule 139). The registry is the operational view of "what is consuming what."

2. **Lag monitoring.** Track `last_processed_message_id` per consumer. Alert if lag exceeds threshold (default: 1000 messages OR 60 seconds, whichever first). The dashboard shows lag per consumer; on-call gets paged if lag crosses the threshold.

3. **DLQ.** Poison messages (un-deserializable, schema-invalid, or processing-failure-after-N-retries) land in the DLQ. The DLQ is enriched with the original payload, failure reason, retry count, and timestamps. Replay is a manual command (`manage.py replay_dlq`) that re-drives the message through the consumer; idempotency (Phase 8 inbox) makes this safe.

### Idempotency (Phase 8 inbox pattern — extended)

- Every consumer has an inbox table: `(message_id, consumer_id)` composite PK.
- `ON CONFLICT DO NOTHING` — duplicate insert is a no-op.
- Insert AFTER processing (same DB transaction as the side effect).
- Same event delivered twice → single side effect (exactly-once-effect semantics).
- The inbox table is per-consumer (not shared) to allow independent lag tracking and DLQ routing.

### Consumer lag monitoring

- Track `last_processed_message_id` per consumer (updated on every successful processing).
- Track `last_processed_at` per consumer (wall-clock time of last successful processing).
- A Celery beat task (`check_consumer_lag`) runs every 30 seconds. For each active consumer:
  - Query the stream's latest message ID.
  - Compute lag = (latest message ID) - (last_processed_message_id).
  - If lag > 1000 messages OR (now - last_processed_at) > 60 seconds → alert.
- Dashboard (`/admin/consumers/`) shows lag per consumer in real time.
- On-call rotation receives PagerDuty alert on threshold breach.

### DLQ (Phase 8 pattern — extended)

- Poison messages land in DLQ after N retries (default N=3).
- DLQ message enrichment:
  - Original payload (raw bytes)
  - Failure reason (e.g., `E_SCHEMA_VALIDATION_FAILED`, `E_PROCESSING_EXCEPTION`, `E_DESERIALIZATION_FAILED`)
  - Retry count
  - First-attempt timestamp
  - Last-attempt timestamp
  - Consumer name
  - Stream name
- Alert on DLQ arrival (Slack `#ops-alerts` + PagerDuty if rate > 10/hour).
- Replay command: `manage.py replay_dlq --consumer <name> --from <ts> --to <ts>`. Idempotent (inbox pattern); safe to replay multiple times.

### Replay

- Consumers can replay events from the stream (idempotent; safe due to inbox).
- `manage.py replay_events --consumer <name> --from <ts> --to <ts>` re-drives events through the consumer.
- Use case: read model rebuild after a bug fix; backfill after a new consumer is registered.

### Linter rule 140

Every consumer has an inbox table. Linter rule 140 verifies:
- The consumer class defines `INBOX_TABLE` attribute.
- The inbox table migration exists.
- The consumer's `process()` method inserts into the inbox in the same transaction as the side effect.

## Alternatives

- **At-most-once (no inbox)** (rejected). Events can be lost on consumer crash. Financial integrity requires at-least-once + idempotency.
- **Exactly-once (distributed transactions)** (rejected). Expensive (2PC across Postgres + Redis); operationally fragile. At-least-once + idempotency is the industry standard and produces exactly-once-effect semantics.
- **Shared inbox table** (rejected). Couples consumers; a single consumer's lag affects all. Per-consumer inbox tables allow independent monitoring and DLQ routing.
- **No lag monitoring** (rejected). Silent staleness; regulator report generated from stale read model is inaccurate.
- **No DLQ** (rejected). Poison messages block the consumer indefinitely; manual intervention required.
- **N=1 retry** (rejected). Transient failures (network blips, brief DB contention) would land in DLQ unnecessarily. N=3 is the industry default.
- **N=10+ retries** (rejected). Poison messages consume resources for too long before DLQ. N=3 balances false-positives and resource waste.

## Consequences

- Per-consumer inbox tables. Migration creates one table per consumer (4 consumers in Phase 17: GGR, NGR, player_activity, financial_summary).
- Lag monitoring Celery beat task (`check_consumer_lag`) runs every 30s. Failure is alertable.
- DLQ table per pipeline (domain DLQ + telemetry DLQ; bifurcated truth per ADR-0104).
- Replay commands in `manage.py` for DLQ + event replay.
- Dashboard endpoint (`/admin/consumers/`) shows consumer status + lag.
- Open question OQ-DATA-005: lag threshold default is 1000 messages OR 60 seconds (recommended); may be tightened per consumer in production config.

## Validation Plan

- **Idempotency test:** deliver the same event 10 times to a consumer; assert exactly one side effect (one inbox row, one read model update).
- **Lag monitoring test:** stop a consumer; wait 70 seconds; assert alert fires (60s threshold breached).
- **DLQ replay test:** inject a poison message; assert it lands in DLQ after 3 retries; run `replay_dlq`; assert it processes successfully (after fix) and the inbox has exactly one row.
- **Consumer crash recovery test:** crash a consumer mid-processing; assert the event is redelivered (at-least-once); assert the inbox prevents double side effect.
- **Linter rule 140 test:** grep for consumer classes; assert each has `INBOX_TABLE` attribute and the migration exists.
- **Linter rule 139 test:** grep for consumer classes; assert each is registered in `EventConsumer` table seed.
