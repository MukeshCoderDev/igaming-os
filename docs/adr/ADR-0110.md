# ADR-0110 — TM Rules Engine — Rule Evaluation & Per-Jurisdiction Thresholds

## Context

Transaction Monitoring (TM) rules are regulator-mandated (FATF Recommendation 20). Every regulated financial institution — including iGaming operators — must implement automated TM that detects suspicious patterns and generates alerts for compliance review. The rules must be threshold-based + velocity + structural + behavioral; per-jurisdiction thresholds are configurable because each jurisdiction sets its own CTR (Currency Transaction Report) threshold, its own velocity limits, and its own structuring definitions.

The 2020 Capital One AML fine ($390M) was partly a TM-rule failure: the bank's rules did not detect structuring because the threshold was set too high and the velocity window was too narrow. The regulator found that the rules existed on paper but were misconfigured in production. The lesson: TM rules must be configurable, versioned, and auditable — every rule change must be traceable to a named human approver.

Phase 18's TM engine builds on:
- Phase 11 ledger (transaction data for evaluation)
- Phase 12 payments (deposit/withdrawal patterns)
- Phase 13 bonuses (bonus abuse patterns)
- Phase 15/16 game rounds (bet patterns)
- Phase 14 JurisdictionPort (per-jurisdiction thresholds)
- Phase 17 bifurcated truth (domain events only; telemetry never-truth)

### Rule types (5)

1. **threshold** — single-event threshold. Example: deposit > $10,000 in 24h (CTR threshold per jurisdiction). Generates signal on the triggering event.

2. **velocity** — rate-based threshold. Example: >5 deposits in 24h; >100 bets in 10 minutes; >3 withdrawals in 1h. Generates signal when velocity exceeds threshold within the time window.

3. **structural** — pattern-based detection. Example: structuring (multiple deposits just below CTR threshold totaling > CTR threshold in 24h); smurfing (multiple small deposits from multiple sources). Generates signal when the structural pattern matches.

4. **behavioral** — anomalous behavior detection. Example: unusual bet patterns (large bets after small deposits); chip dumping (balance transfer via game-round patterns). Generates signal when behavioral anomaly detected.

5. **jurisdictional** — high-risk jurisdiction transactions. Example: transactions with FATF grey/black list jurisdictions. Generates signal when jurisdiction match detected (sourced from Phase 14 JurisdictionPort).

### Rule evaluation

- **Scheduled job:** Celery beat task `evaluate_tm_rules` runs every 5 minutes. Scans transactions from the last 5 minutes (configurable window). Evaluates each active TM rule. Generates RiskSignal if rule matches.

- **Real-time:** Phase 8 outbox consumer. On event publish (payment.captured, game.bet.placed, etc.), evaluates real-time rules (high-severity single-event: sanctions match, PEP match, threshold breach). Generates RiskSignal immediately.

- **Rule actions (configurable per rule):**
  - `generate_signal` — create RiskSignal (default)
  - `escalate_to_case` — auto-create RiskCase (for critical severity)
  - `auto_freeze` — freeze player account (Phase 14 kill-switch pattern; requires dual control per ADR-0113)
  - `alert_compliance` — alert Compliance Officer via Slack/PagerDuty

### Per-jurisdiction thresholds

Per-jurisdiction rules: JurisdictionPort integration (Phase 14). Thresholds configurable per jurisdiction (Q1-blocked for specific values; OQ-RISK-003). Stub returns default thresholds:

- CTR threshold: $10,000 (US default; UK £6,500; EU €10,000)
- Velocity deposit: 5 per 24h (default; configurable per jurisdiction)
- Velocity withdrawal: 3 per 24h (default)
- Structuring detection: 3+ deposits below CTR threshold totaling > CTR threshold in 24h

### Risk scoring

Each signal contributes `risk_score_weight` to the player's cumulative risk score. The cumulative score is stored on the player's risk profile (computed on every signal generation):

- low: cumulative score 1-10
- medium: cumulative score 11-25
- high: cumulative score 26-50
- critical: cumulative score 51+ → auto-escalate to RiskCase (ADR-0112)

### Rule versioning + audit

- Every rule change creates a NEW version (insert-only per Phase 7 pattern).
- Old versions retained indefinitely (audit trail).
- `approved_by` + `approved_at` on every version (named human; CODEOWNERS).
- Rule changes emit audit event (Phase 7): `tm.rule.created`, `tm.rule.updated`, `tm.rule.paused`, `tm.rule.deprecated`.

## Alternatives

- **Manual TM** (rejected). Regulator mandates automated monitoring (FATF Rec 20). Manual review cannot scale.
- **ML-based TM** (rejected initially). Explainability required; deferred to Phase 19+ or vendor (Q5-blocked; OQ-RISK-001).
- **Single threshold (no per-jurisdiction)** (rejected). Each jurisdiction sets its own CTR threshold; a single global threshold would either over-report (low-threshold jurisdictions) or under-report (high-threshold jurisdictions).
- **No rule versioning** (rejected). Rule changes must be auditable; the Capital One fine showed that untracked rule changes allow misconfiguration to go undetected.
- **Real-time only (no scheduled)** (rejected). Velocity and structuring require time windows; real-time evaluation of every event against every rule is computationally infeasible.
- **Scheduled only (no real-time)** (rejected). Sanctions match must trigger within seconds.

## Consequences

- TMRule model with versioning + audit. Insert-only trigger per Phase 7 pattern.
- 5-minute scheduled Celery job + real-time outbox consumer.
- Per-jurisdiction configuration (Q1-blocked; stub returns defaults).
- Risk scoring: cumulative score per player; critical → auto-escalate to RiskCase.
- 4 rule actions: generate_signal, escalate_to_case, auto_freeze, alert_compliance.
- Linter rule 148: TMRule model exists with 5 rule types.
- Open question OQ-RISK-003: CTR threshold per jurisdiction (Q1-blocked).
- Open question OQ-RISK-006: risk scoring weights (configurable per tenant; OPEN).

## Validation Plan

- **Rule evaluation tests (each of 5 types):** for each rule type, construct a triggering scenario; assert rule evaluates correctly.
- **Threshold test:** deposit $10,001 in 24h; assert threshold rule generates signal.
- **Velocity test:** 6 deposits in 24h (threshold 5); assert velocity rule generates signal.
- **Structuring detection test:** 3 × $9,500 deposits in 24h (CTR $10,000); assert structuring rule generates signal.
- **Per-jurisdiction threshold test:** UK player with £6,500 deposit; assert UK threshold rule triggers (not US $10,000).
- **Risk scoring test:** generate 3 medium signals; assert cumulative score = sum of weights; assert severity escalation.
- **Rule versioning test:** modify a rule; assert new version created; old version retained; `approved_by` recorded.
- **Linter rule 148 test:** grep for TMRule model; assert 5 rule types in enum.
