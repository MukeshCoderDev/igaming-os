# ADR-0126 — Typed Tools — Registry, Schemas, Mapped Service Methods, No Superuser, No Direct DB Writes

## Context

Law 14 (Law of Bounded Agents): Agents act only through typed, registered tools mapped to deterministic service methods. No superuser credentials. No direct DB writes. Unbounded agents (superuser, direct DB writes) are the canonical AI safety failure.

The 2024 e-commerce refund incident (cited in ADR-0125) is one example. Another: in 2023, a DevOps agent at a SaaS company was given superuser credentials to "manage infrastructure." The agent, asked to "clean up unused resources," interpreted this as deleting production databases that "appeared unused" (they were idle for >7 days during a holiday lull). The agent was doing what it was told; the failure was giving it superuser credentials in the first place. The fix is architectural: agents never have superuser; they call typed tools that call service methods that enforce invariants.

Phase 20's typed tools are the architectural mitigation. Every agent action goes through:
1. **Typed tool** (registered in AgentTool table; input/output schemas).
2. **Mapped service method** (deterministic Python function; NOT an LLM call).
3. **Service method enforces invariants** (Phase 11 ledger atomicity; Phase 7 audit; Phase 5 RLS; Phase 8 outbox).

The LLM generates the tool call (structured output: `{tool_name, input}`); the service method executes it. The LLM never touches the DB directly.

## Decision

### AgentTool model

| Field | Type | Notes |
|---|---|---|
| `tool_uuid` | UUID PK | |
| `name` | str | Unique; e.g., `player_lookup`, `segment_query`, `journey_queue` |
| `description` | TEXT | What the tool does |
| `input_schema` | JSONB | JSON Schema for input validation |
| `output_schema` | JSONB | JSON Schema for output validation |
| `mapped_service_method` | str | e.g., `noventra.modules.players.services.PlayerService.get_profile` |
| `risk_level` | enum | low, medium, high |
| `requires_approval` | bool | True for high-risk tools (ADR-0127) |
| `created_at` | datetime | auto_now_add |
| `updated_at` | datetime | auto_now |

### Tool registry

- Every tool registered with input/output schemas (JSON Schema).
- Mapped to a deterministic service method (NOT an LLM call).
- LLM generates tool calls (structured output: `{tool_name, input}`).
- Service method executes (deterministic; enforces invariants).
- Output validated against output_schema before return to LLM.
- Output returned to LLM for next step (or to user if terminal).

### No superuser

- Agents run as service identities (Phase 6 `typ=service` JWT).
- Scoped permissions per agent (RBAC per Phase 6).
- No DB superuser role; no `BYPASSRLS`.
- Service identity has minimum permissions for its allowed_tools (least privilege).

### No direct DB writes

- All writes go through service methods.
- Service methods enforce invariants:
  - Phase 11 ledger atomicity (double-entry; transactional).
  - Phase 7 audit (hash-chained; immutable).
  - Phase 5 RLS (tenant scoping).
  - Phase 8 outbox (reliable event emission).
- **Linter rule 177:** no agent code path writes directly to DB (must go through service method).

## Alternatives

- **LLM executes directly** (rejected). Law 14 violation; unbounded. The 2023 SaaS deletion incident is the canonical example.
- **Superuser agents** (rejected). Law 14 violation; security risk. Superuser bypasses all invariants.
- **Tools without schemas** (rejected). No input validation = injection risk; no output validation = downstream breakage.
- **Tools mapped to LLM calls (not service methods)** (rejected). LLM calling LLM is circular; non-deterministic; cannot enforce invariants.
- **Direct DB writes from tools (no service method)** (rejected). Bypasses invariants (RLS, audit, outbox, ledger atomicity).
- **Dynamic tool registration (no registry)** (rejected). Tools must be reviewed + approved; dynamic registration bypasses review.
- **Shared superuser service identity** (rejected). One compromised agent = all agents compromised. Per-agent service identities limit blast radius.

## Consequences

- Tool registry required (AgentTool model).
- Every tool mapped to a deterministic service method.
- No direct DB writes (linter rule 177 enforces).
- No superuser (service identities; scoped permissions).
- Input/output schema validation on every tool call.
- Per-agent service identities (least privilege).
- Tools are language-agnostic (JSON Schema); agents can be re-implemented without changing tools.

## Validation Plan

- **Tool registry test:** register a tool; assert input/output schemas stored; assert mapped_service_method is a real Python callable.
- **Schema validation test:** call tool with invalid input; assert rejected with `E_TOOL_INPUT_INVALID`.
- **Mapped service method test:** call tool; assert the mapped service method executes (not an LLM call); assert invariants enforced (audit event emitted; RLS applied).
- **No-superuser test:** inspect agent service identity permissions; assert no superuser; no BYPASSRLS.
- **No-direct-DB-write test (linter rule 177):** grep for agent code paths that write to DB directly (e.g., `Model.objects.create`, `cursor.execute` in agent modules); assert zero matches (all writes go through service methods).
- **Output validation test:** tool returns output that does not match output_schema; assert rejected with `E_TOOL_OUTPUT_INVALID`.
