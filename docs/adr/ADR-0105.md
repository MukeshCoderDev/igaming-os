# ADR-0105 — Schema Registry — Versioning, Compatibility, Validation

## Context

Events have schemas. When schemas change, old consumers must still process old events. Without a registry, schema drift breaks consumers silently — a producer adds a new field, an old consumer ignores it (fine), but a producer removes a required field and an old consumer crashes on every event (not fine). The silent failure mode is worse: a producer changes a field type from `int` to `string`, the old consumer's deserialization silently coerces or drops the value, and downstream state corrupts over hours before anyone notices.

The iGaming domain is particularly sensitive to schema drift because the same event feeds both operational consumers (real-time dashboards) and financial consumers (GGR/NGR read models that reconcile against the ledger). A schema drift that corrupts the GGR read model is a regulator-reportable defect — the operator files an inaccurate GGR report and the regulator fines them on audit.

Three properties are required:

1. **Versioning.** Every schema change creates a new version. Old versions are retained indefinitely (retention 7+ years per regulator). Consumers declare which version they consume; the registry tracks this.

2. **Compatibility enforcement.** Schema changes are classified by compatibility mode: `backward` (new schema can read old data — adding optional fields), `forward` (old schema can read new data — removing optional fields), `full` (both), `none` (breaking change requiring consumer migration). The registry rejects incompatible changes by default; breaking changes require an explicit migration plan.

3. **Validation.** Every event published is validated against its schema before it enters the outbox. Invalid events are rejected (DLQ per Phase 8). This catches producer bugs at publish time, not at consumer time.

### Versioning

Every schema change creates a new row. The `(name, version)` pair is unique. Old versions are retained indefinitely. A schema in `published` status cannot be mutated; corrections require a new version. A schema in `deprecated` status is retained for audit but new consumers cannot register against it.

### Compatibility enforcement

- **backward** (default; recommended): new schema can read old data. Adding optional fields is backward-compatible. Removing required fields is NOT backward-compatible.
- **forward**: old schema can read new data. Removing optional fields is forward-compatible. Adding required fields is NOT forward-compatible.
- **full**: both backward and forward. Only changes that preserve both directions are allowed.
- **none**: breaking change. Requires a consumer migration plan (documented in the ADR that approves the schema change). New version must be `2.0.0` (major bump).

The registry's `validate_compatibility(new_schema, old_schema, mode)` function returns True/False. Incompatible changes are rejected at registration time.

### Consumer registration

Every consumer declares `(schema_name, schema_version)` in its registration (ADR-0106). Linter rule 139 enforces this. A consumer registered against version `1.0.0` will process events tagged `1.0.0` and (if backward-compatible) events tagged `1.1.0`. It will NOT process events tagged `2.0.0` (major version change).

### Validation

Every event published is validated against its schema before it enters the outbox. The publisher computes the schema hash, validates the payload against the JSON Schema, and on failure routes to the DLQ with reason `E_SCHEMA_VALIDATION_FAILED`. The outbox never contains an invalid event.

### Drift detection

Linter rule 144 (Phase 17): every committed event fixture (in tests) matches its declared schema. This catches producer test drift. CI runs the schema validator on every committed event fixture.

## Alternatives

- **No registry** (rejected). Schema drift breaks consumers silently. The 2023 fine scenario (ADR-0104) is the canonical example.
- **External registry (Confluent Schema Registry)** (rejected initially). Adds a dependency and operational surface. Build in-house for control; the schema registry is ~500 LOC and central to financial integrity, so ownership matters. May revisit in Phase 22 if scale demands.
- **Single schema version, breaking changes require consumer migration** (rejected). No backward compatibility = every consumer breaks on every change. Unsustainable.
- **Schema in code (Pydantic/dataclasses)** (rejected). Schemas in code are not visible to non-Python consumers (e.g., a regulatory report generator written in Go). A registry with a JSON Schema definition is language-agnostic.
- **No validation at publish time** (rejected). Catches producer bugs at consumer time — too late. The DLQ fills with poison messages and the operator's GGR read model falls behind.

## Consequences

- New `event_schema` table + RLS + insert-only trigger (per Phase 7 pattern; corrections require a new version, never mutation).
- Every consumer registered with `(schema_name, schema_version)`. Linter rule 139 enforces.
- Every event validated before publish. Linter rule 138 enforces.
- Schema migration plans documented in ADRs for breaking changes.
- The registry is the single source of truth for event shape. Producers and consumers reference it; neither hardcodes schemas.
- Open question OQ-DATA-004: default compatibility mode is `backward` (recommended); may be tightened to `full` for financial events in a future ADR.

## Validation Plan

- **Schema versioning test:** register `game.bet.placed` v1.0.0; register v1.1.0 (backward-compatible); assert both versions exist; assert v1.0.0 consumers can process v1.1.0 events.
- **Compatibility enforcement test:** attempt to register v2.0.0 with a removed required field; assert rejected (mode=backward); assert accepted if mode=none + major version bump.
- **Consumer registration test:** register a consumer against v1.0.0; assert it processes v1.0.0 and v1.1.0 events; assert it rejects v2.0.0 events.
- **Drift detection test:** commit a test event fixture that does not match its declared schema; CI must fail (linter rule 144).
- **Validation at publish test:** publish an event with a missing required field; assert it routes to DLQ with `E_SCHEMA_VALIDATION_FAILED`; assert the outbox is unchanged.
- **Linter rule 137 test:** grep for event classes; assert each has a registered schema.
- **Linter rule 138 test:** grep for outbox publish calls; assert each validates against schema first.
