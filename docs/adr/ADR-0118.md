# ADR-0118 — Prefiltered Hybrid Retrieval (Law 2; pgvector + FTS)

## Context

Law 2 (Law of Prefiltered Isolation): vector search, stream consumer groups, cache keys, exports, logs, and agent context filter by `tenant_id` INSIDE the scan/query. Post-retrieval filtering is a security violation.

The threat is cross-tenant data leakage. In 2024, a SaaS RAG platform was found to leak documents across tenants because the retrieval query did `SELECT * FROM chunks ORDER BY embedding <=> query LIMIT 10` and then filtered by `tenant_id` in application code. A bug in the application filter (a missed `if` statement) caused tenant A's query to return tenant B's chunks. The fix was post-retrieval filtering, which the vendor shipped as a patch — but the architecture was fundamentally wrong. The correct architecture is prefiltered retrieval: the `WHERE tenant_id = X` clause is inside the SQL query, so the database never returns cross-tenant rows even if the application filter is buggy.

Errata E3 restored the prefiltered query pattern after a temporary regression. Phase 19 mandates prefiltered retrieval at the linter level (rule 167: no code path retrieves chunks without `tenant_id` + `jurisdiction` + `language` + `lifecycle` filter in the query).

Hybrid retrieval (pgvector + FTS) is required because semantic similarity alone misses exact keyword matches (a player searching "RG23" will not find a document titled "Responsible Gaming Form 23" via embedding similarity alone). FTS catches exact matches; pgvector catches semantic matches. The hybrid score is a weighted combination.

## Decision

### Hybrid retrieval: pgvector (semantic) + FTS (keyword)

**Prefiltered query (errata E3):**

```sql
SELECT id, content, metadata,
       (embedding <=> :query_embedding) AS semantic_distance,
       ts_rank(content_tsv, :query_tsquery) AS fts_rank
FROM knowledge_chunk
WHERE tenant_id = :tenant_id
  AND metadata->>'jurisdiction' = :jurisdiction
  AND metadata->>'language' = :language
  AND lifecycle = 'active'
  AND embedding <=> :query_embedding < :threshold
ORDER BY
  (0.7 * (1 - (embedding <=> :query_embedding))) +
  (0.3 * ts_rank(content_tsv, :query_tsquery)) DESC
LIMIT :k
```

**Post-retrieval filtering is a SECURITY VIOLATION (Law 2).**

- Linter rule 165: every RAG query prefiltered by `tenant_id`.
- Linter rule 166: every RAG query prefiltered by `jurisdiction`.
- Linter rule 167: no post-retrieval filtering (linter grep for `SELECT` without `WHERE tenant_id` in retrieval code).

### Vector index

- Per-tenant partial index OR filtered index (pgvector supports both).
- Recommended: filtered index for scalability (`CREATE INDEX ON knowledge_chunk USING ivfflat (embedding vector_cosine_ops) WHERE tenant_id = '...' AND lifecycle = 'active'`).
- For multi-tenant scale: partition `knowledge_chunk` by `tenant_id` (Phase 22+).

### FTS

- PostgreSQL `tsvector` column on `knowledge_chunk.content`.
- Prefiltered by the same `WHERE` clause (tenant_id + jurisdiction + language + lifecycle).
- GIN index on the tsvector column.

### Hybrid scoring

- Weighted combination: `0.7 * semantic_similarity + 0.3 * fts_rank` (configurable per query type).
- Semantic similarity: `1 - cosine_distance` (normalized to [0, 1]).
- FTS rank: `ts_rank` (normalized to [0, 1] via division by max rank in result set).
- Configurable weights per query type (chat: 0.7/0.3; FAQ: 0.3/0.7; agent: 0.5/0.5).

## Alternatives

- **Post-retrieval filtering** (rejected). Law 2 security violation. The 2024 SaaS incident is the canonical example.
- **Semantic-only retrieval (no FTS)** (rejected). Misses exact keyword matches; "RG23" query fails to find "Responsible Gaming Form 23" document.
- **FTS-only retrieval (no semantic)** (rejected). Misses semantic matches; "how do I exclude myself?" query fails to find "self-exclusion process" document.
- **Application-layer filtering (in Python)** (rejected). Same as post-retrieval filtering; buggy filter = cross-tenant leak.
- **Separate indexes per tenant (no filtered index)** (rejected). Index explosion; operational overhead. Filtered index is pgvector's recommended pattern.
- **Equal weights (0.5/0.5)** (rejected). Semantic matches are generally more relevant than keyword matches for natural-language queries; 0.7/0.3 is the industry default.

## Consequences

- Prefiltered query mandatory (Law 2).
- Linter rules 165, 166, 167 enforce prefiltering at code level.
- Per-tenant filtered pgvector index.
- FTS tsvector column + GIN index.
- Hybrid scoring (configurable weights per query type).
- Cross-tenant leak test: tenant A query returns zero tenant B rows (negative test).
- Open question: hybrid scoring weights may need per-tenant tuning in production.

## Validation Plan

- **Prefilter test:** query with `tenant_id = A`; assert all returned rows have `tenant_id = A`.
- **Post-retrieval filtering rejection test (linter rule 167):** grep for retrieval code; assert each has `WHERE tenant_id` in the SQL query; assert no application-layer filtering.
- **Cross-tenant leak test:** tenant A query; assert zero rows from tenant B (negative test).
- **Hybrid scoring test:** query that matches semantically + by keyword; assert both contribute to score; assert ranking correct.
- **Jurisdiction filter test:** query with `jurisdiction = 'uk_gc'`; assert all returned rows have `jurisdiction = 'uk_gc'`.
- **Language filter test:** query with `language = 'en'`; assert all returned rows have `language = 'en'`.
- **Lifecycle filter test:** revoke a chunk; query; assert revoked chunk not returned (Law 10 + Law 2).
- **Linter rule 165 test:** grep for retrieval queries; assert each has `tenant_id` in WHERE.
- **Linter rule 166 test:** grep for retrieval queries; assert each has `jurisdiction` in WHERE.
- **Linter rule 167 test:** grep for retrieval code; assert no application-layer tenant filtering (all filtering in SQL).
