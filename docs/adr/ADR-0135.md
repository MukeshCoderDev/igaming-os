# ADR-0135 — DSAR Drill — Verify → Export → Shred (Errata E1; SE-Survives-Erasure)

## Context

Blueprint errata E1: "DSAR order is fixed: (1) verify requester identity with KYC-grade check; (2) satisfy right of access by generating export pack; (3) only then destroy per-subject KMS key. Erasure never precedes export; export never skips verification."

Phase 9 specified the DSAR flow; Phase 21 implements the operational drill. The order is fixed because:
- **Erasure before export** destroys the data the player has a right to access (GDPR Art 15). The player cannot verify what was held; the operator cannot prove compliance.
- **Export without verification** risks identity fraud (attacker impersonates player; obtains their data; erases their account).

The SE-survives-erasure pattern (Phase 14 ADR-0085) is the second critical constraint: when a player's data is erased, the self-exclusion registry must survive (via HMAC pseudonymization) so the excluded player cannot re-register. Without this, a player could self-exclude, request erasure, then re-register with the same identity document — defeating the self-exclusion.

The 2023 GDPR enforcement against a gaming operator (€4M fine) illustrated both failures: the operator erased a player's data before generating the export (violating E1); the SE registry was also erased, allowing the self-excluded player to re-register 3 weeks later. The regulator called it "systemic privacy + player protection failure."

### Operational order (errata E1 — fixed, cannot be reordered)

1. **verify:** KYC-grade identity check (Phase 10 KYC integration); `status=verified`.
2. **export:** generate export pack (all player data from all modules); `status=exported`.
3. **shred:** destroy per-subject KMS key (Phase 9 crypto-shredding; blueprint §8.1); `status=shredded`.

**Linter rule 186:** DSAR status transitions follow E1 order (pending → verified → exported → shredded; no skipping). Any attempt to skip (e.g., pending → shredded) is rejected with `E_DSAR_ORDER_VIOLATION`.

### SE-survives-erasure (Phase 14 ADR-0085)

- SE registry retained via HMAC pseudonymization (Phase 14 pattern).
- On shred:
  - SE record retained with `pseudonymized_identity` (HMAC of identity document).
  - Original `player_uuid` NULLed (player data destroyed).
  - SE record's `player_uuid` set to NULL; `pseudonymized_identity` retained.
- On re-registration:
  - `check_pseudonymized_identity(identity_document)` computes HMAC; queries SE registry.
  - If HMAC matches an active SE → reject re-registration with `E_SELF_EXCLUDED`.
- **Linter rule 187:** shred operation preserves SE registry (HMAC pseudonymization).

### DSAR drill (acceptance criterion)

End-to-end test (must pass for Phase 21 gate):
1. Create DSAR request (`status=pending`).
2. Verify identity (KYC-grade; `status=verified`).
3. Generate export pack (all modules; `status=exported`).
4. Verify export pack contains all data classes.
5. Shred KMS key (`status=shredded`).
6. Verify SE registry survives (HMAC pseudonymized identity retained).
7. Attempt re-registration with same identity document.
8. Verify re-registration blocked (HMAC match; `E_SELF_EXCLUDED`).

### Negative tests

- **Erasure before export** → rejected (E1 violation; linter rule 186).
- **Export without verification** → rejected (E1 violation; linter rule 186).
- **Shred without preserving SE** → rejected (linter rule 187).
- **DSAR exceeding statutory window** → alert (linter rule 188).

### Statutory window

- 30 days (GDPR Art 12(3); configurable per jurisdiction; OQ-COMP-004 Q1-blocked).
- **Linter rule 188:** DSAR completed within statutory window; alert if approaching (T-7 days before expiry).

## Alternatives

- **Shred before export** (rejected). Errata E1; player loses access to their data; GDPR Art 15 violation.
- **Skip verification** (rejected). Errata E1; identity fraud; attacker impersonates player.
- **SE registry not preserved** (rejected). Phase 14 ADR-0085; excluded player re-registers; the 2023 GDPR enforcement is the canonical example.
- **Reorderable steps** (rejected). Errata E1 mandates fixed order; reorderable = E1 violation.
- **No statutory window tracking** (rejected). GDPR Art 12(3) mandates 30 days; missed = fine.
- **Export pack without all modules** (rejected). Incomplete export = GDPR Art 15 violation; player has right to ALL data.
- **Export pack not stored immutably** (rejected). Operator must prove export was generated; mutable export = no proof.

## Consequences

- DSARRequest model with E1-enforced FSM.
- Linter rule 186: E1 order (no skipping).
- Linter rule 187: SE-survives-erasure (HMAC pseudonymization).
- Linter rule 188: statutory window tracking.
- Export pack from all 11 module data classes; stored immutably (Phase 10).
- DSAR drill end-to-end test (acceptance criterion).
- Open question OQ-COMP-004: DSAR statutory window per jurisdiction (Q1-blocked).

## Validation Plan

- **DSAR drill end-to-end test:** verify → export → shred → SE survives → re-registration blocked (8 steps above).
- **E1 order test (linter rule 186):** attempt pending → shredded (skip verify + export); assert rejected with `E_DSAR_ORDER_VIOLATION`.
- **Export without verification test:** attempt pending → exported (skip verify); assert rejected.
- **SE-survives-erasure test (linter rule 187):** shred a player with active SE; assert SE registry retained (pseudonymized_identity); assert original player_uuid NULLed.
- **Re-registration blocked test:** attempt re-registration with same identity document; assert HMAC match; assert `E_SELF_EXCLUDED`.
- **Statutory window test (linter rule 188):** DSAR pending > 23 days; assert T-7 alert; DSAR pending > 30 days; assert `E_DSAR_WINDOW_EXCEEDED`.
- **Export pack completeness test:** generate export; assert all 11 data classes present; assert pack stored immutably.
